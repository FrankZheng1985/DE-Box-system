# 本地派送「柜 → 派送子订单 → 件」改造方案

飞书《EU-TMS 开发意见表》第 7 条（苏凌 2026-08-10 提）。
**状态：方案待 Frank 确认，尚未动手。**

Frank 2026-08-15 已拍板两条：

1. **结构**：一个柜 → 多个派送子订单 → 每单多件
2. **转单粒度**：客户确认报价后，**一个柜生成 N 张订单**（每个派送子订单一张）
3. **履约字段**（签收文件 / 跟踪号 / 服务渠道）：**放订单阶段**，询价不填

---

## 一、为什么要改

现在的询价是**两层**：一张询价单 → 一堆货物明细（一行一件），按客户单号分组。
三种服务共用这一套模板。

本地派送实际是**三层**：一个柜里装着发往不同地址的多票货，每票又有多件。
现在只能把它硬塞成两层 —— 派送地址只有一个（route_to），
所以一个柜要拆成几十张询价单分别填，取件地址和柜号还得重复抄几十遍。

---

## 二、数据模型（新增 2 张表 + 3 处加列）

```
询价单 inquiries（= 一个柜）
├── 柜号 container_no                        ← 新增列
├── 取件地址 route_from（含发货联系人）        ← 已有，第 8 条刚做
│
└── 派送子订单 inquiry_delivery_orders         ← 新表
    ├── 客户子单号 customer_sub_ref
    ├── 派送地址 delivery_address（公司名/姓名/电话/邮箱）
    ├── 汇总：件数 / 重量 / 体积 / LDM
    │
    └── 件明细 inquiry_cargo_items            ← 已有表，加一列 delivery_order_id
        └── 件号 / 品名 / 件数 / 长宽高 / 单件重
```

### 1. `inquiries` 加一列

| 列 | 类型 | 说明 |
|---|---|---|
| `container_no` | VARCHAR(30) | 柜号。其他服务类型留空 |

总票数、总件数**不存**，由子订单实时汇总 —— 存冗余字段迟早和明细对不上。

### 2. 新表 `inquiry_delivery_orders`（柜下的派送子订单）

| 列 | 类型 | 说明 |
|---|---|---|
| `id` | UUID | 主键 |
| `inquiry_id` | UUID | 属于哪个柜（询价单） |
| `line_number` | INT | 行号，(inquiry_id, line_number) 唯一 |
| `customer_sub_ref` | VARCHAR(100) | 客户给的子订单单号 |
| `delivery_address` | JSONB | 国家/邮编/城市/地址 + 公司名/收件人/电话/邮箱 |
| `quantity` / `weight_kg` / `volume_m3` / `ldm` | 数值 | 由件明细汇总回写，和现有询价表头一个口径 |
| `remarks` | TEXT | 备注 |

### 3. `inquiry_cargo_items` 加一列

| 列 | 类型 | 说明 |
|---|---|---|
| `delivery_order_id` | UUID | 这一件属于哪个子订单。**可空** |

**可空是关键**：卡派 LTL / 卡车 FTL 的件明细继续直接挂询价单（这一列为 NULL），
现有行为一个字都不用改。只有本地派送必须挂到子订单上。

### 4. 新表 `quotation_delivery_lines`（按子订单报价）

| 列 | 类型 | 说明 |
|---|---|---|
| `quotation_id` | UUID | 哪一版报价 |
| `delivery_order_id` | UUID | 哪个子订单 |
| `price` | NUMERIC(12,2) | 这一单的派送费 |

整柜合计仍用 `quotations.total_price`（现有字段），等于各行之和。
单开一张表而不是把报价存回 `inquiry_delivery_orders`，是因为**报价有版本**
（quotations.version），改一次价要留一版历史，存回询价单会把上一版覆盖掉。

### 5. `orders` 加一列

| 列 | 类型 | 说明 |
|---|---|---|
| `source_quotation_id` | UUID | 这张订单是哪张报价转出来的。可空 |

一柜转 N 单，而现有的 `quotations.converted_order_id` **带唯一索引、只能记一张**。
保留它记第一张（前端"跳转到订单"不用改），N 张订单靠这个新列反查。
柜号写进已有的 `orders.container_no`，**订单列表现在就支持按柜号搜索**
（`server/modules/order/routes.js:426`），一个柜的 N 张单能一次筛出来。

## 三、转单：一柜 → N 单

客户确认报价后，遍历子订单，每个建一张订单：

| 订单字段 | 取值 |
|---|---|
| `business_type` | LOCAL_DELIVERY |
| `pickup_address` | 柜的取件地址（N 张单相同） |
| `delivery_address` | 该子订单的派送地址 |
| `container_no` | 柜号（N 张单相同，用它把一个柜串起来） |
| `client_price` | 该子订单的报价 |
| `cargo_quantity` / `weight` / `volume` | 该子订单的汇总值 |
| `source_quotation_id` | 报价 ID |

⚠️ **这一步会一次性生成 N 张已过账凭证，只能冲销不能删**。
所以第一次真实客户单必须人工盯一遍，测试也只在本地库做。

---

## 四、分四步做，每步独立可上线

| 步骤 | 内容 | 能验收什么 |
|---|---|---|
| **1. 询价侧** | 迁移建表；本地派送专用建单表单（柜信息 + 子订单列表 + 每单件明细）；本地派送专用导入模板；运营端询价详情展示三层 | 客户能按柜提交询价，运营看得到完整三层 |
| **2. 报价侧** | 按子订单逐条报价 + 整柜合计；报价单和邮件展示到子订单粒度 | 运营能逐单报价，客户看到每单价格和合计 |
| **3. 转单** | 接受报价 → 一柜转 N 张订单；订单列表按柜号聚合查看 | 客户确认后订单正确生成，能按柜找回这批单 |
| **4. 履约** | 子订单的跟踪号、签收文件、服务渠道（落在订单上） | 派送完能回填跟踪号和签收单 |

前三步做完这条业务线就跑通了，第 4 步是发运之后的事，可以晚一轮。

---

## 五、要注意的几件事

- **导入模板要按服务类型分流**（意见第 7 条的前半句）：先选服务类型再导入。
  卡派 LTL 和卡车 FTL 继续用现在这份模板，本地派送用新模板（一行 = 一件，
  按「柜号 + 子单号」两级分组）。旧模板不能停用，客户手上还有存量。
- **`quotations.converted_order_id` 的唯一索引不能删** —— 它防的是一张订单被两张报价重复转出。
- **子订单单号是客户给的**（`customer_sub_ref`），不是系统编号，不占 ORD 计数器。
- 本地派送的订单初始状态仍是 `PENDING_DISPATCH`（现有逻辑，见 `quotation/service.js:119`）。
- 报价拒绝 / 询价删除时，子订单和报价行要跟着级联清掉。
