## 一、需求 vs 系统现状总对照

| # | 需求 | 现状结论 | 差距 |
|---|------|---------|------|
| 1 | 服务类型改为 卡车派送LTL / 卡车运输FTL / 本地派送 | `orders.business_type` 只有 `CURTAIN_SIDE`(篷布车)/`CONTAINER`(集装箱) 两值，前后端至少 5 处硬编码，两套独立状态机 | 需要三分类改造 + 数据迁移 + 本地派送是全新业务 |
| 2 | 客户确认报价后订单自动进"待审核" | **不存在**。报价 accept 只改状态，生成订单要运营手动点"一键下单"（`quotation/routes.js:342` convert-order）；且客户门户根本看不到报价、无法确认 | 需打通 接受→自动建单 闭环 + 客户门户报价确认页 |
| 3 | 订单各状态上传文件（装车图/CMR/POD） | 订单详情页（OrderDetail.tsx 1177 行）**没有任何上传功能**；CMR 是独立模块，上传时要手工粘订单 UUID；无 POD 文件概念（`orders.pod` 是"卸港"，不是签收凭证，**命名撞车**） | 需新建订单文件中心 + CMR 并入订单维度 |
| 4 | 两种建单方式：固定价 API 直推 / 询价报价 | **对外 API 能力为零**：无 API key、无外部端点、无 webhook | 需从零建开放 API 模块 |
| 5.1 | 询价三来源（客户门户/员工代建/易抵达 API） | 客户门户询价表单只有 5 个字段且 businessType 硬编码；**admin 端没有询价管理页面**（只有报价页）；API 来源为零 | 三个来源都要补/建 |
| 5.2 | 报价后自动邮件通知客户 + 识别回复 | **邮件链路整体是坏的**（详见"地基问题"）；无收信/IMAP 能力 | 先修邮件地基；回复识别建议改为"邮件内确认链接" |
| 5.3 | 服务商询价管理 + 权限隔离 | **不存在**承运商方向的询价；权限只有粗粒度 userType，任何 OPERATOR 全权限，无法隔离 | 依赖权限体系（需求9）先行 |
| 5.4 | 询价含 LDM/长宽高/电话/邮箱，一键复制/模板下载 | `inquiries` 表无长宽高、无电话邮箱；**LDM 全仓库零命中**；无按件明细表 | 需扩展询价数据结构（按件货物明细） |
| 6 | 客户等级 + 信用额度预警 | **DB 和引擎大半已有**：`clients.credit_limit/credit_level(A-D)/risk_category` + `core/credit-manager.js` 已在订单创建时生效。但 UI 有 bug（字段名错位显示不出）、超额预警无界面、人工释放 `overrideBlock()` 是死代码 | 主要是补 UI + 修错位 + 预警通知 |
| 7 | 运输公司分类/类型/备注 | `carriers` 表**无**分类、类型、备注字段 | 加字段 + 表单 + 筛选，工作量小 |
| 8 | 每客户可配置付款/状态邮件通知 | `notification_preferences` 表存在（按用户），但前后端契约不匹配保存必失败、事件 key 对不上、邮件渠道是空壳 | 修通 + 补付款提醒邮件 |
| 9 | 员工权限 + 客户多账号权限 | 8 个角色已 seed 但**无差别**（OPERATOR 一律放行）；`requirePermission` 是死代码（读不存在的 JWT 字段）；Sidebar/路由无权限守卫；客户多账号数据层支持但无自管理 | 需求最大的基建项之一 |
| 10 | 英/德三语 | 三端**零 i18n 基础设施**，全部硬编码中文；`users.language` 字段存在但无人读写 | 全新工程，放最后 |

## 二、探查发现的"地基问题"（新需求踩在这些坑上，必须先修）

这些是本次摸底发现的**现存 bug**，不修的话后面阶段做完也跑不通：

### A. 邮件/通知链路（阻塞需求 5.2、8）
1. `notification-engine.js` 的 `_queueEmail()` 只往 notifications 表插记录，**从不调用 sendEmail**，也没有任何 cron 轮询发送 → EMAIL 渠道是空壳。
2. `cron-jobs.js` 的"资质到期提醒"和"逾期催款"调用了**不存在的** `notificationEngine.send()`（只有 `notify()`），TypeError 被 catch 吞掉 → 这两个定时任务从未真正发过通知。
3. `email-service.js` 的 3 个邮件模板函数全仓库零调用；`server/env.example` 没有 SMTP_* 变量（生产大概率未配置，参考踩坑 005 PM2 环境变量问题）。
4. `Settings.tsx` 保存通知偏好发的是 `{preferences:[...]}` 数组，后端期望单条 `{eventType,...}` → 保存必失败；且前端 5 个小写 key 与后端 11 个大写 `NOTIFICATION_TYPES` 完全对不上 → 即使存进去也匹配不到。

### B. 数据/字段错位（阻塞需求 6、2）
5. `ClientList.tsx` 用 `credit_rating`/`receivable_balance`，后端返回 `credit_level`/`outstanding_amount` → 信用等级列永远 `-`、应收永远 0（典型踩坑 003）。
6. `ClientEdit.tsx` 付款条件下拉存 `net_30` 等字符串，DB `payment_terms` 是 INTEGER → 保存报错。
7. `quotation/routes.js:407` 作废功能写 `void_reason`，但 quotations 表**没有这一列**（缺迁移）；clients/carriers 表同样缺 `void_reason` 而代码在写。
8. `customer-portal/CreateOrder.tsx` 传 `pickupCountry/deliveryCountry`，后端期望 `pickupAddress` 对象 → 客户直接下单的地址落库异常。
9. `contact_inquiries` 表在任何 migration 里都没建过，官网留言接口应该在报错。
10. 订单完成自动开票的 due_date 硬编码 30 天，不读 `clients.payment_terms`（需求 6/8 的账期要真正生效必须改这里，`order/service.js:271`）。

### C. 工作区协调
- 当前工作区有**未提交的"基础数据维护模块"**（MasterData.tsx + 102/103 迁移 + system/routes.js 改动）。开新阶段前必须先把它提交部署掉，否则各 worktree 之间会冲突。新迁移文件从 **104** 号开始编。
- `md_vehicle_types` 种子里有 `CURTAIN_SIDE`（篷布车·车型），和 `business_type` 的 `CURTAIN_SIDE`（服务类型）**撞名不同义**，改造需求 1 时不要混用。

## 三、开发阶段划分（每个阶段 ≈ 一个 Opus 5 对话 + 一个 worktree）

> 推荐按编号顺序做。P0 必须最先；P8（API 对接）的**接口契约讨论要尽早启动**（涉及易抵达/傲翼/翼能外部团队），但开发可以靠后。

### P0 · 地基修复包（1-2 个对话）
**目标**：把上面"地基问题" A + B 全部修掉，让邮件真正能发出去、信用/客户数据正确显示。
- 修 notification-engine 邮件队列：加 cron 轮询 notifications 表中 `channel='EMAIL'` 未发送记录 → 调 `sendEmail`，加 `sent_at`/失败重试标记（需加列或状态字段，走迁移）
- 修 cron-jobs 两个任务改用 `notify()` 正确签名
- env.example 补 SMTP_*/OSS_* 样例；生产配置 SMTP 后 `pm2 delete` 重启（踩坑 005）
- 对齐通知偏好前后端契约 + 事件 key 统一为后端 11 个大写常量；Settings 页打开时 GET 已存偏好
- 迁移 104：quotations/clients/carriers 补 `void_reason`；建 `contact_inquiries` 表
- 修 ClientList/ClientEdit 字段错位、payment_terms 类型；修 customer-portal CreateOrder 地址字段
- 自动开票 due_date 改读 `clients.payment_terms`
- **验收**：报价作废不报错；客户列表能显示信用等级和应收；给测试邮箱真实发出一封状态通知邮件。

### P1 · 服务类型三分类改造（需求 1）（1-2 个对话）
**目标**：`business_type` 从两值改为三值，前后端所有入口统一。
- 推荐枚举：`TRUCK_LTL`（卡车派送 LTL）/ `TRUCK_FTL`（卡车运输 FTL）/ `LOCAL_DELIVERY`（本地派送）
- 数据迁移（105）：存量 `CURTAIN_SIDE→TRUCK_LTL`、`CONTAINER→TRUCK_FTL`；**迁移前备份**
- 状态机映射：TRUCK_LTL 沿用现 `TRUCK_STATUS_FLOW`；TRUCK_FTL 沿用现集装箱逻辑（container 字段按需显示）；LOCAL_DELIVERY 新增简化流（待报价→待派送→派送中→已签收）+ `tracking_number` 字段 + 跟踪号反馈给客户
- 改动点（至少）：`order/service.js:69,107` 两台状态机选择、`quotation/routes.js:139`、`OrderCreate.tsx:32`、`OrderManagement.tsx:69-95` 三个 tab、`QuotationCreate.tsx:52-55`、Excel 导出 `bizTypeMap`（`order/routes.js:75`，现在就和实际值对不上）
- 清理历史遗留：`005_add_business_type.sql` 的 release/transport/both 旧语义确认无引用后归档说明
- ⚠️ 决策点见"四、待确认"第 1 条，**动手前先确认映射**。

### P2 · 订单文件中心（需求 3）（2 个对话）
**目标**：以订单为维度管理文件，按状态引导上传。
- 迁移 106：新表 `order_files`（order_id, file_category: `LOADING_PHOTO`/`CMR`/`POD_PROOF`/`OTHER`, file_url, file_type, uploaded_by, uploaded_at, remarks）。**签收凭证类别命名用 `POD_PROOF`，避开 `orders.pod`（卸港）撞名**
- 后端：`order/routes.js` 加 `POST /:id/files`、`GET /:id/files`、`DELETE /files/:fileId`（复用 CMR 的 multer memoryStorage + OSS 路径规则 `orders/{订单号}_{柜号}/`；20MB；PDF/JPG/PNG/WebP）
- OrderDetail.tsx 加"文件"区块：按当前状态给出引导（运输中→提示传装车图+CMR，装车图要求车牌+货物可见；已到达/派送完成→提示传 POD），缺件时黄色提醒
- CMR 模块改造：`cmr_documents` 保留（签署状态/货损是它的专属价值），CMR 上传入口并入订单详情页；CMRManagement.tsx 保留为汇总视图，上传弹窗把"手粘 UUID"换成订单搜索选择器
- 修 carrier-portal `UploadCMR.tsx`（现在用 JSON 传不了文件，改 FormData）；customer-portal 可查看/下载本公司订单文件
- 接通 `CMR_UPLOADED` 通知（已 import 未调用）

### P3 · 询价报价闭环·客户侧（需求 2 + 5.1 前两种来源 + 5.4）（2-3 个对话，本次核心）
**目标**：询价→报价→客户确认→自动生成待审核订单，全链路打通。
- 迁移 107：
  - `inquiries` 补：联系人电话/邮箱、结构化国家/地址/邮编、`ldm NUMERIC`
  - 新表 `inquiry_cargo_items`（按件明细：单号/件数/长/宽/高/单件实重/单件体积，行级 LDM，汇总回写 inquiries）
- admin 新建**询价管理页**（现在完全没有）：列表、详情、状态、"由此报价"按钮（把 inquiryId 带进 QuotationCreate——后端已支持，前端一直没接）
- QuotationManagement 与询价联动，形成"询价 tab + 报价 tab"或上下联动布局
- **需求 2 核心**：`POST /quotations/:id/accept` 里自动调 `orderService.createOrder` 生成 `PENDING_REVIEW` 订单 + `QUOTATION_TO_ORDER` 单据流（等于把 convert-order 逻辑并进 accept；保留手动按钮兼容）。同时给 accept/reject 加身份校验（现在任何登录用户都能调）
- customer-portal：询价表单升级（业务类型可选、按件明细录入、LDM 自动算）；新增"我的报价"页，客户可查看金额、**接受/拒绝/待定**；接受即触发自动建单
- **5.4 一键复制/下载**：询价详情和列表勾选处加"复制摘要"（固定文本模板，含单号/国家/地址/邮编/电话/邮箱/件数/长宽高/实重/体积/LDM，直接可粘给服务商）和"导出 Excel（固定模板）"——这是清平姐的重点痛点，优先做复制功能
- 修 customer-portal InquiryList 的小写状态 map（踩坑 004 原案发地）

### P4 · 报价邮件通知 + 客户通知设置（需求 5.2 + 8）（1-2 个对话，依赖 P0）
- 报价"发送"动作触发邮件：订单基本信息 + 报价金额 + **三个确认链接（同意/拒绝/待定）**，链接带一次性 token，点击直接回写报价状态（代替"解析客户回复邮件"——系统无 IMAP 收信能力，解析方案不做，见"四、待确认"第 2 条）
- 补齐付款提醒邮件（到期前 N 天 + 逾期）、货物状态更新邮件：复用 email-service 三个从未被调用的模板并扩充
- 通知偏好从"按用户"扩展到客户公司维度可管理（client_admin 可为本公司设置），提醒天数/频次进 `system_settings`（已有 key-value 表和读写接口，前端一直没用）
- 逾期自动把 `payment_status` 翻成 OVERDUE 的 cron 一并补上

### P5 · 权限体系（需求 9）（2-3 个对话，基建） ✅ 2026-08-02 开发完成
> 开发记录：`docs/开发记录/2026-08-02-P5权限体系.md`；迁移号实际用了 **109**（106-108 已被 P2/P3/P4 占用）。
> 除计划内容外，还补了订单/清关/GPS/应收应付的**租户隔离**——这些接口原来直接用 query 参数筛选，
> 门户账号换个参数就能看别家数据（详见踩坑 023）。
**目标**：员工分权 + 客户多账号分权，为 P6 的信息隔离铺路。
- 推荐走**权限码方案**（permissions + role_permissions + `requirePermission` 中间件——即全局规范里的"权限四件套"模式），不用 V2 那套没落地的 auth_objects（15 个对象 seed 了但 auth_values 空、无中间件消费，救活成本高于新建）
- 修 `requirePermission`/`requireAdmin` 读错 JWT 字段的死代码；JWT payload 加 permissions（或登录后单独拉取）
- 收紧现状漏洞：client/carrier 模块现在**只挂了 authenticateToken**，CLIENT/CARRIER 账号也能读写全部客户和承运商主数据——必须加 requireUserType
- admin：角色权限管理页（8 个角色已 seed）；Sidebar 按权限过滤菜单；路由守卫
- 客户门户：client_admin 可管理本公司子账号（新建/停用/角色分配），client_user 只读或受限
- 提交前跑权限-菜单同步校验（参照全局规范四件套）

### P6 · 服务商询价管理（需求 5.3）（1-2 个对话，依赖 P3 + P5）
- 迁移 108：新表 `carrier_inquiries`（关联 client 询价单 id + carrier_id + 询价内容 + 服务商报价 + 状态），形成"客户询价 ↔ 服务商询价"对照
- 询价详情页上下分区：上=客户询价，下=对该单发起的服务商询价（可对多家服务商发）；成本回填 `carrier_cost` 供报价参考
- **权限隔离**：服务商询价区块和 API 均挂 `requirePermission('carrier_inquiry:view')`，只有服务商管理岗看得到；普通报价/操作岗不可见（P5 产物）

### P7 · 客户等级信用 + 服务商分类（需求 6 + 7）（1 个对话，独立可插队）
- 客户：`credit_level`(A-D) 已有——与需求的"VIP/普通"如何对应见"四、待确认"第 5 条；补 ClientList/表单里的等级和风险类别编辑；信用超额预警接通知引擎（credit-manager 已产出 WARNING/BLOCKED，把结果推给运营+客户邮件）；给死代码 `overrideBlock()` 加 API + "信用释放"按钮 + `credit_check_logs` 查看页
- 承运商：迁移 109 加 `carrier_category`（`EXTERNAL` 外部服务商 / `OWN_FLEET` 自营车辆）、`carrier_type`（`PLATFORM` 平台型 / `FLEET` 自营车队型 / `INDIVIDUAL` 个体车辆）、`remarks TEXT`（特点/优势/短板）；CarrierList 列表列+筛选+表单同步；变更追踪 `CARRIER_FIELDS` 白名单加新字段

### P8 · 开放 API 对接平台（需求 4 + 5.1 第三种来源）（3-4 个对话 + 外部协调）
**目标**：傲翼/翼能/易抵达系统直推订单和询价单。
- 迁移 110：`api_keys` 表（partner 名称、key hash、状态、限速配置）+ `api_request_logs`
- 新模块 `server/modules/open-api/`（按五件套结构）：独立前缀 `/api/open/v1/`，API-Key 认证中间件（可复用已写好但从未启用的 `ipWhitelist` 叠加）
- **两类端点，分开设计**（PDF 明确要求区别开发）：
  - `POST /open/v1/inquiries` — 按订单号维度推询价单（国家/单号/地址/邮编/长宽高/实重/LDM/体积 → 复用 P3 的 inquiry_cargo_items 结构）
  - `POST /open/v1/orders` — 按柜号维度直接下单（固定价客户，跳过询价直接落 `PENDING_REVIEW`，进审核派单流程）
- 幂等（同 partner+外部单号去重）、字段校验、错误码文档；给对方出一份 Markdown 接口文档
- ⚠️ **前置动作（现在就可以做）**：和易抵达/傲翼/翼能确认字段清单与推送方式——契约不定，开发排不了。见"四、待确认"第 4 条

### P9 · 三语国际化（需求 10）（3-4 个对话，放最后）
> 放最后的原因：P1-P8 会大量改 UI 文案，先做 i18n 等于每个阶段都要双倍维护语言包。
- 三端引入 react-i18next（新依赖，引入前按规矩报备）+ `locales/zh|en|de` 语言包；Header 加语言切换；选择持久化到 `users.language`（字段已有，一直没人用）
- 分四批：admin（最大）→ customer-portal → carrier-portal → 后端 message/邮件模板/Excel 表头（按请求的 `Accept-Language` 或用户 language 返回）
- 日期/金额格式化统一走 `Intl`（现有 ~40 处硬编码 `toLocaleString('zh-CN'/'de-DE')` 顺带收敛）
- 德/英翻译初稿由 AI 生成，**物流术语（CMR、清关、放单、LDM 等）请德语同事校对一遍再上线**
