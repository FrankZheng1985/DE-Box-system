## 一、结论摘要

系统**主干业务链路完全打通**，端到端跑通了「询价 → 报价 → 发送 → 客户接受 → 自动建单 → 派单 → 承运商接单」全流程，
租户隔离与权限体系经受住了针对性越权测试。同时发现 **2 个 P0 阻断缺陷、5 个 P1 严重缺陷、2 个高危安全问题**，
其中报价详情页在任何真实数据下都会整页崩溃，财务建单功能完全不可用——这两条建议优先修。

| 级别 | 数量 | 说明 |
|------|------|------|
| **P0 阻断** | 2 | 报价详情页崩溃、财务建单功能不可用 |
| **P1 严重** | 5 | 含 2 个高危安全问题 |

### 必须优先修的 5 条

1. **报价详情页整页崩溃**（P0）—— 有报价数据就必崩，现在没暴露只因表是空的

## 三、P1 严重缺陷

### P1-1【安全·高危】Webhook 测试端点存在 full-read SSRF

- **端点**：`POST /api/v1/open-api/keys/:id/webhook-test`
- **问题**：`webhook-service.js` 直接 `fetch(apiKey.webhook_url)`，URL 只校验 `^https?://.+`，**无内网/回环/元数据地址黑名单**，且把目标响应体切 200 字符放进 `responseSnippet` **回显给调用方**
- **实证**：
  - `http://127.0.0.1:8899/ssrf-catch` → 监听器实收到服务器发出的 POST（带签名头）
  - `http://localhost:3002/api/v1/auth/login` → 200，响应体被回显
  - `http://169.254.169.254/latest/meta-data/` → 本机非云环境所以失败，但**服务器确实发起了连接**
- **生产风险**：生产在阿里云 ECS，`169.254.169.254` 是可达的实例元数据端点，可读出临时凭证
- **修法**：出站 URL 黑名单（10/8、172.16/12、192.168/16、127/8、169.254/16、::1、fc00::/7），拒绝解析到内网的域名（防 DNS rebinding 需在连接层校验），生产强制 https，`responseSnippet` 只返回状态码不回显 body

### P1-2【安全·中高】生产静态页面无任何安全响应头

- **实测对比**：
  ```
  /api/health   → x-frame-options: DENY, x-content-type-options: nosniff,
                  x-xss-protection, referrer-policy, permissions-policy  ✅
  /login, /admin/, /customer/, /carrier/, /  → 一个安全头都没有  ❌
  ```
- **原因**：安全头由 Express 的 `securityHeaders` 中间件添加，只覆盖 `/api/*`；nginx 直出的 HTML 走的是另一条路径
- **风险**：三个门户的登录页**都能被嵌进 iframe → 点击劫持**；无 HSTS → 首访可被 SSL 剥离
- **修法**：nginx server 块加 `add_header X-Frame-Options DENY always;` 等；HSTS 建议 `max-age=31536000; includeSubDomains`（先小 max-age 观察）
- **附带**：响应头暴露 `x-powered-by: Express` 和 `server: nginx/1.24.0 (Ubuntu)`，建议关掉

### P1-3 发票模板页字段名全错 + 假保存

- **位置**：`admin/src/pages/InvoiceTemplates.tsx`
- **字段名全错**：后端 snake_case，前端 interface camelCase，只有 `id`/`currency` 对得上：
  `tpl.name`→实为 `template_name`、`clientType`→`client_type`、`taxRate`→`tax_rate`、
  `triggerRule`→`auto_trigger`，而 `tpl.lastUsedAt` **库里根本没这列**
- **会崩**：`:94` 和 `:130` 对 `tpl.taxRate.replace('%','')` 调用 → `undefined.replace()` → 编辑/预览弹窗 TypeError
- **假保存**：`:110` 调 `PUT /invoice-templates/:id`，**后端没有 PUT 路由**（只有 GET / GET rules / GET :id / POST）→ 404 被 `:114` 的空 catch 吞掉（注释写着"接口可能未完全实现，静默处理"），finally 照样更新本地 state + 关窗 → **用户看到"保存成功"，实际没存，刷新即丢**
- **为什么现在没暴露**：`:62` 是 `if (res.data && res.data.length > 0) setTemplates(res.data)`，空表时显示前端硬编码的 3 张演示卡片，看起来一切正常。**第一条真实模板入库即全线崩塌**

### P1-4 `/quotes/:id/edit` 路由不存在，点「编辑」进白屏

- **位置**：`admin/src/App.tsx:150-152` 缺路由 ← `QuotationManagement.tsx:309` 有 `navigate('/quotes/:id/edit')`
- **实证**：直接访问该路径，框架（侧边栏/顶栏）在、**内容区完全空白**，无 404 提示、控制台无报错
- **加重**：整个 App.tsx **没有 `path="*"` 兜底路由**，任何未匹配路径都是空白页
- **对比**：orders 和 inquiries 都配了完整的 `/:id/edit`，唯独 quotes 漏了

### P1-5 财务收款/作废弹窗单号显示空白

- **位置**：`FinanceManagement.tsx:744`（收款）、`:939`（作废）读 `row.bill_no`
- **实际字段**：`financial_records.record_number`（同文件表格主体 `:134` 用的就是 `record_number`，是对的）
- **风险**：作废弹窗文案是「即将作废 ___」——单号空白时**用户无法确认作废的是哪一张**，而作废不可逆
- **TypeScript 为何没拦住**：`BillRow` interface 带索引签名 `[key: string]: any`，任意字段名都合法

## 四、P1/P2 安全问题（已确认，非阻断）

### 订单导出缺纵深防御（架构层）

`GET /api/v1/orders/export` 只挂了 `requirePermission('order:export')`，**没有 `requireUserType('OPERATOR')`**，
导出 SQL 也不按登录方收窄（`WHERE 1=1`，含 `client_price`/`carrier_cost`）。
对比同文件 `/stats` 就明确加了 OPERATOR 闸门。

实测：门户账号当前调用返回 403，但**原因是门户角色恰好没配 `order:export` 权限码，不是架构挡住的**。
模拟"运营在角色权限页误勾一格"后，siemens 立刻能导出**含全部租户报价与成本**的 xlsx。

> 同类根因还有两处：`PUT /system/roles/:roleId/permissions`、`PUT /system/settings/company`。
> 建议统一排查所有 `system`/`export`/`open-api` 路由是否都补齐了 userType 闸门。

### 公司设置无权限码门槛（可改银行账号）

`PUT /api/v1/system/settings/company` 只挂了 `authenticate`，**不查任何权限码**。
实测把 `carrier_admin` 的 `carrier_portal:company_settings` 权限码移除后**仍能改成功** → 该权限码形同虚设。
承运商银行账号（`bank_name`/`bank_account`）是**打款字段**，任何绑定了公司的门户账号（含 `carrier_driver`）都能改。

好消息：**越权改别家公司已被挡住** —— 在 body 里塞别家 `id`/`clientId` 会被忽略，
写入对象只认 JWT 里的 `linkedEntityId`。

### 免登录咨询接口无限流 + 邮件 HTML 注入

- `POST /api/v1/contact` 连发 30 次全部 200（对照 `/auth/login` 第 10 次后就 429）→ 可刷成邮件轰炸 + 表膨胀
- `contact/routes.js:46-49` 把 `name`/`email`/`message` **原样插进邮件 HTML**，全仓无任何转义工具。
  `email` 被放进 `href="mailto:${email}"`，`">` 即可闭合属性注入任意标签 → 运营打开通知邮件时渲染攻击者控制的 HTML

## 十、两点方法论提醒

1. **空表是巡检盲区**。本次 4 个字段名 bug（发票模板、报价详情 ×2、财务弹窗）全部发生在空表页面——
   接口全绿、TypeScript 全绿、页面看起来正常，**上线遇到第一条真实数据才炸**。
   建议给 dev 库每张业务表灌 1-2 条种子数据。
2. **索引签名不是唯一元凶**。踩坑 033 的防护规则如果只盯 `[key: string]: any`，
   会漏掉本次发票模板和报价详情这几个——它们的 interface 没有索引签名，只是**自信地写错了**。
   根因是 `api.get<ApiResponse<T>>()` 这个泛型断言从不校验实际 JSON，
   一个「完整但错误」的 interface 照样能完美通过类型检查。
