# 030 认证中间件在前，新路由"上线了"和"没上线"返回一模一样

## 问题现象

P8 第三阶段加了两个新端点（`GET /api/open/v1/orders/:externalOrderNo` 等），
push 部署后照惯例 curl 验证：

```bash
curl https://kalunasped.com/api/open/v1/orders/NOPE
# {"code":401,"message":"缺少 X-API-Key 请求头","data":{"errorCode":"AUTH_ERROR"}}
```

看到 401 就"确认路由生效了"——**这是错的**。当时 CI 还在跑（23 秒），
新代码根本没上服务器，返回的 401 是旧代码给的。

## 根本原因

模块入口把认证挂在所有路由前面：

```js
router.use(apiRequestLogger)
router.use(apiKeyAuth)      // ← 任何路径先过这里
router.get('/orders/:externalOrderNo', ...)   // 新加的
```

`router.use()` 对**挂载前缀下的任意路径**生效，不管后面有没有匹配的路由。
所以：

| 情况 | 无钥匙请求新路径的响应 |
|------|----------------------|
| 新代码已上线 | 401（被 apiKeyAuth 拦下） |
| 新代码没上线 | 401（**同样**被 apiKeyAuth 拦下，压根走不到"路由不存在"） |

两者完全无法区分。而"401 说明服务在跑"这个直觉又太顺理成章，
很容易就当成验证通过了。

同类形态：任何挂在路由前的全局中间件（限流、租户校验、维护模式开关）
都会把"新端点是否存在"这个信息吃掉。

## 正确做法

**带上能过认证的凭据，验到业务响应为止**：

```bash
# 临时签发一把冒烟钥匙（验完即删）
node scripts/create-api-key.js create --partner-code P8SMOKE ...

curl https://kalunasped.com/api/open/v1/orders/NOPE -H "X-API-Key: $KEY"
# {"code":404,"message":"未找到该单号对应的订单","data":{"errorCode":"NOT_FOUND"}}
#   ↑ JSON 格式的 404 只可能来自新 handler；
#     旧代码没有这个路由，会落到 Express 默认 404（HTML 页面）
```

关键是找一个**只有新代码才能产生的响应特征**：这里是"JSON 且带 errorCode 的 404"，
区别于 Express 默认的 HTML `Cannot GET /...`。

其他可用的确认手段（按可靠性排序）：

1. 直接查服务器上的文件：`ssh eu-tms "grep -c getOrderStatusForApi .../routes.js"`
2. 等 CI 明确成功：`gh run watch <run-id> --exit-status`，别凭"过了一会儿"就认为部署完了
3. PM2 重启时间：`pm2 list` 看 uptime 是否是刚刚

验证用的临时钥匙、测试数据记得**连同日志一起清理**，别在生产留残留。

## 防护规则

1. **验证新端点，必须验到只有新代码才有的响应**。任何在路由之前拦截的中间件
   （认证、限流、租户校验）都会让"新路由"和"没这个路由"的响应变得一样。
2. **不要把"服务能响应"当成"新代码已部署"**。这两件事之间隔着一整条 CI/CD。
3. **部署后先确认代码真的到了服务器**（grep 文件 / 等 CI exit code / 看 PM2 uptime），
   再做功能验证——顺序反了会得到"验证通过"的假象。
4. 生产功能验证要造的临时凭据/数据，**开始前就想好怎么清理**，验完立刻删干净。
