# 040 · 空表让前端字段名写错永远暴露不出来

## 问题现象

一批页面在测试环境里"看起来完全正常"，接口 200、TypeScript 零报错、ESLint 零 error，
但**一旦有真实数据就全线崩塌**：

- 报价详情页 `/quotes/:id`：**整页崩溃**，红字 `Objects are not valid as a React child`
- 发票模板页：所有卡片字段变空白，点编辑/预览直接 TypeError
- 财务收款/作废弹窗：单号一直是空白（作废弹窗写着「即将作废 ___」）

## 根本原因

**空表是巡检盲区。** 这三处的共同点是：

1. 前端 interface 是**臆造的字段名**，和后端返回对不上
2. 但对应的表在 dev 库里是空的，页面走的是空态或前端硬编码的演示数据
3. 于是接口全绿、类型检查全绿、页面看着正常 —— 直到第一条真实数据入库

三个具体例子：

| 页面 | 前端读 | 后端实际 |
|---|---|---|
| QuotationDetail | `route_from`（当字符串渲染） | jsonb `{country, city}` → React 抛错崩整页 |
| InvoiceTemplates | `name` / `clientType` / `taxRate` / `triggerRule` / `lastUsedAt` | `template_name` / `client_type` / `tax_rate` / `auto_trigger`，`lastUsedAt` **库里根本没这列** |
| FinanceManagement | `row.bill_no` | `record_number` |

## 为什么 TypeScript 没拦住

两个不同的原因，**只防其中一个是不够的**：

1. **索引签名兜底**：`FinanceManagement` 的 `BillRow` 带 `[key: string]: any`，
   于是 `row.bill_no` 这种查无此字段的写法照样通过类型检查。
2. **interface 写得完整但就是错的**：`InvoiceTemplates` / `QuotationDetail` 的
   interface **没有**索引签名，只是把字段名整套写错了。
   `api.get<ApiResponse<T>>()` 这个泛型断言从不校验实际 JSON，
   一个"完整但错误"的 interface 能完美通过 tsc。

> 踩坑 033 的防护规则如果只盯 `[key: string]: any`，会漏掉后面这一类。

## 防护规则

1. **dev 库每张业务表至少灌 1-2 条种子数据**。空表页面 = 没被真正测过。
2. **写 interface 前先把接口跑一次**，用真实返回的 key 对照，别照着页面上的中文标签臆造：
   ```bash
   curl -s -H "Authorization: Bearer $T" "$API/finance/receivables?pageSize=1" \
     | node -pe 'JSON.stringify(Object.keys(JSON.parse(require("fs").readFileSync(0)).data[0]))'
   ```
3. **禁止在列表行的 interface 上加 `[key: string]: any`**。
   去掉它往往会立刻暴露出一批同类错误（本次去掉后当场又冒出 `r.name`、`r.status` 两处）。
4. **jsonb 列一律当对象处理**，不要直接丢进 JSX 渲染。
   项目里已有现成写法可抄：`QuotationManagement.tsx` 的 `routeText()`。
5. **警惕"演示假数据打底"**：
   ```js
   // ❌ 空表时显示前端硬编码的假卡片，让人以为功能是好的
   if (res.data && res.data.length > 0) setTemplates(res.data)
   ```
   应该老老实实显示空态。假数据比空白更危险 —— 它同时掩盖了字段名错误**和**"还没配数据"这个事实。

## 涉及文件

| 文件 | 问题 |
