# 049 修好了存储却没修展示，字段名对不上照样白存

## 问题现象

前一天刚修完踩坑 047：建单页传的 `pickupContact` / `deliveryPhone` 后端从来没接收，
改成在 service 层并进地址 JSONB，查库确认存进去了、自测也断言了
`pickup_address.contactName === 'Max'`，收工。

第二天做别的需求时顺手打开管理端订单详情页，发现那一整块「联系人信息」
**装货联系人、卸货联系人全是 `-`** —— 明明库里有值。

## 根本原因

详情页读的键和后端写的键不是一个：

```tsx
// admin/src/pages/OrderDetail.tsx —— 一直这么写
interface Address {
  contact: string     // ← 页面期待的键
  phone: string
}
<span>{pickupAddr.contact || '-'}</span>
```

```js
// server/modules/order/service.js —— 昨天新写的
return { ...address, contactName: name, contactPhone: phone }   // ← 实际写入的键
```

`contact` vs `contactName`。JSONB 是无 schema 的，读一个不存在的键得到 `undefined`，
`|| '-'` 兜底成一条横线 —— **不报错、不警告、看起来像「这单没填联系人」**。

更值得记的是链条：**这个字段之前根本没存过**，所以详情页那块从上线起就一直是 `-`，
没人当成 bug；等我把存储修好，它依然是 `-`，于是「修了等于没修」很容易蒙混过关。

## 正确代码

```tsx
// 接口和取值都对齐后端实际写入的键
interface Address {
  country?: string
  city?: string
  zipCode?: string
  address?: string
  contactName?: string    // ← 与 service.js 的 mergeContactIntoAddress 一致
  contactPhone?: string
  reference?: string      // 集装箱单的提柜参考号
}

<span>{pickupAddr.contactName || '-'}</span>
```

## 防护规则

1. **「让字段真正存下来」的修复，必须一路验到页面**。查库断言只证明了存储端，
   证明不了展示端 —— 这两端本来就是各写各的，字段名对不上是常态。
   验收标准要写成「在页面上看见这个值」，不是「库里查得到」。
2. **JSONB 字段名没有编译期保护**。列名写错 SQL 会报错，JSONB 键写错只会得到 undefined。
   所以 JSONB 的键必须有一处明确的定义作为准绳（本项目是 service.js 的
   `mergeContactIntoAddress`），前端接口按它写，别各写各的。
3. **`|| '-'` 这类兜底要警惕**：它让「没数据」和「取错键」长得一模一样。
   写兜底时问一句「如果这个兜底天天被走到，我能发现吗」（踩坑 013 防护第 2 条的复现）。
4. 排查这类问题最快的一招：**先查库拿到真实 JSON，再拿真实键名去代码里 grep**，
   而不是从页面往回猜。

## 涉及文件

- `admin/src/pages/OrderDetail.tsx`（Address 接口 + 联系人区块取值）
- `server/modules/order/service.js`（`mergeContactIntoAddress`，键名的准绳）
