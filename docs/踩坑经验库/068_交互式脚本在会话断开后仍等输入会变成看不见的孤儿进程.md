# 068 交互式脚本在会话断开后仍等输入，会在生产变成看不见的孤儿进程

> **2026-08-18 订正**：这篇初版把根因写成了「脚本 import 业务模块拉起 pg 连接池、
> 事件循环永不清空」。**那是错的**——`reset-user-password.js` 本来就有
> `db.closePool()` + `process.exit(0)`，走到结尾一定会退出。
> 真正的原因是它**根本没走到结尾**，卡在等密码输入那一步。
> 根因写错会把后来人引到"给脚本加 exit"这条修不好的路上，所以整篇重写。

## 问题现象

2026-08-17 做上线验证时顺手 `ps` 了一下生产，发现一个进程从 **8 月 3 日跑到当天，14.9 天**：

```
root  1068836  PPID=1  node scripts/reset-user-password.js suling
内存 53MB ｜ CPU 时间 utime 16 + stime 3（约 0.19 秒）｜ 握着 1 条 RDS 连接
```

它的特征是「哪儿都看不到」：

- **不在 `pm2 list` 里** —— 不是 pm2 起的，pm2 管不着
- **PPID=1** —— 启动它的 SSH 会话早断了，进程被 systemd 收养
- **没有任何面板会提示** —— 不像后台任务会显示 Running
- CPU 时间近乎为零，也不会因为吃 CPU 被发现

## 根本原因

脚本是**交互式**的：查完用户、打印完目标账号信息之后，
调 `askHidden()` 等人输入新密码。

```js
const found = await db.query('SELECT ... FROM users WHERE username = $1', [username])
// ← 到这里已经建了连接池、查了库，所以进程握着一条 RDS 连接
process.stdout.write(`目标账号: ...`)
const password = await askHidden('请输入新密码（不会显示）: ')   // ← 卡在这里
// ...下面才是 db.closePool() 和 process.exit(0)，永远走不到
```

`readline` **不会因为 SSH 断了就结束**。操作者那天大概是看到提示后没继续
（或者网断了），SSH 会话没了，而进程还在等 stdin —— 一等 15 天。

所以这跟连接池没关系：连接池是「已经建了、还没关」，
而不是「关不掉」。**脚本卡在中间，后面的清理代码一行都没执行。**

## 正确做法

交互式脚本必须**能自己结束**，等输入这一步要有两条退出路：

```js
// server/scripts/lib/prompt.js
export function askHidden(prompt, timeoutMs = 5 * 60 * 1000) {
  return new Promise((resolve, reject) => {
    const rl = readline.createInterface({ input: process.stdin, output: process.stdout, terminal: true })
    let answered = false

    // ① stdin 被关掉（SSH 断开 / 管道结束 / Ctrl-D）
    //    正常应答也会触发 close，靠 answered 区分：没答就关 = 被动断开
    rl.on('close', () => {
      if (answered) return
      reject(new Error('输入已中断（连接断开或输入结束），未做任何改动'))
    })

    // ② 等太久
    const timer = setTimeout(() => {
      if (answered) return
      reject(new Error('等待输入超过 300 秒，已自动退出，未做任何改动'))
    }, timeoutMs)

    rl.question(prompt, (answer) => {
      answered = true
      clearTimeout(timer)
      rl.removeAllListeners('close')
      rl.close()
      resolve(answer)
    })
  })
}
```

抛出的错由调用方现成的 `main().catch()` 接住，那里会关连接池并 `exit(1)` ——
**不用给每个脚本单独加退出逻辑**。

`reset-user-password.js` 和 `create-client-portal-user.js` 原先各抄了一份
`askHidden`，已抽到 `server/scripts/lib/prompt.js` 共用，免得下次再抄第三遍。

## 防护规则

1. **写交互式命令行脚本时，等输入必须带超时和 close 处理。**
   「用户会看着终端把它跑完」这个假设在生产上不成立。
2. **在生产跑完脚本，当场 `ps -ef | grep <脚本名>` 确认它退出了。**
   看到命令打印完提示就以为结束了，是这个坑的全部来源 ——
   而交互式脚本恰恰会停在"打印完提示"的那一刻。
3. **定期巡检**（发现这个进程用的就是这条）：
   ```bash
   ssh eu-tms "ps -ef | grep '[n]ode' | grep -v 'PM2\|germany-box\|pm2-logrotate'"
   ```
   输出应该是空。`pm2-logrotate` 是正常常驻，别误杀。
4. **kill 前先取证**，别看见长时间运行就杀：
   ```bash
   PID=xxx
   awk '{print $14, $15}' /proc/$PID/stat     # utime stime，接近 0 = 空转
   tr '\0' ' ' < /proc/$PID/cmdline           # 当时到底跑的什么
   ss -tnp | grep "pid=$PID"                  # 是否握着数据库连接
   pm2 list                                   # 确认不是在用的服务
   ```
   隔一会儿再取一次 CPU 时间对比，两次完全一样才敢断定是空转 ——
   只看一次分不清「空转」和「跑得慢」。
5. **排查这类进程，先看它卡在哪，别先怀疑连接池。**
   `/proc/<pid>/stat` 第 3 列是状态：`S` = 睡眠等 I/O（多半在等输入或等网络），
   配合 CPU 时间接近 0，基本就能锁定「卡在某个 await 上」而不是「跑完了不退出」。
