# 069 门户接口按 `o.*` 透传，把承运商成本价发给了客户

> 日期：2026-08-27
> 模块：订单（order）／客户门户 + 承运商门户
> 性质：现存漏洞，在做「客户端订单详情」（飞书开发意见 #11）时顺带查出并堵掉

---

## 问题现象

**没有任何现象。** 页面一切正常，接口全 200，日志干净。

客户门户「我的订单」列表和订单详情接口，返回的 JSON 里一直带着
`carrier_cost`（我们付给承运商的成本价）、`carrier_score`（承运商评分）、
`credit_level`（这家客户的信用等级）以及凭证号、公司代码等内部字段。

页面上看不到，是因为前端**没有渲染**它们 —— 但数据确确实实发到了客户的浏览器里，
F12 打开 Network 面板看响应体就能读到进价，算一次减法就知道我们赚多少。

承运商门户是对称的另一半：它拿得到 `client_price`（我们报给客户的售价）。

---

## 根本原因

订单是三端共用同一套接口的（`CAN_VIEW_ORDER = ['order:view', 'portal:order_view',
'carrier_portal:task_view']`），而取数层是按运营端的需要写的：

```js
// ❌ server/modules/order/model.js
async getById(client, id) {
  const result = await client.query(
    `SELECT o.*,                                    // ← orders 表全部列，含 carrier_cost
            c.company_name as client_name, c.credit_level,
            cr.company_name as carrier_name, cr.performance_score as carrier_score,
            d.doc_number, d.status as doc_status
     FROM orders o ...`, [id])
}

async list(client, {...}) {
  let sql = `SELECT o.id, ..., o.client_price, o.carrier_cost, o.currency, ...`  // ← 明写了
}
```

**租户隔离做了，字段隔离没做。** `controller.js` 里的 `scopeToTenant` /
`canAccessOrder` 确保了「只能看自己家的单」，于是很容易以为安全问题已经解决了 ——
但「哪些单」和「单里的哪些字段」是两个正交的问题，只做前者等于把自家单的全部内部数据交出去。

**为什么长期没被发现**：只要前端不渲染，界面看起来就是对的。
这和踩坑 054（草稿报价只靠前端 `.filter()` 藏起来）是同一个根因的两种形态 ——
**藏在前端等于没藏**。

### 同一批接口里的第二个洞：时间线完全没有租户校验

```js
// ❌ server/modules/order/controller.js
async getTimeline(req, res) {
  const result = await query(
    `SELECT osl.from_status, ... FROM order_status_logs osl WHERE osl.order_id = $1`,
    [req.params.id])          // ← 只按 order_id 查，没问过这单是不是你的
  res.json({ code: 200, message: 'success', data: result.rows })
}
```

同一个 router 里的 `/:id/files` 老老实实调了 `loadOrderWithAccessCheck`，
`/:id` 走 controller 里的 `canAccessOrder`，**唯独 `/:id/timeline` 一个都没有**。
门户账号带着自己的合法 token、换一个订单 UUID，就能读到别家订单的状态变更史，
连带 `changed_by_name`（我们内部员工的姓名）。

这正是踩坑 067 那条规则的复现：**详情接口的租户隔离必须每个接口自己做一遍**，
「隔壁那个接口做过了」不算数。

---

## 解决方案

### 1. 加一层「门户可见字段」白名单

新建 `server/modules/order/portal-view.js`，按登录身份挑字段：

```js
// ✅ 白名单，不是黑名单
const CLIENT_FIELDS = ['id', 'order_number', 'customer_ref', ..., 'client_price', 'carrier_name']
const CARRIER_FIELDS = ['id', 'order_number', ..., 'carrier_cost']
const TIMELINE_FIELDS = ['from_status', 'to_status', 'created_at']   // 去掉操作人和内部备注

export function scrubOrder(user, row) {
  if (!row) return row
  const viewer = resolveViewer(user)              // 口径与 canAccessOrder 完全一致
  if (viewer === 'OPERATOR') return row
  return pick(row, viewer === 'CLIENT' ? CLIENT_FIELDS : CARRIER_FIELDS)
}
```

controller 的 `list` / `getById` / `getTimeline` 在 `res.json` 之前过一遍。

**为什么必须是白名单**：`orders` 表还留着 V1 时期的一批列
（`void_by` / `release_confirmed_by` / `cost_center` …），以后加列也只会更多。
黑名单漏一个字段 = 把内部数据发出去（看不见的失败）；
白名单漏一个字段 = 详情页少显示一项（看得见的失败）。**失效方向必须是后者。**

### 2. 时间线补上租户校验 + UUID 守卫

```js
// ✅
const owner = await query(`SELECT client_id, carrier_id FROM orders WHERE id = $1`, [req.params.id])
if (owner.rows.length === 0 || !canAccessOrder(req.user, owner.rows[0])) {
  return res.status(404).json({ code: 404, message: '订单不存在', data: null })   // 不是 403
}
```

顺带给 `orders /:id`、`inquiries` 的 `loadInquiryWithAccessCheck` 补了
`UUID_RE` 守卫 —— 非 UUID 扔给 pg 会抛类型转换错误，白白变成一个 500（踩坑 067）。

## 防护规则

- **「能看到哪些记录」和「记录里能看到哪些字段」是两件事，都要做。**
  做完 `scopeToTenant` / `canAccessOrder` 不等于安全审查通过。
  三端共用的接口，**默认假设取数层是按运营端写的**，一定要检查它 SELECT 了什么。
- **给门户开放一个已有接口之前，先把它的响应体逐字段读一遍。**
  这次是因为要做详情页（把响应渲染出来）才发现的 ——
  也就是说「前端没渲染」这层遮羞布，会在任何一次 UI 迭代中被掀掉。
- **`SELECT *` 不要出现在门户可达的取数路径上。** 要么显式列字段，要么在出口按白名单收窄。
- **新增门户可见字段时改 `portal-view.js` 的数组，不要去动 model 的 SELECT** ——
  动 model 会同时影响运营端和导出。
- **每个按 id 取数的接口都要自己做租户校验**（踩坑 067 已写过一次，这次在
  `getTimeline` 上又中了）。写完一个 `/:id/xxx` 路由，回头数一遍同一个 router 里
  所有的 `/:id*` 路由，看是不是每个都有校验。
- **不属于当前登录方一律回 404，不要回 403**：403 等于确认这个 UUID 是有效记录。
