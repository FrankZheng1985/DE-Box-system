# 067 详情页从列表前 100 条里 find 出记录，翻页之后就查不到

> 日期：2026-08-17
> 模块：财务（finance）／运营管理端财务详情页
> 性质：预防性修复 —— 生产数据量还没到，但入口刚被打通

---

## 问题现象

打开 `/finance/<id>` 财务记录详情页，页面显示「记录不存在」，
但这条记录在财务列表里明明看得见、点得开付款和作废。

**没有任何报错**：接口全是 200，控制台干净，pm2 的 error 日志一行没有。
数据越多坏得越厉害 —— 财务记录不到 100 条时完全正常，
超过 100 条以后，靠后的那些记录一个个变成「不存在」。

---

## 根本原因

详情页**根本没有详情接口**，它是拉两个列表回来，在前端 `find` 出目标记录的：

```tsx
// ❌ admin/src/pages/FinanceDetail.tsx（修复前）
const arRes = await api.get<any>('/finance/receivables?pageSize=100')
const apRes = await api.get<any>('/finance/payables?pageSize=100')
const allRecords = [...arRes.data, ...apRes.data]
const found = allRecords.find((r: any) => r.id === id)
if (found) setRecord(found)      // find 不到就一直是 null → 显示「记录不存在」
```

`pageSize=100` 是**分页的第一页**，不是「全部」。列表按 `due_date ASC` 排序，
所以第 101 条往后的记录压根不在返回结果里，`find` 必然落空。

**为什么是静默的**：两个列表接口都正常返回 200，
"查不到" 在前端表现为 `found === undefined`，走的是和「这条记录真被删了」
完全相同的那个分支。前端分不出「没查到」和「不存在」，就只能说不存在。

**为什么现在才需要管**：这条路以前走不到。
`/finance/:id` 只有财务列表页的「查看」按钮能进，一次只看当前页的记录，
而当前页就在那 100 条里，永远撞不上。
2026-08-16 的提交 bd2b013 修好了订单详情页的单据流卡片，
新增了「从单据流条目点进财务详情」的入口（用 `entity_id`），
从此可以从任意一张老订单直接跳到任意老财务记录 —— 隐患这才变成可触发的。

---

## 解决方案

给财务模块补一个真正的详情接口，前端改成调它。

```js
// ✅ server/modules/finance/routes.js
router.get('/records/:id',
  requirePermission('finance:view', 'portal:billing_view', 'carrier_portal:billing_view'),
  async (req, res) => {
    const { id } = req.params
    if (!UUID_RE.test(String(id))) {
      return res.status(404).json({ code: 404, message: '财务记录不存在', data: null })
    }
    const result = await query(
      `SELECT fr.*, COALESCE(cl.company_name, cr.company_name) AS counterparty_name, o.order_number
       FROM financial_records fr
       LEFT JOIN clients  cl ON cl.id = fr.counterparty_id AND fr.counterparty_type = 'CLIENT'
       LEFT JOIN carriers cr ON cr.id = fr.counterparty_id AND fr.counterparty_type = 'CARRIER'
       LEFT JOIN orders   o  ON o.id = fr.order_id
       WHERE fr.id = $1`, [id])
    const record = result.rows[0]
    if (!record || !canReadRecord(req.user, record)) {
      return res.status(404).json({ code: 404, message: '财务记录不存在', data: null })
    }
    res.json({ code: 200, message: 'success', data: record })
  })
```

```tsx
// ✅ admin/src/pages/FinanceDetail.tsx
const res = await api.get<ApiResponse<any>>(`/finance/records/${id}`)
if (res.data) setRecord(res.data)
```

配套的三件事，一件都不能省：

1. **返回字段与列表逐字对齐**（`fr.*` + `counterparty_name` + `order_number`）。
   详情页原本吃的就是列表行，字段名对不上就是踩坑 066 那种「接口好了页面还是空」。
   注意应收对手方在 `clients`、应付在 `carriers`，一条 SQL 要 join 两张表再 COALESCE。
2. **非 UUID 直接当不存在**。主键是 UUID，`/finance/records/abc` 这种字符串扔给 pg
   会抛 `invalid input syntax for type uuid`，白白变成一个 500。
3. **租户隔离要在详情里重做一遍**。列表是「先收窄查询条件再查」，
   详情没有条件可收窄，只能查出来再判 —— 少了这一步，
   详情接口就成了绕过列表隔离的后门（见下）。

## 防护规则

- **列表接口 + 前端 find ≠ 详情接口。** 只要页面是按 id 打开单条记录的，
  就给它一个按 id 查的后端接口。用 `pageSize=100`（或任何常数）当"全部"，
  是一颗跟着数据量增长而必然引爆的雷，而且引爆时不报错。
  排查「详情页说不存在但记录明明在」时，第一件事是看它的取数方式是不是 find。
- **新开一条跳转路径时，回头查一遍目标页面的取数假设。**
  这次的坑不是 bd2b013 引入的，是它把一条一直走不到的路打通了。
  「加了个链接」这种看起来零风险的改动，会让别处的旧假设第一次被真正检验。
- **详情接口的租户隔离必须独立实现，不能指望列表那份。**
  口径要和列表完全一致：客户只能看自己的应收、承运商只能看自己的应付。
  尤其**应付记录里是承运商成本价**，客户看到就等于看到我们的采购底价。
  不属于当前登录方的一律回 **404 不是 403** —— 403 等于告诉对方这个 UUID 是有效记录。
- **接受 UUID 路径参数的接口，先 `UUID_RE.test` 再进 SQL。**
  本项目 order / cmr / inquiry 三个模块已经各自有这个常量了，照抄即可。
- **新加 `/records/:id` 这类接口时留意路由顺序**：第一段固定的写法（`/records/:id`）
  本身是安全的，但将来若给同一个 router 加 `GET /:id`，必须排在它**后面**
  （固定路径在参数路径之前，本项目已踩 5 次）。
