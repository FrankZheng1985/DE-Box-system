# 踩坑记录 009：通知的 EMAIL 渠道是空壳，从来没发出过一封邮件

## 问题现象

系统里所有"邮件通知"功能看起来都正常（代码在调、日志不报错、通知列表里也有记录），
但客户和员工**从来没收到过任何一封系统邮件**。

## 根本原因

有三处独立的断点，任何一处都足以让邮件发不出去：

### 1. `_queueEmail()` 只入库，从不发送

`core/notification-engine.js` 里注释写着"实际发送通过 node-cron 定时任务轮询"，
但**这个定时任务从来没有被写出来**。方法名叫 queue，实际只是往 notifications 表插了一条
`type = 'EMAIL_xxx'`、`title = '[邮件] xxx'` 的记录就结束了。

顺带还有个副作用：`channel = 'BOTH'` 时会写两行通知（正常一行 + `[邮件]` 前缀一行），
用户在站内信列表里看到重复条目。

### 2. `cron-jobs.js` 调了一个不存在的方法

```javascript
// ❌ NotificationEngine 上根本没有 send() 这个方法，只有 notify()
await notificationEngine.send({ type, title, content, targetRole }).catch(() => {})
```

`.catch(() => {})` 把 `TypeError: notificationEngine.send is not a function` 静静吞掉了，
所以"资质到期提醒"和"逾期催款"两个定时任务跑了几个月，一条通知都没产生过，日志还显示"检查完成"。

而且两者的参数签名完全对不上：`notify()` 要的是 `(client, {userIds, type, title, message})`，
`send()` 传的是 `{type, title, content, targetRole}` —— 连数据库连接和目标用户都没有。

### 3. 生产 `.env` 没有 SMTP_* 变量

`env.example` 里从来没有 SMTP 配置样例，`email-service.js` 的 `isConfigured()` 检测不到
`SMTP_USER`/`SMTP_PASS`，直接 `return { skipped: true }` —— 就算前两个问题修了也发不出去。

## 解决方案

**渠道分层：core 负责入队，utils 负责发信。**

```javascript
// core/notification-engine.js —— 一条通知只写一行，标记是否要发邮件
await client.query(
  `INSERT INTO notifications
     (user_id, type, title, message, related_order_id, channel, email_to, email_status)
   VALUES ($1,$2,$3,$4,$5,$6,$7,$8)`,
  [userId, type, title, message, relatedOrderId, actualChannel,
   emailTo, emailTo ? 'PENDING' : null]
)
```

```javascript
// utils/email-queue.js —— 由 cron 每 2 分钟轮询，真正调 sendEmail
// utils/cron-jobs.js  —— 用 notify() 的正确签名，先按角色查出 userIds
const userIds = await notificationEngine.getUserIdsByRoles(client, ['finance', 'sys_admin'])
await notificationEngine.notify(client, { userIds, type: NOTIFICATION_TYPES.INVOICE_DUE, title, message })
```

迁移 104 给 notifications 表补了
`email_to / email_status / email_attempts / email_claimed_at / email_sent_at / email_error`。

## ⚠️ PM2 cluster 模式下必须防重复发信

生产是 `pm2 start ... -i 2`，**两个进程会同时跑同一个 cron**。
如果轮询写成"SELECT 出 PENDING 再逐条发"，同一封邮件会被两个进程各发一遍。

正确做法是先用 `FOR UPDATE SKIP LOCKED` 原子"领取"：

```sql
UPDATE notifications SET email_status = 'SENDING', email_claimed_at = NOW()
WHERE id IN (
  SELECT id FROM notifications
  WHERE email_status = 'PENDING' AND email_to IS NOT NULL
  ORDER BY created_at LIMIT 20
  FOR UPDATE SKIP LOCKED     -- ← 关键：另一个进程直接跳过被锁的行
)
RETURNING id, type, title, message, email_to, email_attempts
```

领取时间记在 `email_claimed_at`（**不能用 `created_at`** —— 那是通知创建时间，
一条早上创建、刚刚被领取的记录会被误判成"卡死"而放回队列，反而造成重复发送）。

## 防护规则

1. **写"队列"就必须同时写消费者。** 只入库不发送的 queue 方法等于没有功能，
   注释里说"由定时任务处理"时，必须确认那个定时任务真的存在。
2. **`.catch(() => {})` 是禁忌。** 吞掉所有异常会让 TypeError 这种低级错误潜伏几个月。
   至少要 `.catch(err => console.error(...))`。
3. **跨模块调用前先确认方法真实存在**，尤其是引擎类的 API —— 名字像不等于有。
4. **cluster 模式下的定时任务必须考虑多进程并发**，涉及"取任务去执行"一律用
   `FOR UPDATE SKIP LOCKED` 原子领取，不能先 SELECT 再 UPDATE。
5. 新增环境变量必须同步补进 `env.example`，并记得 `pm2 delete all` 重启（见踩坑 005）。
