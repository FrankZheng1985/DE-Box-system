# 013 业务类型与运输类型值域错配

## 问题现象

散布在四个地方、同一个模式的静默失效（全部在 P1 三分类改造时发现）：

1. **Excel 导出**：业务类型列一直显示原始英文（`CURTAIN_SIDE`），从没显示过中文。
2. **admin Dashboard**：最近订单的"类型"列同样一直显示原始英文。
3. **OrderDetail**：集装箱订单的"航运信息"区块从来没显示过。
4. **OrderManagement 集装箱 Tab**：状态子标签点了没反应——选"等待安排"后列表直接变空，而不是筛出等待安排的单。

共同点：**页面不报错、不崩溃，只是默默显示兜底值或空列表**，所以一直没被发现。

## 根本原因

`orders` 表上有三个"看起来都像类型/状态"的字段，值域完全不同，但代码里互相拿错：

| 字段 | 值域 | 含义 |
|------|------|------|
| `business_type` | `TRUCK_LTL` / `TRUCK_FTL` / `LOCAL_DELIVERY`（旧：CURTAIN_SIDE/CONTAINER） | 业务线 |
| `transport_type` | `FTL` / `LTL` / `FCL` / `LCL` | 整车/拼车方式 |
| `delivery_status` | `WAITING_ARRANGE` / `FLEET_CONFIRMED` / … | 集装箱派送子状态（≠ 主状态 `status`） |

## 错误代码

```js
// 案发点 1/2：拿 transport_type 的值域去匹配 business_type
const bizTypeMap = { FTL: '整车', LTL: '零担', CONTAINER: '集装箱', EXPRESS: '快递' }
bizTypeMap[row.business_type]   // business_type 是 CURTAIN_SIDE → 永远 undefined

// 案发点 3：大小写错（库里是大写）
const isContainer = order.business_type === 'container'   // 永远 false

// 案发点 4：把派送子状态传给主状态参数
params.append('status', 'WAITING_ARRANGE')   // 后端拿去筛 orders.status → 永远空
// 后端明明单独支持 deliveryStatus 参数，前端没用
```

## 正确代码

```ts
// 中文名只从唯一来源取（admin/src/constants/businessTypes.ts / server order/service.js）
import { BUSINESS_TYPE_LABELS, BUSINESS_TYPES } from '../constants/businessTypes'
BUSINESS_TYPE_LABELS[row.business_type]

const isContainer = order.business_type === BUSINESS_TYPES.TRUCK_FTL

// FTL 子状态筛选走 deliveryStatus 参数
if (businessType === BUSINESS_TYPES.TRUCK_FTL) {
  params.append('deliveryStatus', statusFilter)
} else {
  params.append('status', statusFilter)
}
```

## 防护规则

1. **枚举值和中文名不许在页面里手抄**。前端一律 import `constants/businessTypes.ts`（customer-portal 用自己那份），后端一律 import `order/service.js` 的导出。新页面 review 时看到手写 `{ XXX: '中文' }` 的业务类型/状态 map 就该警惕。
2. **`?? '-'` / `|| raw` 这类兜底是双刃剑**：它让错配不报错。写兜底时问一句"这个兜底如果天天被走到，我能发现吗"；拿不准就先 console.warn。
3. 筛选参数名要和后端字段对齐：主状态 `status`、集装箱派送子状态 `deliveryStatus`，别混。
4. 库里状态/类型值全部**大写**（踩坑 004 的老规矩），比较前别 toLowerCase 完再去配大写 map。
