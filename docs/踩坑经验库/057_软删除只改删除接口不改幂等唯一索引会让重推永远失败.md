# 057. 软删除只改删除接口、不改幂等唯一索引，会让重推永远失败

> 2026-08-07 · 询价单软删除（开发意见 #2）

## 问题现象

给 `inquiries` 加软删除（`deleted_at`）时，很自然地做了两件事：

1. 删除接口从 `DELETE FROM inquiries` 改成 `UPDATE ... SET deleted_at = NOW()`
2. 所有业务查询加上 `AND deleted_at IS NULL`

看起来很完整。但只要那张被删的单是**开放 API 推进来的**，合作方拿同一个
`externalOrderNo` 重推就会拿到 **500 服务器内部错误**，而且是永久性的
——那个单号从此再也导不进系统，除非人工去库里把那行硬删掉。

对客户来说这是最难受的一种坏法：**「我把导错的单删了，结果正确的那版再也导不进来。」**

## 根本原因

幂等键靠的是迁移 112 建的部分唯一索引：

```sql
CREATE UNIQUE INDEX uq_inquiries_external
  ON inquiries(external_source, external_ref)
  WHERE external_source IS NOT NULL AND external_ref IS NOT NULL;
```

软删除之后**那一行还在表里**，索引自然还认它。于是重推时：

1. 应用层「先查后插」的查重语句已经加了 `AND deleted_at IS NULL` → 查不到 → 判定为新单，往下走 INSERT
2. INSERT 撞上 `uq_inquiries_external` → 抛 `23505`
3. catch 分支里的补查语句**同样带着 `AND deleted_at IS NULL`** → 还是查不到
4. 补查为空 → `throw err` → 500

三处逻辑各自都"正确"，合起来是死循环。**软删除把「行还在不在」和「行算不算数」拆成了
两个概念，而数据库约束只认前一个。**

## 错误代码

```js
// 查重加了过滤（对的）
const dup = await client.query(
  `SELECT id FROM inquiries
   WHERE external_source = $1 AND external_ref = $2 AND deleted_at IS NULL`, ...)
```
```sql
-- 但索引没跟着改（错的）——已删的行仍然占着幂等键
CREATE UNIQUE INDEX uq_inquiries_external
  ON inquiries(external_source, external_ref)
  WHERE external_source IS NOT NULL AND external_ref IS NOT NULL;
```

## 正确代码

索引的谓词必须和应用层的过滤条件**说同一句话**：

```sql
-- 注意：IF NOT EXISTS 不会修改已存在索引的定义，必须 DROP 后重建
DROP INDEX IF EXISTS uq_inquiries_external;
CREATE UNIQUE INDEX uq_inquiries_external
  ON inquiries(external_source, external_ref)
  WHERE external_source IS NOT NULL AND external_ref IS NOT NULL AND deleted_at IS NULL;
```

同一原则也适用于"客户单号重复"这类应用层查重：

```js
// 已删除的单不算重复，否则客户删掉错单后同一个客户单号再也导不进来
`SELECT DISTINCT customer_ref FROM inquiries
 WHERE client_id = $1 AND customer_ref = ANY($2::text[]) AND deleted_at IS NULL`
```

## 防护规则

给任何一张表加软删除时，**除了改查询，还要把这三类东西一并盘一遍**：

| 类型 | 怎么查 | 不改的后果 |
|------|--------|-----------|
| 唯一索引 / 唯一约束 | `\d <表名>` 看 UNIQUE 行 | 删掉的值永久占位，重新录入报 23505 → 500 |
| 应用层查重 | 搜 `SELECT ... WHERE <业务键>` | 提示"已存在"但用户界面上根本看不到那条 |
| 外键指过来的下游表 | `\d <表名>` 看被引用关系 | 下游挂着查不到上游的孤儿记录 |

第三类本次的处理方式是**在删除守卫里堵住**，而不是在下游查询里过滤：
只要"还没有报价、也没发过服务商询价"才允许删，`quotations` / `carrier_inquiries`
的外键就永远指不到一张被删的单，下游一行代码都不用改。
**能用前置条件消灭的问题，不要靠在 N 个下游查询里加过滤来兜——那 N 个地方以后一定会漏。**

还有一条容易忘的：`CREATE UNIQUE INDEX IF NOT EXISTS` 对**已存在**的同名索引
是彻底的空操作，不会按新谓词重建。改谓词一律 `DROP INDEX IF EXISTS` + `CREATE`。
