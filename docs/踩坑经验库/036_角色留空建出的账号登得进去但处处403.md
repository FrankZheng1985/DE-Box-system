# 036 · 角色留空建出的账号，登得进去但处处 403

> 发现日期：2026-08-03（核查生产账号时发现）
>
> **订正（2026-08-06）**：本文原写"该账号尚未被使用，属于提前拦下"，不成立。
> pm2 错误日志里有实打实的记录，对方真的登录过并被挡在外面：
>
> ```
> [权限拒绝] username: duguirong | roleCode: null | 需要: dashboard:view 或 portal:order_view
>            | path: GET /api/v1/dashboard/client
> ```
>
> `last_login_at` 当时显示为 null 具有误导性——它只在**登录成功**时更新，
> 而这类账号是"登录成功、后续接口全挂"，所以那个字段反映不出用户碰过壁。
> 排查这类问题别只看 `last_login_at`，要去翻 `[权限拒绝]` 日志。
>
> 补角色后已验证：`client_admin` 含 `portal:order_view`，
> `duguirong` 与 `suling` 调仪表板和订单接口均返回 200。
> 涉及数据：生产库 `users.role_id IS NULL` 的账号

## 问题现象

用管理端「客户详情 → 账号 tab → 添加账号」给客户翼能建了门户账号 `duguirong`：

- 账号在列表里，状态启用 ✅
- 用户类型 `CLIENT`、`linked_entity_id` 正确绑到翼能 ✅
- 密码也是对的，**能登录成功** ✅
- 但登进去之后**每一个接口都返回 403**

表现是"账号看起来完全正常，就是什么都点不动"，很容易被当成"权限配置没生效"
或者"前端 bug"去查，实际问题在建账号那一刻就埋下了。

## 根本原因

`users.role_id` 是 `NULL`。

登录本身不校验角色，所以能登进去。但权限是这么解析的：

```js
// server/core/permission-service.js
export async function getPermissionsByRoleCode(roleCode) {
  if (!roleCode) return new Set()   // ← 角色为空，直接返回空集合，不报错
  ...
}
```

而门户的每个接口都挂着 `requirePermission(...)`：

```js
// server/modules/order/routes.js
router.get('/', requirePermission(...CAN_VIEW_ORDER), orderController.list)
```

于是：**登录成功 → 权限集为空 → 所有 requirePermission 一律不通过 → 全线 403**。

## 为什么会建出这种账号

前后端**两层都没把角色当必填**：

```js
// 前端 admin/src/components/EntityAccountsPanel.tsx
if (!form.username.trim() || !form.password.trim() || !form.display_name.trim()) {
  setError(t('accounts.errorRequired'))   // ← 校验里没有 role_id
  return
}
// 提交时还主动兜成 null
role_id: form.role_id || null
```

```js
// 后端 server/modules/user/routes.js
if (!username || !password || !display_name) { ... }   // ← 同样没有 role_id
// 插入时也兜成 null
user_type, role_id || null, linked_entity_id || null
```

角色下拉框不选就是空字符串，一路兜成 `null` 存进去，全程无任何提示。

## 和踩坑 035 的区别（两个坑长得很像，别搞混）

| | 035 悬空绑定 | 036 角色为空 |
|---|---|---|
| 坏在哪 | `linked_entity_id` 指向已删除的公司 | `role_id` 是 NULL |
| 能登录 | 能 | 能 |
| 接口返回 | **200 + 空数组** | **403** |
| 像什么 | 像"这家公司确实没业务" | 像"权限没配对" |

一个静默返回空，一个明着报没权限——**都不会告诉你真正的原因在账号本身**。

## 解决方案

三层一起补：

1. **后端必填校验**（关键防线，任何调用方都绕不过）：
   ```js
   if (!role_id) {
     return res.status(400).json({ code: 400, message: '参数错误：必须为账号指定角色' })
   }
   ```
2. **后端角色类型匹配校验**：`roles.role_type` 必须等于 `users.user_type`，
   否则会建出「CLIENT 账号挂运营角色」这种越权账号。前端虽然已经按
   `entityType` 筛过下拉框，但后端不能依赖前端筛过——直接调接口就绕过去了。
3. **前端必填校验 + 三语文案**：把 `!form.role_id` 加进提交前校验，
   `accounts.errorRequired` 文案补上"角色"。

## 防护规则

1. **建账号时角色必填，没有例外**。一个没有角色的账号不是"权限小"，
   而是"完全不能用"，且失败方式很隐蔽。
2. **前端筛过的东西，后端必须再校验一遍**。前端下拉框按类型筛只是体验，
   直接 POST `/api/v1/users` 就绕过了。
3. **新建账号后，别只看列表里有没有这一行**，要确认三样东西齐了：
   角色、用户类型、（门户账号还要）绑定实体。一条 SQL 全查出来：
   ```sql
   SELECT u.username, u.user_type, r.role_code, u.linked_entity_id,
          (SELECT company_name FROM clients  WHERE id = u.linked_entity_id) AS client_name,
          (SELECT company_name FROM carriers WHERE id = u.linked_entity_id) AS carrier_name
   FROM users u LEFT JOIN roles r ON r.id = u.role_id
   WHERE u.is_active;
   ```
   `role_code` 为空、或门户账号两个 name 都为空的，都是坏账号。
4. **`getPermissionsByRoleCode` 对空角色返回空集合是对的**（不该抛异常），
   但正因为它不报错，坏账号才能一路建出来——所以拦截必须放在建账号那一层。
