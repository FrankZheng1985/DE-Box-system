# 029 测试密码写进仓库文档，就等于生产超管密码公开

> 日期：2026-08-02　模块：认证 / 账号安全

## 问题现象

项目 `.claude/CLAUDE.md` 有一节「测试账号」，大方写着：

| 门户 | 账号 | 密码 |
|------|------|------|
| 运营管理端 | admin | admin123 |
| 客户门户 | siemens | client123 |
| 承运商门户 | speedtrans | carrier123 |

2026-08-02 在生产环境实测，`admin` / `admin123` **直接登录成功**。
这个 admin 是 `sys_admin` 角色，拥有全部 74 项权限。

也就是说：任何拿到这个仓库读权限的人（同事、外包、被泄露的备份、
将来某天设成 public 的一瞬间），等于直接拿到了生产环境的超级管理员。

同样的明文还散落在 `README.md`、`deploy/阿里云购买指南.md`、
`server/scripts/init-db.js`、`create-test-users.js`、`test-api-full.js`、
`101_eu_tms_v2_seed_data.sql` 的注释里——一共 6 处，删一处没用。

## 根本原因

三个心理误区叠在一起：

1. **「这是测试账号」** —— 但它从来没有只存在于测试环境。生产库是拿同一份
   seed SQL 初始化的，`101_eu_tms_v2_seed_data.sql` 里写死了 admin123 的
   bcrypt 哈希，所以**生产 admin 从诞生那天起就是 admin123**，没人再改过。
2. **「哈希是不可逆的，写进 SQL 没关系」** —— 哈希不可逆不代表安全。注释里
   直接写着原文 `密码: admin123`；就算不写，`$2a$10$N9qo8uLOickgx2ZMRZoMye...`
   这个哈希是 bcrypt 教程里的公开值，搜一下就知道对应 admin123。
3. **「仓库是私有的」** —— 私有是当下的状态，不是永久属性。凭据的生命周期
   比仓库的可见性设置长得多。

## 解决方案

1. 六处明文全部清除，`.claude/CLAUDE.md` 的「测试账号」章节改成「账号凭据」，
   只写"密码存放处 = Frank 的密码管理器"，不写密码本身。
2. 种子密码改为环境变量注入，脚本里不再硬编码：
   - `init-db.js` 读 `SEED_ADMIN_PASSWORD`，没设就大声警告"admin 仍是公开默认密码"
   - `create-test-users.js` 读 `SEED_CLIENT_PASSWORD` / `SEED_CARRIER_PASSWORD`，
     没设就临时随机生成一个，结尾打印一次
   - `test-api-full.js` 读 `TEST_ADMIN_PASSWORD`，没设直接拒跑
3. 新增两个交互式脚本，密码从终端隐藏输入，不走命令行参数也不走环境变量
   （避免落进 shell history）：
   - `server/scripts/reset-user-password.js`
   - `server/scripts/create-client-portal-user.js`
   两者都强制 ≥12 位且至少三类字符，从源头挡住下一个 admin123。

## 顺带挖出来的更大的问题

排查时发现 `admin` 账号的 email 是 `suling@yineng56.com` —— 客户「翼能」
(C-00002) 联系人的公司邮箱。这个账号 `sys_admin` + 74 项权限 +
`linked_entity_id = NULL`（不绑任何租户）。

**密码弱只是表象，把全权限账号交给外部客户才是真问题**：对方能看到系统里
所有客户的订单、财务、报价、清关数据，第 8 条"门户必须后端强制租户隔离"
的架构规则被从上层绕过去了——因为他根本不是从门户进来的。

正确做法是给客户开 `user_type=CLIENT` + `client_admin` 角色 +
`linked_entity_id` 绑到自己公司的门户账号，而不是共享运营超管。

## 防护规则

1. **仓库里任何位置都不写密码原文**——文档、注释、脚本、提交信息、开发记录都算。
   加字段前先问："这行如果出现在公网上，我睡得着吗？"
2. **不要在 seed / migration 里写死可登录的密码哈希**。种子账号的密码必须由
   环境变量注入，或初始化后强制改。已经写死的，要在注释里明确标注
   "这是公开占位值，必须覆盖"。
3. **外部客户一律走门户账号**，永远不要把 OPERATOR 类型账号（尤其 sys_admin）
   给客户或承运商用。判断信号：`users` 表里 `user_type='OPERATOR'` 的账号，
   email 域名却是客户/承运商的公司域名。
4. **定期查一次**：`SELECT username, email, user_type FROM users WHERE is_active`，
   看有没有账号的邮箱域名和身份对不上。
5. 系统目前**没有登录日志表**，`last_login_at` 是单字段、会被覆盖。一次自动化
   测试脚本登录就能把真人的历史痕迹冲掉，事后根本查不出"谁在什么时候用过这个
   账号"。要追责或做安全审计，得先补一张登录日志表。
