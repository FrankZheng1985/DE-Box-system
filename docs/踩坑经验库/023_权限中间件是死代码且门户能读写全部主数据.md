# 023 权限中间件是死代码，门户账号能读写全部主数据

## 问题现象

P5 权限体系开发前的摸底发现，系统"看起来有权限控制"，实际三层全是空的：

1. **8 个角色毫无差别**：`roles` 表 seed 了 sys_admin / op_manager / op_staff / finance 等 8 个角色，
   但任何一个运营账号登录后，能做的事完全一样——财务专用的过账、作废、利润分析，运营专员照样能点。
2. **客户和承运商账号能读写全部客户/承运商主数据**：拿客户门户的 token 直接请求
   `GET /api/v1/clients`，返回**全部客户**的公司名、VAT、信用额度、账期、应收余额；
   `PUT /api/v1/clients/:id` 还能改。承运商账号同理能看到所有同行的资质和结算信息。
3. **前端菜单和路由零守卫**：Sidebar 14 个菜单对所有人全量展示，地址栏直接敲
   `/settings/chart-of-accounts` 页面照样渲染。
4. **给员工分配角色一直没生效**：用户管理页选了角色保存成功，但库里 `role_id` 始终是 NULL。

## 根本原因

**（1）`requirePermission` / `requireAdmin` 读的是 JWT 里不存在的字段。**

中间件判 `req.user.role === 'admin'` 和 `req.user.permissions`，
但登录接口签发的 token payload 里只有 `id / username / userType / roleCode / roleName /
companyCode / linkedEntityId` —— **没有 `role`，也没有 `permissions`**。
于是 `userPermissions` 恒为 `[]`，`hasPermission` 恒为 false。
这个中间件在全仓库**一次都没被 import 过**，所以没人发现它是坏的。

**（2）真正生效的只有 `requireUserType`，而 client/carrier 模块压根没挂它。**

两个模块只写了 `router.use(authenticateToken)` —— 只验"登录了没"，不验"你是谁"。

**（3）V2 那套 SAP 风格授权对象是空架子。**

`auth_objects` seed 了 15 条，`auth_values`（真正的授权分配）是**空表**，
且没有任何中间件消费它。前端 `AuthContext.hasAuth()` 查的就是这个空数组，恒返回 false；
它的兜底判断写的是 `roleCode === 'admin'`，而实际角色码是 `sys_admin`，
所以连超管兜底也没生效。

**（4）UUID 被 `Number()` 转成了 NaN。**

`roles.id`、`clients.id`、`carriers.id` 都是 UUID，
前端提交时写 `Number(form.role_id)` → `NaN` → `JSON.stringify(NaN)` 得到 `null` → 落库为空。
接口返回 200"保存成功"，页面也不报错，所以两个月没人察觉。

```js
export function requirePermission(...permissions) {
  return (req, res, next) => {
    if (req.user.role === 'admin') return next()        // payload 里没有 role
    const userPermissions = req.user.permissions || []  // payload 里没有 permissions，恒为 []
    ...
  }
}
```

```js

const router = Router()
router.use(authenticateToken)
router.get('/', async (req, res) => { /* 返回全部客户 */ })
```

```tsx
// ❌ UUID 不能 Number()
role_id: form.role_id ? Number(form.role_id) : null,   // Number('9f8c-…') === NaN → null
```

## 正确代码

```js
// ✅ 权限码按角色查库 + 内存缓存，中间件真正落地
export function requirePermission(...permissions) {
  return async (req, res, next) => {
    if (!req.user) return res.status(401).json({ code: 401, message: '请先登录', data: null })
    const allowed = await roleHasAnyPermission(req.user.roleCode, permissions)
    if (!allowed) return res.status(403).json({ code: 403, message: '没有权限执行此操作', data: null })
    next()
  }
}
```

```js
// ✅ 主数据模块整体挡成运营专用，再逐接口挂权限码
router.use(authenticateToken)
router.use(requireUserType('OPERATOR'))
router.get('/', requirePermission('client:view'), handler)
router.get('/export', requirePermission('client:export'), handler)
```

```tsx
// ✅ UUID 原样传，不做数字转换
role_id: form.role_id || null,
linked_entity_id: form.linked_entity_id || null,
```

## 防护规则

1. **权限中间件写完必须立刻挂到至少一条路由上，并用不同角色实测一次 403/200。**
   只定义不使用的中间件 = 没人会发现它是坏的。本次新增 `server/scripts/test-permissions.js`，
   用不同角色的 token 打真实接口断言状态码，就是为了让这类问题在开发阶段就暴露。
2. **凡是"前端传参决定能看到哪些数据"的接口，都要按登录身份在后端强制收窄。**
   本次除了 client/carrier，还发现订单列表、清关列表、GPS 全部接口、应收应付列表
   都是直接用 `req.query.clientId` 筛选——客户门户账号换个参数就能看别家数据。
   规则：门户可访问的列表接口，`clientId`/`carrierId` **一律取 JWT 的 `linkedEntityId`，
   忽略 query 传参**（和踩坑 016 同源）。
3. **任何 ID 字段，动手前先确认库里是 UUID 还是 INTEGER。**
   本项目 V2 表主键全是 UUID，前端一律按 string 处理，禁止 `Number()`。
   `Number(uuid)` 得 NaN，JSON 序列化后变 null，**不会报错**，是典型的静默失败。
4. **前端权限判断的兜底角色码要用常量。**
   本次把 `sys_admin` 收进 `admin/src/constants/permissions.ts` 的 `SUPER_ROLE_CODE`，
   前后端各一份但值一致；散落的字符串字面量正是当初写成 `'admin'` 却没人发现的原因。
5. **提交前跑 `cd server && node scripts/check-permission-menu-sync.js`**，
   校验代码里用到的权限码在迁移字典里都有定义、Sidebar 每个菜单都配了权限映射。
