# 037 · 编辑弹窗回填读错字段，点开保存一次就把真实状态改掉了

> 发现日期：2026-08-03（P9 给 admin 清关管理做三语时）
> 涉及文件：`admin/src/pages/CustomsManagement.tsx`

## 问题现象

清关管理列表里点「更新状态」，弹窗打开时：

- 「清关状态」下拉**永远停在「待清关」**，哪怕这条记录已经是「已放行」
- 「报关行」输入框**永远是空的**，哪怕库里存着报关行名字

运营看到状态不对，很自然会以为"哦，那我选成正确的再保存"——
但如果他没注意、直接点了保存（比如只想改报关行），
**这条记录的状态就被悄悄改回 PENDING 了**。

## 根本原因

弹窗回填读的两个字段后端根本不返回：

```tsx
// ❌ 打开弹窗时回填
const openStatusModal = (item: CustomsItem) => {
  setStatusForm({
    status: item.clearance_status?.toUpperCase() || 'PENDING',  // 没有 clearance_status
    customsBroker: item.broker_name || '',                      // 没有 broker_name
    exceptionReason: '',
  })
}
```

`customs_clearances` 表里是 `status` 和 `customs_broker`，
接口 `SELECT cc.*` 返回的也是这两个名字。
`item.clearance_status` 是 `undefined`，于是：

- `undefined?.toUpperCase()` → `undefined` → `|| 'PENDING'` **兜底成了待清关**
- `undefined || ''` → **报关行变空串**

## 为什么这个比"整列空白"危险得多

踩坑 033 那类字段错配是**读**错，最坏结果是界面空白，看得见。
这条是**回填**错，后面紧跟着一个保存动作：

> 读错 → 兜底成默认值 → 用户点保存 → **默认值被写回数据库**

也就是说，一个纯展示层的字段名笔误，最终变成了**数据被改写**。
而且改写是"合法"的：接口正常、状态流转合法、日志显示是运营本人操作的。
事后追查会以为是人操作失误。

同一页的列表列也读了 `item.clearance_status`（状态徽章空白），
所以现象上是「列表里状态是空的，弹窗里状态是待清关」——
两处不一致本身就是信号，只是没人留意。

## 正确做法

1. **回填一律用后端真实返回的字段名**：

```tsx
setStatusForm({
  status: item.status?.toUpperCase() || 'PENDING',
  customsBroker: item.customs_broker || '',
  exceptionReason: '',
})
```

2. **回填的兜底值要慎选**。`|| 'PENDING'` 这种"取不到就给个默认状态"的写法，
   在字段名写错时会把错误伪装成正常值。宁可让它是空、让保存按钮禁用，
   也不要静默兜成一个**合法但错误**的业务状态。

## 防护规则

1. **打开编辑弹窗后，先核对回填值和列表行显示的是否一致**。
   不一致就说明至少有一处字段名错了。
2. **凡是"读出来 → 回填 → 保存回去"的闭环，字段名必须核对两遍**：
   读的时候一遍，写的时候一遍。这类闭环比纯展示危险一个量级。
3. **状态类字段的兜底值优先用空**，让校验拦住提交，而不是兜成默认状态。
4. 沿用踩坑 033 的纪律：**写页面前先把接口 SQL 拉出来看实际列名**。
   ```bash
   grep -n "SELECT" -A 15 server/modules/<模块>/routes.js
   ```
