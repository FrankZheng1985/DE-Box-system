# 064 pm2 日志从不轮转，四个月前的报错看起来像"长期存在"

## 问题现象

生产 pm2 error 日志里有一条报错，看上去是运营端「用户管理」页面列表接口一直在 500：

```
获取用户列表失败: error: column r.name does not exist
```

`roles` 表确实没有 `name` 列（只有 `role_code` / `role_name` / `role_type`），
报错本身完全成立，读起来像是个没人管的长期故障。

**但它其实是 2026-04-13 就修掉的 bug，日志里那行是四个月前留下的唯一一次记录。**
按"线上还在坏"去查，会白查一轮，还可能"修"出一个本来就对的地方。

## 根本原因

**这台服务器的 pm2 日志从 2026-04-12 起就没清过，也没配轮转。**

```
-rw-r--r-- 1 root root  87228 Aug 16 05:55 germany-box-server-error-0.log   # 1176 行
-rw-r--r-- 1 root root 100725 Aug 16 05:55 germany-box-server-error-1.log
```

一个文件横跨四个月。而 **pm2 默认不给日志加时间戳**，
每条报错只有文案和调用栈，看不出是什么时候发生的。
于是 `grep` 命中 = "这个错存在过"，但完全不等于 "这个错还在发生"。

这条 `r.name` 在 error-0.log 里位于**第 151 行 / 共 1176 行**，
也就是文件最开头那一段——4 月中旬的事。

同一份日志里另外两条也是同样情况，都早已修复：

| 日志里的报错 | 真实状态 |
|---|---|
| `[定时任务] 逾期催款检查失败: column fr.client_id does not exist` | 已修，现行代码用 `fr.counterparty_id` LEFT JOIN clients，连日志文案都改成了「账单提醒失败」 |
| `[定时任务] 过账期间管理失败: invalid input syntax for type uuid: "系统自动"` | 已修，`opened_by`/`closed_by` 改写 NULL，代码里还留了注释说明 |

三条的共同特征：**日志里的文案/行号，和现在代码里的对不上。**

## 怎么判断一条 pm2 报错是不是还活着

按下面四步走，四步都指向"活的"才动手修：

**1. 看调用栈行号对不对得上现在的代码**

这次的栈是：

```
at async file:///var/www/germany-box-system/server/modules/user/routes.js:88:24
```

而生产上那个文件现在第 88 行附近根本不是这条查询：

```bash
ssh eu-tms "grep -n 'r.role_name\|r\.name' /var/www/germany-box-system/server/modules/user/routes.js"
# 101:              r.role_name, r.role_code
# 136:              r.role_name, r.role_code
```

行号漂移 + 列名已是对的 → 这条栈来自旧版本代码。
（对照旧版：`git show 8c85af9^:server/modules/user/routes.js` 第 92 行正是
`r.name AS role_name, r.code AS role_code`，查询起始行就是 88。）

**2. 看报错在日志文件的什么位置**

```bash
ssh eu-tms "wc -l ~/.pm2/logs/germany-box-server-error-0.log
            grep -n '<报错关键字>' ~/.pm2/logs/germany-box-server-error-0.log"
```

日志是**追加写**的，行号越靠前 = 越久远。靠近 `tail` 的才值得紧张。

**3. 数出现次数**

```bash
grep -E '^[^ ].*(失败|error:)' ~/.pm2/logs/germany-box-server-error-0.log \
  | sed 's/[0-9a-f]\{8\}-[0-9a-f-]*/<uuid>/g' | sort | uniq -c | sort -rn
```

四个月只出现 **1 次**的，几乎不可能是"页面接口一直 500"——
真坏着的话，每次有人打开那个页面就是一条。

**4. 直接拿现行代码的 SQL 去生产库跑一遍（只读）**

这一步是决定性的，别省：

```bash
ssh eu-tms "cd /var/www/germany-box-system/server && export \$(grep '^DATABASE_URL' .env | xargs) \
  && psql \"\$DATABASE_URL\" -c \"SELECT u.id, u.username, r.role_name, r.role_code
       FROM users u LEFT JOIN roles r ON u.role_id = r.id LIMIT 5;\""
```

跑通了就是真的没坏。

## 防护规则

- **在 pm2 日志里 grep 到报错，先证明它还活着，再去修。** 四步：栈行号对不对得上
  现行文件、在日志里的位置靠不靠后、出现次数、把现行 SQL 拿到生产库实跑一遍。
- **不要因为"报错内容成立"就认定故障存在。** `roles` 确实没有 `name` 列——
  这条报错任何时候读都是"合理"的，唯独不能说明它现在还在发生。
- **判断某个报错是否已修，看代码不看日志**：`git log -S '<报错里的字段名>' -- server/`
  能直接翻出是哪个提交、什么时候修的。这次是 `8c85af9`（2026-04-13）。
- 与踩坑 063 是一体两面：063 说的是「500 只在 error 日志里，别只看 `/api/health`」，
  064 补上另一半——**「error 日志里有，也不等于现在还有」**。两条都要记。

## 根治办法（2026-08-16 已全部执行）

**日志现状（排查生产必看）：**

| 项 | 现状 |
|---|---|
| 路径 | `/var/log/pm2/germany-box-{out,error}.log`，两实例合并写一份 |
| 时间戳 | 每行带（`2026-08-16T06:16:21:`），由 ecosystem 的 `time: true` 提供 |
| 轮转 | pm2-logrotate 3.0.0：满 10M 或每天 0:00 切、压缩、留 30 份 |
| 旧路径 | `~/.pm2/logs/germany-box-server-*-{0,1}.log` **已停止更新**，内容已归档到 `/var/backups/pm2-logs/` |

⚠️ **去旧路径 tail 会看到一个静止在 2026-08-16 06:09 的文件** —— 那正是本篇说的陷阱，
只不过这次是治理动作自己造出来的。查日志一律用新路径。

**顺带修掉的一个雷**：`deploy/ecosystem.config.cjs` 自 2026-04-12 起就没被真正加载过。
CI 的重启逻辑是

```
if pm2 describe germany-box-server; then pm2 reload ...   # 进程一直在 → 永远走这条
else pm2 start deploy/ecosystem.config.cjs ...            # 从没执行过
```

所以配置里的 `log_date_format` / `error_file` / `merge_logs` 全是死设置（这也是"配了日期格式
却没时间戳"的原因）。让它首次生效前，先把 `wait_ready` 从 `true` 改成 `false` ——
`server/app.js` 并没有调用 `process.send('ready')`，开着会让每个实例白等
`listen_timeout` 10 秒。以后要开它，得先在 app.js 里补 ready 信号。

**因此：重启生产一律用 ecosystem，不要用裸命令。**

```bash
ssh eu-tms "cd /var/www/germany-box-system && pm2 delete germany-box-server \
  && pm2 start deploy/ecosystem.config.cjs --env production && pm2 save"
```

裸 `pm2 start server/app.js --name germany-box-server -i 2` 起来的进程不带上述任何日志设置，
会把一切静默打回治理前，且不会有任何报错提示。
