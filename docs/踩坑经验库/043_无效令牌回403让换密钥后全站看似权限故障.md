# 043 · 无效令牌回 403，换密钥后全站看似"权限故障"

> 发现日期：2026-08-06（生产切换 JWT_SECRET 当天，Frank 在管理端全站 403）

## 问题现象

生产换掉 JWT 密钥（踩坑 041 的整改：去掉硬编码兜底、.env 配真实 `JWT_SECRET`）
并重启后端之后，之前登录过的用户页面上**每个接口都报 403**，前端统一显示
「没有权限访问此资源」：

```
GET /api/v1/notifications/unread-count 403 (Forbidden)
GET /api/v1/inquiries/stats 403 (Forbidden)
获取询价统计失败: ApiError: 没有权限访问此资源
```

三重误导叠加，让它看起来像权限配置坏了，而不是登录态坏了：

1. 前端把**所有** HTTP 403 统一翻译成「没有权限访问此资源」（`apiError.forbidden`）；
2. 报 403 的接口里有 `/notifications/unread-count` 这种**根本没挂权限中间件**的；
3. 服务端**零日志**——`[权限拒绝]` 日志一条都没有，因为根本没走到权限层。

用户侧则是"登录着，但什么都点不动"，且不会被自动登出，卡死在坏令牌上。

## 根本原因

`authenticateToken` 对"令牌校验失败（非过期）"回的是 **403**：

```js
// ❌ server/middleware/auth.js（旧）
} catch (error) {
  if (error.name === 'TokenExpiredError') {
    return res.status(401).json({ errCode: 401, msg: '认证令牌已过期，请重新登录', data: null })
  }
  return res.status(403).json({ errCode: 403, msg: '无效的认证令牌', data: null })  // ← 问题在这
}
```

而三端前端只对 **401** 做自愈（清本地登录态 → 回登录页）：

```ts
// admin/customer-portal/carrier-portal 三份 api.ts 一致
if (response.status === 401) {
  localStorage.removeItem(AUTH_STORAGE_KEY)   // ← 只有 401 走这条自愈路径
  throw new ApiError(i18n.t('apiError.sessionExpired'), 401, 'UNAUTHORIZED')
}
if (response.status === 403) {
  throw new ApiError(i18n.t('apiError.forbidden'), 403, 'FORBIDDEN')  // ← 403 只报"没权限"
}
```

换密钥后，旧令牌 `jwt.verify` 抛的是 `JsonWebTokenError: invalid signature`
（不是 `TokenExpiredError`），于是走 403 分支 → 前端不清登录态 → 用户永远
拿着坏令牌重试，全站 403。

语义上这本来就该是 401：**401 = 你是谁我不认（重新登录能解决），
403 = 我认识你但你不能做这件事（重新登录也没用）**。签名校验失败属于前者。

## 解决方案

```js
// ✅ server/middleware/auth.js（新）
} catch (error) {
  if (error.name === 'TokenExpiredError') { /* 原样，401 */ }
  // 无效令牌必须回 401 而不是 403：三端前端只对 401 清登录态回登录页，
  // 403 会被显示成"没有权限"，用户卡在坏令牌上出不来（JWT 换密钥后全站如此）
  console.warn('[认证拒绝] 令牌校验失败:', error.message, '| path:', req.method, req.originalUrl)
  return res.status(401).json({ errCode: 401, msg: '无效的认证令牌', data: null })
}
```

msg 文案不变，P9 的 messageCode 中间件按文案映射（`INVALID_TOKEN`），不受状态码影响。
前端三端零改动——401 的自愈路径本来就在。

## 防护规则

1. **认证层的失败一律 401，权限层的失败才是 403。** 判断标准就一句话：
   "重新登录能不能解决？"能 → 401，不能 → 403。
2. **拒绝类分支必须留日志。** 这次 403 分支一行日志都没有，排查时
   `[权限拒绝]` 全 grep 不到，反而成了定位线索（说明没走到权限层）——
   但这是靠反推，不该指望。凡 return 4xx 的分支至少 `console.warn` 一条。
3. **换 JWT 密钥是全员登出事件**，上线时要预期"所有旧会话立即失效"，
   提前告知或选低峰期操作；遇到"换密钥后有人全站报错"，第一反应是让对方
   重新登录，而不是查权限表。
4. **排查全站 403 时，先找一个"没挂权限中间件的接口"看它 403 不 403**
   （本项目用 `/api/v1/notifications/unread-count`）：它也 403 → 问题在认证层；
   它正常 → 才去查权限。

## 涉及文件

| 文件 | 操作 |
|------|------|
| `server/middleware/auth.js` | 无效令牌 403 → 401，补 `[认证拒绝]` 日志 |
