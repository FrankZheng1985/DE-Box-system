# 041 · 认证密钥的兜底默认值，等于给系统留了个后门

> 发现日期：2026-08-06（换完 JWT_SECRET 后顺手核对配置读取链时发现）
> 涉及文件：`server/config/index.js`

## 问题现象

没有任何现象——这正是它可怕的地方。

`server/config/index.js` 里写着：

```js
export const serverConfig = {
  jwtSecret: process.env.JWT_SECRET || 'germany-box-transport-secret-key-2024',
}
```

只要 `JWT_SECRET` 这个环境变量没配上（`.env` 丢了、部署到新机器忘了配、
某次改配置手滑删了一行），服务**照常启动、日志一切正常、功能全都能用**，
只是它签发和校验 token 用的是上面那个写死在仓库里的字符串。

## 为什么这比密码写进仓库还严重

踩坑 029 记的是"测试密码写进仓库 = 生产超管密码公开"，但那至少还要走登录流程。
认证密钥泄露是另一个量级：

```js
// 任何拿到仓库读权限的人，都可以这样凭空造一个超管身份
jwt.sign(
  { id: '...', username: 'whoever', userType: 'OPERATOR', roleCode: 'sys_admin' },
  'germany-box-transport-secret-key-2024'
)
```

**不需要用户名，不需要密码，不需要账号存在**。`authenticateToken` 只做
`jwt.verify` 签名校验、完全不查数据库（这点本身是另一个坑，见下），
签名对了就直接 `req.user = decoded` 放行。

而且它是**静默降级**：没有报错、没有告警、监控上看不出任何异常，
可能已经这样跑了几个月都没人知道。

## 根本原因

`||` 兜底这种写法在配置里太顺手了，`port || 3002`、`env || 'development'`
都很合理，于是 `jwtSecret || '...'` 就跟着一起写了。

但端口和环境名配错了顶多服务起不来或行为不对，**认证密钥配错了是安全边界塌掉**。
这两类配置不能用同一种写法。

判断标准很简单：**这个配置项缺失时，是"退化成一个不太好的默认行为"，
还是"退化成一个所有人都知道的密钥"？** 后者必须 fail fast。

同类思路见 CLAUDE.md 第 8 条「过滤条件的失效方向必须是拒绝」——
一样的道理，只是那条讲租户隔离，这条讲认证密钥。也可对照踩坑 038
（声称存在的防护其实从没生效过）：都是"看起来有防护，实际是空的"。

## 解决方案

去掉兜底，缺失就拒绝启动：

```js
if (!process.env.JWT_SECRET) {
  console.error('致命错误: 未配置 JWT_SECRET，拒绝启动')
  console.error('请在 server/.env 中设置 JWT_SECRET（建议 openssl rand -hex 32 生成）')
  process.exit(1)
}

export const serverConfig = {
  jwtSecret: process.env.JWT_SECRET,   // 不再有 || 兜底
}
```

已验证：缺 `JWT_SECRET` 时退出码 1 并打印明确指引；配了则正常读取环境变量值。

## 防护规则

1. **安全相关的配置项一律不给兜底默认值**：JWT 密钥、加密密钥、API Key、
   数据库密码、签名盐。缺失就 `process.exit(1)`，让它响亮地失败。
2. **可以给兜底的**：端口、环境名、超时时间、分页大小、日志级别——
   这些配错了不会破坏安全边界。
3. **新增配置项时先问一句**：这个值如果泄露，攻击者能做什么？
   答案是"能伪造身份"或"能解密数据"的，就不许写 `||`。
4. **CORS 也是同一类**：`origin: process.env.CORS_ORIGIN || '*'` 目前还留着。
   生产 `.env` 里配了具体域名所以暂时没暴露，但失效方向同样是错的
   （配置一丢就变成允许任意来源）。**本次未改**，因为改严会影响本地开发，
   需要按环境区分对待，留待后续处理。
5. **换完密钥要顺手核对读取链**：本次就是换 `JWT_SECRET` 之后，
   去确认「签发」和「校验」是否读同一个来源时，才发现校验侧读的是
   带兜底的 `serverConfig.jwtSecret`。换密钥是个很好的核对时机。

## 附带发现（未修，待评估）

`authenticateToken` 只验签名、不查数据库，导致：

- 停用账号 → 旧 token 仍有效
- 改密码 → 旧 token 仍有效
- 改角色/降权 → 旧 token 仍是旧权限

在 token 有效期（7 天）内，上述操作**都不会立即生效**。目前唯一能立刻作废
所有已签发 token 的手段是更换 `JWT_SECRET`（代价是所有人重新登录一次）。
如果将来账号数量变多，应该考虑加 `users.token_version` 字段，
签发时写进 payload、校验时比对，这样就能精确作废单个账号的 token。
