# 028 登录接口三端共用，但管理端前端不校验用户类型

## 问题现象

在管理端登录页 `/login` 输入**客户账号**（user_type = CLIENT）的用户名密码，
能够**成功登录并进入运营管理端界面**——侧边栏、订单管理、财务管理这些页面都渲染出来了。

虽然进去之后每个接口都返回 403、页面是空的，但"门户账号能进管理端的门"这件事本身
就不该发生，属于纵深防御缺口。

同时发现 `GET /api/v1/system/roles` 完全没有守卫：任何登录用户
（包括客户和承运商）都能列出全部 8 个内部角色，
连 `sys_admin` / `finance` / `op_manager` 这些运营角色的代码和名称都能拿到。

## 根本原因

**（1）三端共用同一个登录接口，接口不区分调用方来自哪个端。**

`POST /api/v1/auth/login` 只验用户名密码，验完就签发 token，
payload 里带 `userType`，但**接口本身不关心请求来自管理端还是门户**。
这个设计本身没错（少维护两套登录逻辑），但它把"这个账号该不该进这个端"
的判断责任完全推给了前端。

**（2）管理端前端接住 token 就认，从来没看过 `userType`。**

`AuthContext.login()` 只判 `data.code === 200` 就写 localStorage、置登录态；
`ProtectedRoute` 只判 `isAuthenticated`。两处都没有校验 `userType === 'OPERATOR'`。

**（3）后端逐路由挂守卫时漏了一条。**

P5 权限体系给 system 模块每条路由都挂了 `requireUserType('OPERATOR')` + `requirePermission()`，
唯独 `/roles` 这条漏了——因为它"只是个下拉选项列表"，看起来无关紧要。
但角色列表泄露的是内部权限结构，等于把地图递给外人。

## 错误代码

```tsx
// ❌ 登录成功就认，不看这个账号属于哪个端
if (data.code === 200 && data.data) {
  const { token, user } = data.data
  localStorage.setItem(AUTH_STORAGE_KEY, JSON.stringify({ token, user }))
  setState({ user, isAuthenticated: true, ... })
  return { success: true, message: '登录成功' }
}
```

```tsx
// ❌ 保护路由只问"登录了没"，不问"你是谁"
function ProtectedRoute({ children }) {
  const { isAuthenticated, isLoading } = useAuth()
  if (isLoading) return <FullScreenLoading />
  return isAuthenticated ? <>{children}</> : <Navigate to="/login" replace />
}
```

```js
// ❌ "只是个下拉列表"，于是一个守卫都没挂
router.get('/roles', async (req, res) => {
  const result = await query(`SELECT id, role_code, role_name, role_type FROM roles WHERE is_active = true`)
  res.json({ code: 200, message: 'success', data: result.rows })
})
```

## 正确代码

```tsx
// ✅ 登录时就按 userType 拒绝，并告诉用户该去哪个门户
if (user?.userType !== 'OPERATOR') {
  return { success: false, message: PORTAL_LOGIN_HINT[user?.userType] || '该账号无权访问运营管理端' }
}
```

```tsx
// ✅ 保护路由再挡一次，兜住 localStorage 里的历史登录态
function ProtectedRoute({ children }) {
  const { isAuthenticated, isLoading, userType, logout } = useAuth()

  useEffect(() => {
    if (!isLoading && isAuthenticated && userType !== 'OPERATOR') logout()
  }, [isLoading, isAuthenticated, userType, logout])

  if (isLoading) return <FullScreenLoading />
  if (!isAuthenticated) return <Navigate to="/login" replace />
  return userType === 'OPERATOR' ? <>{children}</> : <FullScreenLoading />
}
```

```js
// ✅ 补守卫；两个消费方权限不同，放行任一即可
router.get('/roles', requireUserType('OPERATOR'), requirePermission('system:role', 'system:user'), handler)
```

## 防护规则

1. **共用登录接口时，"该不该进这个端"必须在每个端的前端入口各挡一次，
   而且要挡两处：登录成功那一刻，和每次进受保护路由时。**
   只挡登录不挡路由，localStorage 里的历史登录态会绕过去
   （客户先前在管理端登过一次，后来才加的守卫，他刷新页面照样在里面）。
2. **给接口挂守卫时，"看起来只是个下拉列表"的接口最容易被漏。**
   判断标准不是"这个接口返回的数据重不重要"，而是
   **"这个接口的返回值，给一个完全的外人看会不会让他更懂我的系统"**。
   角色列表、权限码字典、枚举选项、模板列表都属于这一类。
3. **给共享接口补权限守卫前，先 grep 出全部消费方，确认它们的权限码。**
   `/system/roles` 有两个消费方：角色权限页（`system:role`）和用户管理页（`system:user`）。
   只挂 `system:role` 会把"只有用户管理权、没有角色管理权"的人挡死——
   而这种角色配置在角色权限页上是可以配出来的。
   `requirePermission(a, b)` 是**任一满足**的语义，正好用于这种场景。
4. **排查权限问题前先 `git fetch` 并确认本地工作区没落后于 origin/main。**
   本次排查一开始读的是落后 21 个提交的本地代码，
   得出了"client/carrier 模块没有任何端类型守卫"的错误结论——
   而这个问题早在 P5（踩坑 023）就修好了。
   **读代码下结论前，先确认读的是不是线上那份。**
