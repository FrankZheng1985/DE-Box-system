# 065 安全组放行 ≠ 端口可达：这台机器还有一层 ufw

## 问题现象

排查生产网络暴露面时，查阿里云安全组 `sg-j6ch3x980uowk2rpf1zq`，看到四个端口对全网开放：

```
TCP  25/25          源: 0.0.0.0/0   Accept
TCP  7000/7000      源: 0.0.0.0/0   Accept
TCP  10143/10143    源: 0.0.0.0/0   Accept
TCP  10993/10993    源: 0.0.0.0/0   Accept
```

读起来像四个敞着的洞。**但从公网实际探测，这四个端口一个也连不上。**

反过来的误判更危险：因为这个安全组是**两台 ECS 共用**的，而阿里云普通安全组
**同组实例默认内网互通**，据此会推出「先锋系统那台能直连 EU-TMS 的任意端口、
包括绕过 nginx 直接打 3002」——这个结论同样是错的。

## 根本原因

**这台服务器上还有第二层防火墙：ufw，而且是 active 的。**

```
Status: active
Default: deny (incoming), allow (outgoing), disabled (routed)

To          Action      From
22          ALLOW IN    Anywhere
80          ALLOW IN    Anywhere
443         ALLOW IN    Anywhere
```

`iptables -L -n` 里 `Chain INPUT (policy DROP)`。ufw 对**所有来源一视同仁**，
不区分公网还是同 VPC，所以：

- 那 4 个端口安全组放行了，包到主机被 ufw 丢掉 → 实际打不进来
- 先锋那台（`172.16.0.9`）能碰到 EU-TMS 的也只有 22/80/443，和公网上任意一台机器完全一样

**两层的关系是"与"不是"或"**：任何一层拒绝，连接就不通。
只看其中一层，两个方向的误判都会发生——
看安全组会**高估**暴露面，看 ufw 会**低估**云平台层的配置漂移。

## 探测手法：`nc` 要看耗时，不能只看通不通

```bash
# ❌ 坏的：两种完全不同的情况都归为"不通"
nc -z 47.83.241.117 25 && echo 通 || echo 不通

# ✅ 好的：量耗时
```

| 现象 | 含义 |
|---|---|
| 约 0.1 秒失败 | 防火墙**放行**，只是没有进程监听 → 收到 RST（连接被拒绝） |
| 约 5 秒超时 | 被防火墙**丢包**（DROP），根本没到应用层 |

本次实测：

```
25      不通             耗时 5.07s      ← 被 ufw 丢包
7000    不通             耗时 5.07s
10143   不通             耗时 5.09s
10993   不通             耗时 5.09s
22      通（有进程监听） 耗时 0.15s
443     通（有进程监听） 耗时 0.11s
```

如果只写 `nc -z` 判断通断，这四个端口和"安全组已经关掉"的状态在输出上**完全一样**，
改完之后根本验证不出改动有没有生效。

## 防护规则

- **判断某个端口到底暴不暴露，安全组和主机防火墙两层都必须查**，
  只查一层的结论一律不可信：
  ```bash
  # 云平台层
  aliyun ecs DescribeSecurityGroupAttribute --RegionId cn-hongkong \
    --SecurityGroupId <sg-id> --Direction ingress
  # 主机层（ufw 之外还要看全部 iptables 链，第三方软件插的链不出现在 ufw status 里）
  ssh eu-tms "ufw status verbose; iptables -L -n"
  # 实际监听
  ssh eu-tms "ss -tlnp"
  ```
- **三者对不上是常态，要分清"配置上开着"和"实际能打进来"**。
  本次三层的说法各不相同：安全组说 8 个端口开着，ufw 说只有 3 个，
  `ss` 说实际监听 4 个（80/443/22/3002）。
- **做网络加固前先量一次基线，改完再量一次**，且要量耗时。
  否则像本次这种"改动落在被 ufw 遮住的那一层"，外部观测**改前改后一模一样**，
  你无法自证改动生效——只能靠 API 查规则和实例归属来确认。
- 同族记忆：全局 CLAUDE.md 里 Tailscale 那条讲的是同一件事的另一个版本——
  **第三方软件插的 iptables 链不出现在 `ufw status` 里**，所以查主机层要看全部链，
  不能只看 `ufw status`。

## 本次结论（2026-08-16）

发现 ufw 已经挡住了这些端口，所以拆分安全组的性质从**补漏洞**降级为**纵深防御**
（云平台层与主机层策略保持一致，将来谁重装系统忘了配 ufw 时有兜底）。
