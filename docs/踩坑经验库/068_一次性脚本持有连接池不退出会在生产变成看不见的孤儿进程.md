# 068 一次性脚本持有连接池不退出，会在生产变成看不见的孤儿进程

## 问题现象

2026-08-17 做上线验证时顺手 `ps` 了一下生产，发现一个进程从 **8 月 3 日跑到当天，14.9 天**：

```
root  1068836  PPID=1  node scripts/reset-user-password.js suling
内存 53MB ｜ CPU 时间 utime 16 + stime 3（约 0.19 秒）｜ 握着 1 条 RDS 连接
```

它的特征是「哪儿都看不到」：

- **不在 `pm2 list` 里** —— 不是 pm2 起的，pm2 管不着
- **PPID=1** —— 启动它的 SSH 会话早断了，进程被 systemd 收养
- **没有任何面板会提示** —— 不像后台任务会显示 Running
- CPU 时间近乎为零，也不会因为吃 CPU 被发现

密码重置那件事 8 月 3 日当天就做完了，脚本该打印的都打印了。之后 15 天它纯粹在
占 53MB 内存和一条 RDS 空闲连接。

## 根本原因

`server/scripts/` 下的一次性脚本普遍 `import` 了业务模块，而业务模块顶层会
`import` `core/db.js` —— 那里创建了 **pg 连接池**。

连接池会在事件循环里挂着定时器和 socket，**Node 的事件循环永远不会清空**，
于是主流程跑完、结果打印完，进程还是不退出。

在本地跑没人在意（Ctrl-C 就完了）。在生产上通过 SSH 跑就不一样：
**关掉 SSH 不会杀死它，只会让它失去父进程从而隐身。**

## 正确做法

**任何在生产跑的一次性脚本，主流程结束后显式退出：**

```js
// ❌ 坏的：脚本逻辑跑完就"结束"了，进程其实还活着
await resetPassword(username)
console.warn('密码已重置')

// ✅ 正确：显式关池 + 退出
await resetPassword(username)
console.warn('密码已重置')
await pool.end()          // 有直接持有池的话
process.exit(0)           // 兜底，不管有多少层 import 拉起了连接
```

**只想读个常量/配置就别 import 业务模块** —— 直接 `grep` 源码，读常量根本不需要连数据库。

## 防护规则

1. **在生产跑完脚本，当场 `ps -ef | grep <脚本名>` 确认它退出了。**
   看到命令打印完结果就以为结束了，是这个坑的全部来源。
2. **`npx tsx -e` / heredoc 这类随手敲的一行流风险最高** ——
   它连文件都不留，事后只能从 `/proc/<pid>/cmdline` 还原当时敲了什么。
3. **定期巡检**（发现这个进程用的就是这条）：
   ```bash
   ssh eu-tms "ps -ef | grep '[n]ode' | grep -v 'PM2\|germany-box\|pm2-logrotate'"
   ```
   输出应该是空。`pm2-logrotate` 是正常常驻，别误杀。
4. **kill 前先取证**，别看见长时间运行就杀：
   ```bash
   PID=xxx
   awk '{print $14, $15}' /proc/$PID/stat     # utime stime，接近 0 = 空转
   tr '\0' ' ' < /proc/$PID/cmdline           # 当时到底跑的什么
   ss -tnp | grep "pid=$PID"                  # 是否握着数据库连接
   pm2 list                                   # 确认不是在用的服务
   ```
   本次四项都取了才动手：空转、任务早已完成、握着一条 RDS 连接、不在 pm2 列表。
5. 隔一段时间取两次 CPU 时间对比 —— 两次完全一样才敢断定是空转，
   只看一次分不清「空转」和「跑得慢」。
