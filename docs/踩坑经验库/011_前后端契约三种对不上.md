# 踩坑记录 011：前后端契约对不上的三种形态（形状 / 取值 / 类型）

踩坑 003 讲的是"字段名不一致"，本次在 P0 又碰到三种**不同形态**的契约错位，
共同点是：**HTTP 200，页面不报错，但功能实际是坏的**——比字段名对不上更难发现。

---

## 形态一：请求体形状对不上（发数组，后端要单条）

### 现象
设置页点"保存通知设置"，toast 提示保存成功，刷新后设置全部丢失。

### 原因
```javascript
// 前端 Settings.tsx 发的是数组
api.put('/notifications/preferences', { preferences: [{eventType, channelEmail, channelSystem}, ...] })

// 后端 notification/routes.js 解构的是单条
const { eventType, channelEmail, channelSystem } = req.body   // 全部 undefined
await query(`INSERT INTO notification_preferences ... VALUES ($1,$2,$3,$4)`,
            [req.user.id, undefined, undefined, undefined])
```
`eventType` 是 `undefined` 但列有 NOT NULL 约束 → 数据库报错 → 500。
前端只判断了 `res.code === 200` 却没有 else 分支，异常路径静默走过，用户看到的还是"已保存"。

### 修法
后端同时兼容两种形状；前端补 else 分支把后端 message 显示出来。
```javascript
const list = Array.isArray(body.preferences) ? body.preferences : [body]
```

## 形态二：枚举取值对不上（前端小写自造，后端大写常量）

### 现象
就算偏好存进去了，也**永远不生效**——通知该发邮件的时候还是只发站内信。

### 原因
前端硬编码了 5 个自己起的小写 key：
```javascript
{ key: 'order_status' }, { key: 'cmr_upload' }, { key: 'payment_reminder' },
{ key: 'alert_warning' }, { key: 'qualification_expiry' }
```
后端 `NOTIFICATION_TYPES` 是 11 个大写常量：
```javascript
ORDER_CONFIRMED, CARRIER_ACCEPTED, PICKED_UP, STATUS_UPDATE, DELIVERED,
CMR_UPLOADED, EXCEPTION, CLEARANCE_RELEASED, RELEASE_STATUS_CHANGED,
QUALIFICATION_EXPIRING, INVOICE_DUE
```
两边**没有一个对得上**（连 `cmr_upload` 和 `CMR_UPLOADED` 都不是大小写差异，是拼写不同）。
发通知时 `_resolveChannel()` 拿 `event_type = 'CMR_UPLOADED'` 去查偏好表，
表里存的是 `'cmr_upload'`，查不到 → 走默认值 SYSTEM。

这是踩坑 004（状态枚举大小写）的同一类问题，只是换到了通知事件上。

### 修法
1. 后端把中文名也定义成常量 `NOTIFICATION_TYPE_LABELS`，和 `NOTIFICATION_TYPES` 放一起；
2. 前端 key 一律照抄后端常量（全大写）；
3. 后端 PUT 接口**校验 eventType 必须在 NOTIFICATION_TYPES 里**，不在就返回 400 ——
   让下次再写错的时候当场报错，而不是静默存进一堆匹配不到的垃圾数据；
4. 另开 `GET /notifications/event-types` 供前端取清单，避免两边各抄一份。

## 形态三：数据类型对不上（存字符串，列是 INTEGER）

### 现象
编辑客户，改任何字段点保存都报错。

### 原因
```tsx
// ClientEdit.tsx 付款条件下拉存的是字符串
<option value="net_30">Net 30</option>
```
但 `clients.payment_terms` 是 `INTEGER DEFAULT 30`（账期天数），
后端把 `'net_30'` 原样塞进 SQL → `invalid input syntax for type integer: "net_30"`。

### 修法
下拉 value 改成数字天数（`0` 预付 / `7` / `14` / `30` / `60` / `90`），
并在后端加 `parsePaymentTerms()` 守卫，非法值返回 400 而不是让 PostgreSQL 报错。

⚠️ 顺带的坑：读取时不能用 `d.payment_terms || ''` 兜底 ——
**预付客户的账期是 `0`，会被 `||` 当假值吞掉**，要用 `??`。

## 形态四（同类）：嵌套对象被拍平

`customer-portal/CreateOrder.tsx` 传 `pickupCountry` / `deliveryCountry` 两个平铺字段，
后端 `order/model.js` 执行的是 `JSON.stringify(data.pickupAddress)` 写进 JSONB 列。
`data.pickupAddress` 是 `undefined` → `JSON.stringify(undefined)` 返回 **`undefined` 而不是字符串** →
pg 当 NULL 处理 → **客户自助下单的地址整个落空，且不报任何错**。

修法：前端按后端契约构造嵌套对象，结构和 admin 端 `OrderCreate.tsx` 保持一致：
```javascript
pickupAddress: { country, city, zipCode, address }
```

## 防护规则

1. **接口两端必须有一个"单一事实来源"**：枚举清单定义在后端，前端通过接口拉取或照抄常量，
   **绝不允许前端自己起一套 key**。
2. **后端要校验并拒绝非法值**（返回 400），不要指望前端传对。静默接受错误数据比报错更糟。
3. **前端 `if (res.code === 200)` 必须配 else 分支**把后端 message 显示出来，
   否则失败会被伪装成成功。
4. **改接口任何一端，都要打开另一端的代码对照一遍**：形状、取值、类型、嵌套结构四项都要看。
5. 兜底值用 `??` 不用 `||`，避免 `0` / `''` / `false` 这些合法值被吞掉。
