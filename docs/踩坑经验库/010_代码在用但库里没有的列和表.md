# 踩坑记录 010：代码在读写，但数据库里根本没有这一列 / 这张表

## 问题现象

三个功能在**代码层面完全正确**、review 也看不出问题，但一到线上就 500：

| 功能 | 表现 |
|------|------|
| 报价 / 客户 / 承运商「作废」 | 点确定后报"作废失败"，日志 `column "void_reason" of relation "quotations" does not exist` |
| 官网留言表单 | 提交报"提交失败，请稍后重试"，日志 `relation "contact_inquiries" does not exist` |

## 根本原因

**写代码的时候顺手加了字段/表，但没有配套写迁移脚本。**

- `void_reason`：`004_data_security_delete.sql` 只给 `orders` / `invoices` / `tms_shipments` 加过这一列，
  后来 quotation / client / carrier 三个模块也做了作废功能，SQL 里照抄了 `void_reason = $1`，
  但**没人回头给这三张表加列**。
- `contact_inquiries`：`modules/contact/routes.js` 有完整的增删改查 + 统计四个接口，
  但翻遍 001 到 103 全部迁移文件，**这张表从来没被建过**。

这类问题的隐蔽之处在于：**本地开发时如果手工 `ALTER TABLE` 过一次，本地就一直是好的**，
只有生产（或新同事的干净库）才会炸。

## 解决方案

迁移 `104_p0_foundation_fix.sql` 补齐：

```sql
ALTER TABLE quotations ADD COLUMN IF NOT EXISTS void_reason TEXT;
ALTER TABLE clients    ADD COLUMN IF NOT EXISTS void_reason TEXT;
ALTER TABLE carriers   ADD COLUMN IF NOT EXISTS void_reason TEXT;

CREATE TABLE IF NOT EXISTS contact_inquiries (
  id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  name VARCHAR(100) NOT NULL,
  ...
  replied_by UUID REFERENCES users(id),
  created_at TIMESTAMP DEFAULT NOW()
);
```

建表字段必须**逐个对照消费它的代码**来定，不能凭感觉写。
本次是照着 `contact/routes.js` 的四个接口（INSERT 的列、SELECT 的筛选条件、
UPDATE 的 `notes`/`replied_at`/`replied_by`、统计的 `status` 取值）反推出来的。

## 怎么提前发现这类问题

在一个**全新的空库**上按顺序跑完所有迁移，然后启动服务把主要功能点一遍。
本次就是用这个办法验证的：

```bash
createdb eutms_p0_migration_test
for f in 100_*.sql 101_*.sql 102_*.sql 103_*.sql 104_*.sql; do
  psql -d eutms_p0_migration_test -v ON_ERROR_STOP=1 -f "$f"
done
# 再跑一遍 104，确认 IF NOT EXISTS 幂等
dropdb eutms_p0_migration_test
```

只在自己那个被手工改过的本地库上测，是发现不了的。

## 防护规则

1. **写下 `ALTER TABLE` 之外的任何新字段引用前，先去 `migrations/` 搜一遍这个列是否真的存在。**
   `grep -rn "字段名" server/database/migrations/`，搜不到就说明要补迁移。
2. **加字段和写迁移必须同一个提交完成**，不允许"先把功能做完，迁移回头补"。
3. 迁移一律用 `IF NOT EXISTS` / `ADD COLUMN IF NOT EXISTS`，保证可重复执行。
4. **本地库不可信**（可能被手工改过）。验证迁移要用全新空库从头跑。
5. 建表时字段清单要对着消费方代码列，建完回头再核对一遍每个接口用到的列都在。
