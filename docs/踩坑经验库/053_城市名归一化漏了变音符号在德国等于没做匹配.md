# 052 · 城市名归一化漏了变音符号，在德国等于没做匹配

> 发现日期：2026-08-07（在生产上真点了一遍派单页才看出来）
> 涉及文件：`server/modules/carrier/routes.js` 的 `/match`

## 问题现象

派单页承运商卡片上明明显示「覆盖路线 **LUNEN → MADRID**」，
而当前这单正是 **Lünen → Madrid**，可绿色的「跑过这条线」标记**就是不出现**。

界面不报错、接口 200、数据也都在——就是标记不亮。

## 根本原因

匹配时做了大小写和首尾空格归一，**唯独没抹变音符号**：

```sql
LOWER(TRIM(o.pickup_address->>'city')) = LOWER(TRIM($1))
```

```
lower('Lünen') = 'lünen'
lower('LUNEN') = 'lunen'
                    ↑ ü ≠ u，永远不相等
```

运营录单时有人打 `Lünen`、有人打 `LUNEN`、有人打 `Lunen`，
在德国业务里 **München / Köln / Düsseldorf / Nürnberg 全是这个毛病**，
这个匹配基本等于废的。

## 为什么自测没发现

**我测的时候用的是 `lunen`——和库里存的一模一样。**

这是最要命的一点：拿"和数据库里长得一样"的值去测字符串匹配，
**测的是"相等的东西相等"，什么也没验证**。真实数据的多样性（大小写、
变音符号、空格、全半角）才是这类功能的考点。

后来是**在生产上真点开派单页**，看见「覆盖路线」显示着却标记不亮，
才发现的。数据层测试全绿，UI 一眼看穿。

## 解决方案

归一化加一步抹变音符号。**不用 `unaccent` 扩展**——生产 RDS 没装，
装扩展要库级权限；`translate()` 是内置函数，今天就能上：

```js
function normCity(expr) {
  return `TRANSLATE(LOWER(TRIM(REPLACE(${expr}, 'ß', 'ss'))), ` +
    `'áàâãäåéèêëíìîïóòôõöøúùûüñçý', ` +
    `'aaaaaaeeeeiiiioooooouuuuncy')`
}
```

两个细节：

1. **`ß` 必须先单独 `replace`**：`translate()` 是 1:1 字符映射，做不了 `ß→ss` 这种一对二。
2. **源串和目标串长度必须一一对应**（本例各 27 个字符）。不一致时
   `translate()` **不报错**，多出来的字符会被直接删掉——又是一个静默错误。
   写完先数一遍：
   ```js
   [...src].length === [...dst].length
   ```

实测：`Lünen`/`LUNEN` → 同为 `lunen`；`München→munchen`、`Köln→koln`、`Straße→strasse`。

## 顺带查出的第二个问题：取消的单被算作"跑过这条线"

`route_hits` 和 `covered_routes` 都只过滤了 `carrier_id IS NOT NULL`，
**没排除已取消/已拒绝的订单**。于是一张建完就取消的测试单，
让 SGF 显示成"跑过 Lünen → Madrid"——**虚报承运商的线路经验**，
会误导运营派单。已加 `status NOT IN ('CANCELLED','REJECTED')`。

## 防护规则

1. **字符串匹配的测试数据，绝不能和数据库里存的长得一样**。
   要用真实世界会出现的变体去测：大小写、变音符号、多余空格、全半角。
2. **凡是人手录入的地名/公司名参与比较，先归一化**：
   trim → lower → 抹变音符号。德语/法语/西语业务尤其躲不掉。
3. **`translate()` 两个串长度必须相等**，不等会静默吞字符，写完数一遍。
4. **"统计某方做过什么"的查询，先想清楚哪些状态不算数**
   （取消、拒绝、作废）。默认全算会虚报。
5. **数据层验证过不代表功能对**。本次 SQL 单测全绿，
   是在真实页面上看见"显示着路线却不亮标记"才发现的——
   凡是最终要给人看的功能，**至少在真实数据上看一眼渲染结果**。
