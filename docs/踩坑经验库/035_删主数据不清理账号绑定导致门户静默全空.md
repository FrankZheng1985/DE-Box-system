# 035 · 删主数据不清理账号绑定，门户会「静默全空」而不是报错

> 发现日期：2026-08-03（P9 做完客户门户，Frank 想登进去验收时查出）
> 涉及数据：生产库 `users.linked_entity_id` 指向已被删除的 `clients` / `carriers` 记录

## 问题现象

客户门户和承运商门户的账号都还在、都是启用状态、密码也对，**登得进去**，
但登进去之后**每一个页面都是空的**：订单 0 条、报价 0 条、账单 0 条、CMR 0 条。

接口全部返回 `200` + 空数组，**控制台没有任何报错**，看起来就像"这家公司确实还没有业务"。

## 根本原因

`users.linked_entity_id` 指向的公司记录**已经不存在了**：

```
users.username = 'siemens'    linked_entity_id = 1953e9c8-…  → clients 表里查无此 id
users.username = 'speedtrans' linked_entity_id = 85061206-…  → carriers 表里查无此 id

clients  实际只有：22b9827c-…（安百，27 单）、4653c364-…（翼能，2 单）
carriers 实际只有：776718fc-…（Eurosped）、b380819d-…（SGF）
```

**旧的演示公司记录被删了，但指向它们的用户账号被留了下来。**

> **归因订正（2026-08-03）**：本文最初把来源写成 2026-08-02 的
> 「账号凭据清理与测试账号删除」，经核查**不成立**，具体是哪次操作删掉了这两家
> 演示公司**目前仍未查明**，只能确定发生在 2026-08-02 11:17 之前。证据：
>
> - 那次操作对数据库的唯一写入是
>   `DELETE FROM users WHERE username ~ '^(tu|sec)_[0-9]+$' AND is_active = false`，
>   删掉的 8 行全是 `tu_*` / `sec_*` 测试账号。`siemens` / `speedtrans` 是
>   `is_active = true`，根本不匹配这个条件，没被碰过。
> - `DELETE FROM users` 在物理上不可能删除 `clients` / `carriers` 的行。
> - 该次操作**执行前**生成的备份 `/root/db-backups/users-20260802-111727.sql` 里，
>   `siemens` 的 `linked_entity_id` 已经是悬空的 `1953e9c8-…`；
>   且同一时刻查 `clients` 表总数就已经是 2（安百 + 翼能），`1953e9c8` 不在其中。
> - 备份里 `siemens` 这行的 `updated_at` 停在 `2026-04-18`，此后未被修改过。
>
> 也就是说**悬空绑定在那次清理之前就已经存在**。真正的来源是更早某次删演示主数据
> 时没清理账号绑定——本文的现象、机理、排查方法和防护规则全部成立，只有这句
> 来源归错了。查历史问题时别顺着这条线去翻 8-02 的账号清理，会白费工夫。

门户所有列表接口都按 `WHERE client_id = <linkedEntityId>` 做租户隔离（P5 的设计），
绑定指向一个不存在的 UUID 时，这个条件**永远匹配不到任何行**——
于是查询成功、返回空、无报错。

## 为什么 P5 的 requireTenantBinding 没挡住

`requireTenantBinding` 挡的是 **`linkedEntityId` 为空**的情况（防止"过滤条件不加 = 返回全部"）。
它**不校验这个 ID 是否真实存在**。

所以两种坏法的表现完全不同：
- 绑定为空 → 被中间件挡下，返回明确错误 ✅
- **绑定指向已删除的 ID → 一路放行，静默返回空** ❌

后者更危险：客户会以为"系统里没有我的单子"，运营也查不出毛病。

## 排查方法

一条 SQL 就能查出所有悬空绑定：

```sql
SELECT u.username, u.user_type, u.linked_entity_id,
       (SELECT company_name FROM clients  WHERE id = u.linked_entity_id) AS client_name,
       (SELECT company_name FROM carriers WHERE id = u.linked_entity_id) AS carrier_name
FROM users u
WHERE u.user_type IN ('CLIENT','CARRIER');
```

两列都是 `null` 的行就是悬空的。

## 防护规则

1. **删除 `clients` / `carriers` 前，必须先查有没有账号绑着它**：
   ```sql
   SELECT username FROM users WHERE linked_entity_id = '<要删的公司id>';
   ```
   有的话先把账号一起停用/改绑，再删公司。
2. **删除主数据优先用「作废」而不是物理删除**——`clients`/`carriers` 都有 `status` 字段，
   置为 `INACTIVE` 既保住引用完整性，也保住历史订单的关联。
   （ERP 业务规则本来就要求财务相关主数据不可物理删除。）
3. **`users.linked_entity_id` 没有外键约束**，所以数据库层面拦不住。
   要么补外键，要么在删除流程里显式检查——本次选了后者（补外键要处理存量脏数据，风险更高）。
4. **门户"全空"要先怀疑绑定，再怀疑业务**。顺序是：
   查账号绑定 → 查该公司有没有数据 → 才是查代码。
   本次如果没查绑定，很容易误判成"P9 的 i18n 改动把页面搞坏了"。
