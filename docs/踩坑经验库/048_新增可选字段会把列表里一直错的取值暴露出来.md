# 048 新增可选字段会把列表里一直错的取值暴露出来

## 问题现象

给集装箱订单（TRUCK_FTL）加了「提柜地点」这个**选填**字段之后，
订单列表里新建的集装箱单路线显示成：

```
Hamburg → -
```

看着像「目的地丢了」。第一反应是去查新加的字段有没有写坏 `delivery_address` ——
查了，没有，`delivery_address` 本来就是空的，一直都是空的。

## 根本原因

集装箱订单的两头**从来就不在装卸货地址里**：

| 字段 | 集装箱单 | 卡车单 |
|------|---------|--------|
| `pickup_address->>'city'` | 一直是空 | 装货城市 |
| `delivery_address->>'city'` | 一直是空 | 卸货城市 |
| `pod` / `final_destination` | 卸货港 / 最终目的地 | 不用 |

两端列表却一直无差别地读 `pickup_city → delivery_city`。
所以集装箱单的路线**一直是错的**，只不过以前两头都空，显示成 `- → -`，
看起来像「这单没填地址」，没人当成 bug。

新字段一填，左边有值了、右边还是空，`Hamburg → -` 这种**半截数据**立刻显得不对劲——
是新字段把老问题照出来了，不是新字段引入了问题。

## 错误代码

```tsx
// 两端列表都这么写，不分业务类型
<span title={`${order.pickup_city} → ${order.delivery_city}`}>
  {order.pickup_city} → {order.delivery_city}
</span>
```

## 正确代码

```tsx
// 集装箱单走 pod / final_destination，其余走装卸货城市
function routeFrom(order: OrderRow): string {
  const value = order.business_type === BUSINESS_TYPES.TRUCK_FTL
    ? order.pod || order.pickup_city
    : order.pickup_city
  return value || '-'
}
```

列表接口也要相应带出这两列（`server/modules/order/model.js` 的 list SELECT）。

## 防护规则

1. **加了新字段后，去看所有会显示这组数据的地方**，别只验证「新字段自己存没存对」。
   本次是路线列，同样的模式还可能出现在导出、单据、通知文案里。
2. **`A → B` 这种成对展示，一头有值一头空要当成信号**：要么数据没填，要么取值取错了源。
   写的时候就该问一句「这个业务类型的这两头到底存在哪一列」。
3. **`- → -` 这种「两头都空」最容易掩盖取值错误**，因为它看起来像合法的空数据。
   兜底值让错误静默（踩坑 013 防护第 2 条的同款教训）。
4. 改完记得**重启后端**再看效果：列表 SELECT 改了但进程没重启，页面上什么都不会变，
   很容易误判成前端没生效（本次就多绕了一圈）。
