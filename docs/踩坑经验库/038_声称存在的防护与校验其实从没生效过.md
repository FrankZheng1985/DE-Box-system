# 038 · 声称存在的防护与校验，其实从没生效过

> 发现日期：2026-08-04（需求表 1.0 全部交付后做收尾清理时查出）
> 涉及文件：三端 `package.json` 的 lint 脚本、`docs/踩坑经验库/035_*.md` 的防护规则 #3

## 问题现象

两件事表面上都"已经有了"，实际上**从来没有真的在起作用**：

### 一、三端 `npm run lint` 从建项目起就跑不起来

`admin` / `customer-portal` / `carrier-portal` 三个前端：

- `package.json` 里都有 `"lint": "eslint . --ext ts,tsx --report-unused-disable-directives --max-warnings 0"`
- `devDependencies` 里 `eslint`、`@typescript-eslint/*`、`eslint-plugin-react-hooks`、
  `eslint-plugin-react-refresh` 五个包一个不少，全都装着

**但三个目录里都没有 `.eslintrc.cjs`**，跑起来直接：

```
ESLint couldn't find a configuration file.
```

所以这个"代码规范检查"一次都没执行过。全局 CLAUDE.md 里写的
「禁止 `console.log`」「未使用变量用 `_` 前缀」这些规则，**没有任何东西在强制**。

补上配置后一跑，攒了 **25 个错误 + 35 个警告**。

> 交接文档里当时只记了「carrier-portal 的 lint 跑不起来」，
> 因为发现时只试了那一端。实际上三端都是坏的——**别信"只有 X 有问题"，
> 同一类配置要三端都验一遍。**

### 二、踩坑 035 写的防护规则，代码里根本没有

踩坑 035（删主数据不清理账号绑定 → 门户静默全空）的防护规则 #3 原文：

> `users.linked_entity_id` 没有外键约束，所以数据库层面拦不住。
> 要么补外键，要么在删除流程里显式检查——**本次选了后者**（补外键要处理存量脏数据，风险更高）。

「本次选了后者」读起来像是已经做了。实际上：

- 全仓库搜 `linked_entity_id`，`client` / `carrier` 两个模块里**一处都没有**
- 更根本的是，**这两个模块压根没有删除路由**——只有 `toggle-status`（启用/停用）。
  应用层删不掉公司，"删除流程"这个落点在系统里并不存在

也就是说那条防护规则从写下来那天起就是空的，而且**永远不可能被实现**，
因为它假设了一个不存在的流程。

## 根本原因

两件事的共同点：**"存在"被当成了"生效"**。

- 有 lint 脚本 + 装了 eslint 依赖 → 看起来 lint 是有的，没人真跑过一次看退出码
- 踩坑文档里写了防护规则 → 看起来防护是有的，没人回头验证代码里真有这段

踩坑文档尤其危险：它是**写给未来的自己看的可信来源**，
一条没落地的防护规则会让后来者以为这个坑已经堵上了，从而不再检查。

## 解决方案

1. 三端各补一份 `.eslintrc.cjs`，清掉 25 个错误，lint 退出码归 0
2. 防护改到**真实存在的落点**——登录入口（`server/modules/auth/routes.js`）：
   门户账号绑定的公司查不到就拒绝登录并明确报错，不再放进去看满屏空列表
3. 回头把踩坑 035 的防护规则 #3 改成实际做法，并注明原方案为何不成立

## 防护规则

1. **写进踩坑文档的防护规则，必须附上"落在哪个文件哪一段"**。
   只写"选了 X 方案"而不指向具体代码位置，等于没写——
   下次读的人无从验证，只会默认它已经生效。
2. **声称做了某个防护，提交前要能 grep 出来给自己看一眼。**
   搜不到就是没做。
3. **任何"质量保障"类脚本（lint / check / test），加进 package.json 的同时
   必须真跑一次看退出码**，而不是加完就认为它在守着。
   本次教训：一个从没执行过的 lint 脚本在仓库里躺了整个项目周期。
4. **同类配置要三端都验**。发现一端坏了，默认另外两端也坏，逐个确认再下结论。
5. 设计防护时先确认**这个流程在系统里真的存在**。
   踩坑 035 押在"删除流程"上，而 clients / carriers 根本没有删除接口。
