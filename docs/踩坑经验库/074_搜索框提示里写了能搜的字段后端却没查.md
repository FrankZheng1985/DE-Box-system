# 074 · 搜索框提示里写了「能搜柜号」，后端却没查这一列

> 发现日期：2026-09-05（客户提了「筛选功能增加按柜号筛选」，回头查才发现提示语早就这么写了）
> 涉及文件：`customer-portal/src/pages/InquiryList.tsx`（提示语）、`server/modules/inquiry/routes.js`（搜索条件）

## 问题现象

客户门户询价列表的搜索框提示写着：

```
搜索询价编号 / 柜号 / 贵司单号
```

客户照着输柜号，**搜出来是空的**。不报错、不提示，就是"查无此单"的样子 ——
客户只会以为这张单不在系统里，不会想到是搜索功能少查了一列。

## 根本原因

前端提示语列了三个字段，后端 `GET /inquiries` 的 search 分支只查了两个：

```js
sql += ` AND (i.inquiry_number ILIKE $1 OR i.customer_ref ILIKE $1 OR c.company_name ILIKE $1)`
//                                                    ↑ 没有 i.container_no
```

**提示语是随手写的，没有对着后端逐字核对。** 加提示语时想的是"这个列表里有柜号列，
那搜索肯定能搜"，但列表显示用的是 `SELECT i.*`（顺带就带出来了），
搜索却是另一段独立的 WHERE 条件，两者根本不是一回事。

## 为什么特别值得记

**这类 bug 不会被任何门禁发现**：tsc 过、eslint 过、构建过、i18n 检查也过 ——
提示语只是一个字符串，没有任何工具知道它在向用户承诺什么。
只有真的拿柜号去搜一次才会暴露。

而且它的表现极具误导性：客户搜不到会去问运营"我这单是不是没进系统"，
运营在管理端一看单子好好的，双方都不会怀疑到搜索框身上。

## 正确做法

```js
// 提示语里写了几个字段，WHERE 里就要有几个
sql += ` AND (i.inquiry_number ILIKE $1 OR i.customer_ref ILIKE $1
              OR i.container_no ILIKE $1 OR c.company_name ILIKE $1)`
```

## 防护规则

1. **写或改搜索框 placeholder 时，逐字对着后端的 WHERE 条件核一遍** ——
   提示里每列一个字段，后端就得有一个 `ILIKE`。多一个少一个都是向用户撒谎。
2. **反过来也要核**：后端加了可搜字段，提示语要跟上，否则用户根本不知道能这么搜
  （本次管理端就是这种情况：后端补上柜号后，同步把提示改成
   「搜索询价编号 / 柜号 / 客户单号 / 客户名称」）。
3. **验收搜索功能，必须拿提示语里的每一类值各搜一次**，不能只搜单号了事。
   对照着验：改之前搜柜号命中 0 条、改之后命中 1 条，两者不同才算真的修好。
4. 同类风险点：列表能「显示」某字段 ≠ 能「搜索」它，
   显示走 `SELECT`、搜索走 `WHERE`，两段代码互不相干。
