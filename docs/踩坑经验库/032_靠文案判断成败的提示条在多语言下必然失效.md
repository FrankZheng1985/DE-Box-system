# 032 · 靠文案判断成败的提示条，一上多语言就必然失效

> 发现日期：2026-08-03（P9 三语国际化，承运商门户）
> 涉及文件：`carrier-portal/src/pages/{UploadCMR,GPSReport,CompanySettings}.tsx`

## 问题现象

这三个页面的提示条都是同一个写法：成功和失败共用一个 `message` 字符串状态，
靠**文案里有没有"成功"两个字**来决定显示绿色还是红色。

```tsx
const [message, setMessage] = useState('')
setMessage('CMR 上传成功')     // 想要绿色
setMessage('上传失败，请重试')  // 想要红色

<div className={message.includes('成功') ? 'bg-green-50 text-green-600' : 'bg-red-50 text-red-600'}>
  {message}
</div>
```

中文界面下看不出问题。**一旦把文案换成英文/德文，`includes('成功')` 永远为 false**——
"CMR uploaded successfully" 和 "CMR erfolgreich hochgeladen" 里都没有"成功"两个字，
于是**上传成功也显示成红色报错样式**。用户会以为操作失败，反复重传。

更麻烦的是：这类 bug **不报错、不崩溃、类型检查也过**，只有真的切到德语点一次上传才看得见。

## 根本原因

把「业务状态」编码进了「展示文案」里。文案是会变的（换语言、改措辞、后端返回的
`res.message` 直接透传），而状态判断依赖它，等于把逻辑挂在最不稳定的东西上。

同一个页面里还有个隐藏版本：`setMessage(res.message || '上传失败，请重试')`
——后端返回的 message 是什么内容前端根本控制不了，就算不做多语言，
后端哪天把"操作成功"改成"已完成"，颜色也会翻车。

## 正确写法

状态和文案分开存，颜色只看状态：

```tsx
// 成败单独存布尔值，跟文案彻底解耦
const [message, setMessage] = useState<{ text: string; ok: boolean } | null>(null)

setMessage({ text: t('cmr.success'), ok: true })
setMessage({ text: res.message || t('cmr.errorFailed'), ok: false })

<div className={message.ok ? 'bg-green-50 text-green-600' : 'bg-red-50 text-red-600'}>
  {message.text}
</div>
```

## 防护规则

1. **任何 UI 分支（颜色、图标、显示隐藏）都不许判断文案内容**——
   不许 `includes('成功')` / `includes('失败')` / `=== '已完成'` 这类写法。
   要判断就判断状态码、布尔值、枚举值。
2. 提示条统一用 `{ text, ok }` 结构，或直接上 toast 组件的 `success/error` 两个方法。
3. **做 i18n 时，除了替换文案，必须回头搜一遍 `includes('` 和字符串比较**——
   替换文案本身是机械活，这类隐藏依赖才是真正会上线出事的地方。
   搜索命令：`grep -rn "includes('" src --include='*.tsx'`
4. 同理适用于：靠中文状态名做 `switch`、把中文当 Map 的 key、
   按文案长度算宽度（见踩坑 022）。
