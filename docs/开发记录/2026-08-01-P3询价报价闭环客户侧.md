## 功能说明

打通「询价 → 报价 → 客户确认 → 自动生成订单」全链路。

### 1. 需求 2：客户接受报价即自动建单

老流程是两步且中间常年断档：客户接受（只改状态）→ 运营手工点「一键下单」。
现在 `POST /quotations/:id/accept` 内部直接建单：

| 服务类型 | 自动建出的订单初始状态 | 说明 |
|---------|----------------------|------|
| TRUCK_LTL / TRUCK_FTL | `PENDING_REVIEW` 待审核 | 正是需求 2 要的"自动进待审核" |
| LOCAL_DELIVERY | `PENDING_DISPATCH` 待派送 | 见下方「设计决策」 |

- 货物信息从来源询价单带进订单（旧的手工 convert-order 建出来的是空订单）
- `quotations.converted_order_id` 记住产出的订单，"建没建单"有唯一事实来源
- 建单失败（信用超额）整笔事务回滚，报价退回原状态 —— Frank 2026-08-01 拍板的口径
- 手工 `convert-order` 保留，收紧为仅运营可调，用于存量补建

### 2. 需求 5.1：询价三来源补齐前两种

| 来源 | 本次状态 |
|------|---------|
| 客户门户自助提交 | 表单从 5 个字段升级为结构化地址 + 联系人 + 按件明细 |
| 运营代客户建单 | **全新**，admin 此前完全没有询价页面 |
| 开放 API（易抵达等） | P8 再做，数据结构已按 `inquiry_cargo_items` 预留 |

### 3. 需求 5.4：按件明细 + 一键复制 + 导出

- 新表 `inquiry_cargo_items`：单号 / 件数 / 长宽高 / 单件实重 / 单件体积 / 行级 LDM
- **LDM = 长m × 宽m ÷ 2.4 × 件数**（2.4 = 欧洲标准车厢内宽），自动算、可勾「手改」覆盖
- 单件体积 = 长 × 宽 × 高 ÷ 1,000,000（长宽高单位 cm）
- 明细汇总回写询价表头的件数/实重/体积/LDM；**无明细行时不回写**，避免抹掉客户手填的总量
- 「复制摘要」：固定文本模板，含单号/国家/地址/邮编/电话/邮箱/件数/长宽高/实重/体积/LDM，直接可粘给服务商（清平姐的重点痛点，支持列表批量勾选）
- 「导出 Excel」：固定模板，一行一件货，表头字段每行重复，方便服务商筛选排序

### 4. 新增报价状态 PENDING_DECISION（客户待定）

客户在门户可选**接受 / 拒绝 / 待定**。待定后报价停在 `PENDING_DECISION`，
运营在列表和统计卡片上能一眼挑出需要跟进的单，客户之后仍可改为接受或拒绝。

## 设计决策（需要 Frank 知晓）

1. **本地派送自动建单落 `PENDING_DISPATCH` 而不是 `PENDING_REVIEW`。**
   P1 定的本地派送状态机初始状态是 `PENDING_QUOTE`（待报价），但报价已经被客户接受了，
   订单停在"待报价"自相矛盾。本地派送的简化流里没有"待审核"这一环，所以推进一格到待派送。
   **代价**：本地派送订单不经运营审核直接进待派送。如果业务上要保留审核关口，需要再议。

2. **询价地址不另开列，继续用 `route_from` / `route_to` JSONB**，
   形状固定为 `{ country, city, zipCode, address }`，与 `orders.pickup_address` 一致。
   这样前后端只有一套契约（踩坑 011 形态四就是两端形状不一致踩的）。

3. **admin 侧边栏仍是一个「询价报价」入口**，指向 `/inquiries`，
   页内用 `InquiryQuotationTabs` 在询价/报价两张列表间切换，`/quotes` 也点亮同一菜单项。

## 关联影响分析

- **顺带修掉的越权漏洞**：报价的 accept / reject 此前只挂 `authenticateToken`，**任何登录账号
  （含别家公司的客户账号、承运商账号）都能接受或拒绝任意一张报价**；create/edit/void 同理。
  本次全部补上身份校验。询价的 `GET /:id` / PUT / DELETE 也有同样问题，一并修复。
- **carrier-portal 不受影响**：承运商不参与询价报价流程，接口层已显式拒绝 CARRIER 身份。
- **订单模块**：只通过 `orderService.createOrder` / `updateStatus` 调用，**没有改动 order 模块任何文件**，
  与并行进行的 P2 订单文件中心不冲突。
- **信用管理**：复用 `createOrder` 内既有的信用检查，未改 credit-manager。
- **自动开票**：本地派送签收即 COMPLETED，行为不变。
- **确认过不受影响**：CMR / 清关 / 放单 / GPS / 财务均不读询价与报价表。

该路径已在本地对着真实 PostgreSQL 完整验证过三种服务类型
（LTL/FTL → `PENDING_REVIEW`、本地派送 → `PENDING_DISPATCH`，货物信息带入、
`converted_order_id` 写上、单据流连线建立）。
