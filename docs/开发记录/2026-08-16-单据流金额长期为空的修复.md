# 2026-08-16 单据流（document_flow）金额长期为空的修复

**模块**：ERP 内核 —— 单据流引擎 / 凭证引擎、订单模块、财务模块

---

## 问题

`document_flow` 表里所有报价→订单（`QUO_TO_ORD`）连线的 `amount` 和 `currency` 都是 NULL。

```sql
select flow_type, count(*), count(amount) as with_amount from document_flow group by 1;
```

这个问题在 `docs/踩坑经验库/017` 里记录过，但当时属于 P3 范围外，只记未修，一直留到现在。

## 根因

**同一条连线被两处代码各建了一次，先到的那处没带金额，后到的那处被静默丢弃。**

1. `server/core/document-engine.js` 的 `createDocument()` 只要收到 `sourceDocType` / `sourceDocId`
   就会自动建一条连线，`flow_type` 是拼出来的（`'QUO' + '_TO_' + 'ORD'` = `QUO_TO_ORD`），
   **不带金额**。
2. `server/modules/order/service.js` 的 `createOrder()` 步骤 4 随后又显式调
   `documentFlow.createFlowLink()`，带着 `amount` 和 `flow_type: 'QUOTATION_TO_ORDER'`，
   但撞上唯一约束 `UNIQUE(preceding_doc_id, subsequent_doc_id)`，被
   `ON CONFLICT ... DO NOTHING` **整条丢掉** —— 不只是 flow_type 没改成它想要的名字，
   连本该带上的金额也一起丢了。

所以步骤 4 那段代码从上线起**一次都没生效过**，而 `DO NOTHING` 不报错、不返回受影响行数，
谁也没发现。

## 修改内容

采用「两头都堵」：既让第一个写入方就带上金额（根因修复），
也让 ON CONFLICT 不再静默丢弃后来者带来的信息（防护网）。

| 文件 | 操作 | 说明 |
|------|------|------|
| `server/core/document-flow.js` | 修改 | `createFlowLink` 的 `ON CONFLICT ... DO NOTHING` 改为 `DO UPDATE SET`，用 `COALESCE(已有值, EXCLUDED.新值)` 只补空值。**`flow_type` 刻意不在 DO UPDATE 里** |
| `server/core/document-engine.js` | 修改 | `createDocument` 新增两个可选参数 `flowAmount` / `flowCurrency`，传给它自动建的那条连线；仅在有来源凭证时生效 |
| `server/modules/order/service.js` | 修改 | 步骤 2 建订单凭证时传 `flowAmount: clientPrice`；**删除**步骤 4 那段从未生效的 `createFlowLink`；自动生成应收/应付凭证处（`FI_AR`/`FI_AP`）一并补上 `flowAmount`；`documentFlow` 已无引用，从 import 里移除 |
| `server/modules/finance/routes.js` | 修改 | 收付款凭证（`FI_AR`/`FI_AP` → `FI_REC`/`FI_PAY`）补 `flowAmount: payAmount`，金额是本次收付额（可能是部分付款，不等于发票总额） |
| `server/database/migrations/132_backfill_document_flow_amount.sql` | 新增 | 回填存量空金额，按 `orders.client_price` 补；只碰 `amount IS NULL` 的行，幂等 |
| `docs/踩坑经验库/017_...md` | 修改 | 「遗留」章节改为「已修复」，补上做法、边界和新涉及文件 |

### 为什么 `flow_type` 不进 DO UPDATE

两个写入方用的名字不一样（`QUO_TO_ORD` vs `QUOTATION_TO_ORDER`）。如果一并覆盖，
库里的取值会随两处代码的执行顺序在两个值之间横跳，
而踩坑 017 的**起因**正是"按字面值 WHERE 的迁移命中 0 行"。所以只补金额，名字不动。
迁移 107 里 `flow_type IN ('QUO_TO_ORD','QUOTATION_TO_ORDER')` 的双值匹配继续保留。

## 关联影响

### 一并改了的

- **应收/应付单据流**（`ORD_TO_FI_AR` / `ORD_TO_FI_AP`）：`order/service.js` 里自动生成
  应收应付凭证时同样传了 `sourceDocType: 'ORD'`，是同一个根因，本次一并带上金额。
- **收付款单据流**（`FI_AR_TO_FI_REC` / `FI_AP_TO_FI_PAY`）：同上，一并带金额，
  这样「报价→订单→应收→收款」整条钱链在单据流上都有金额。

### 确认不受影响的

- **`finance/routes.js` 手工建应收/应付**（`ORDER_TO_FI_AR` / `ORDER_TO_FI_AP`）：
  那里 `createDocument` **没有**传 `sourceDocType`，`createFlowLink` 是唯一写入方，
  本来就带着金额、从来没坏过。本次 ON CONFLICT 的改动对它是空操作（不会冲突）。
- **`cmr/routes.js` 的 ORDER_TO_CMR**：CMR 单据本身没有金额概念，不传即保持 NULL，符合预期。
- **`getFullDocumentFlow` 的递归查询**：只读，未改。
- **表结构**：没动 `document_flow` 的任何列、约束、索引。迁移只 UPDATE 两列的值。
- **三端前端**：本次零前端改动。

### 受影响但本次未改（已向 Frank 说明并确认）

1. **`INQ_TO_QUO`（询价→报价）和 `QUO_TO_QUO`（报价改版本）的金额仍是 NULL。**
   不是遗漏：`quotation/routes.js` 是**先建凭证、后跑定价引擎**，
   建凭证那一刻报价总价还没算出来，要带金额得先调整代码顺序。
   和本次"金额被 DO NOTHING 吃掉"不是同一个问题，性质不同，另行评估。

2. **订单详情页「单据流」卡片的字段名和后端返回完全对不上**（本次顺带发现的独立缺陷）：
   后端 `getFullDocumentFlow` 返回 `preceding_doc_type` / `preceding_doc_id` / `flow_type` /
   `amount` / `currency` / `depth`，而 `admin/src/pages/OrderDetail.tsx` 的
   `LinkedDocument` 接口声明的是 `{ id, type, doc_number }`，`DocFlowItem` 读的
   `doc.id` / `doc.type` / `doc.doc_number` **三个全是 undefined**，
   而且它根本没有渲染金额的地方。
   **后果**：本次修好金额后，页面上的单据流卡片仍然看不到金额，连单号都是空的。
   Frank 2026-08-16 决定另开任务单独修（本次改动保持纯后端、零前端部署面）。
   属于踩坑 011 / 033 那一族（前后端契约对不上）。

## 验证

1. **ON CONFLICT 语义**（本地库，事务内跑完 ROLLBACK）：
   - 先插一条无金额的连线 → 再插一条带 900.00 EUR 的 → 金额被补齐为 `900.00 / EUR`，
     `flow_type` 保持 `QUO_TO_ORD` 未被覆盖 ✓
   - 已有金额的行再被写入 `1.00 / USD` → 保持 `900.00 / EUR` 不被覆盖 ✓
2. **端到端**（本地库，走真实 `createDocument` 代码路径，事务内 ROLLBACK）：
   ```
   单据流结果: [{"flow_type":"QUO_TO_ORD","amount":"900.00","currency":"EUR"}]
   ```
   对照踩坑 017 里记录的原始症状 `[{"flow_type":"QUO_TO_ORD","amount":null}]`，已修复。
3. **迁移 132**（本地库，事务内跑完 ROLLBACK）：
   `QUO_TO_ORD` 的 `with_amount` 从 0/1 → 1/1；复跑一次 `UPDATE 0`（幂等）；
   其余 4 类 flow_type 计数不变（不误伤）。
4. **门禁**：`node --check` 四个文件全过；根目录 `npm run check:i18n` exit 0；
   后端 `eslint` 对四个文件 exit 0。无前端改动，未跑前端门禁。

## 部署注意（重要）

**本项目 push main 即自动部署，且 CI 不跑数据库迁移**（踩坑 063）。

本次的迁移 132 是**纯数据回填**，不新增列、代码也不依赖新列，
所以代码和迁移谁先谁后都不会 500。但仍按项目规矩执行：**先备份 → 先跑迁移 → 再 push**。

```bash
# 1. 备份
ssh eu-tms "cd /var/www/germany-box-system/server && export \$(grep '^DATABASE_URL' .env | xargs) \
  && pg_dump \"\$DATABASE_URL\" | gzip > /var/backups/germany-box-db/germany_box_transport_\$(date +%Y%m%d_%H%M%S).sql.gz"

# 2. 跑迁移
ssh eu-tms "cd /var/www/germany-box-system/server && export \$(grep '^DATABASE_URL' .env | xargs) \
  && psql \"\$DATABASE_URL\" -f database/migrations/132_backfill_document_flow_amount.sql"

# 3. 确认回填到位后再 push
```
