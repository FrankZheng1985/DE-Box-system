## 🧠 关键决策

| 决策 | 结论 | 原因 |
|---|---|---|
| i18n 方案 | **react-i18next**（2026-08-03 Frank 拍板） | 行业标准，插值/复数/命名空间开箱即用；自研 t() 后期要自己补轮子 |
| 语言包放哪 | **每端各一份** `src/i18n/locales/`，不搞 monorepo 共享包 | 三端是三个独立 Vite 应用，为共享几十个通用词建 workspace 属于过度工程化 |
| 德语上线策略 | **AI 初稿直接上线**，同时导出术语表给德语同事校对，校对完批量回改（Frank 拍板） | 不阻塞上线；物流术语（CMR/清关/放单/LDM）人工兜底 |
| 语言优先级 | localStorage → `users.language` → 浏览器语言 → `zh` | 未登录也能记住选择；登录后以账号设置为准 |
| 持久化接口 | 复用 `PUT /api/v1/system/settings/account` 的 `language` 字段 | 该接口只挂 `authenticateToken`，三端账号都能调，不用新建端点 |
| 做的顺序 | carrier-portal（最小）→ customer-portal → admin | 最小端当样板跑通全链路，后两端照抄，返工风险最低 |

## 🔗 关联影响

1. **后端 `auth/routes.js` 是三端共用的登录接口**——多返回一个 `language` 字段是**纯新增**，
   客户门户和管理端的现有代码不读这个字段，不受影响；等它们做 i18n 时直接就能用。
2. **`PUT /api/v1/system/settings/account`** 被语言切换器复用。该接口只挂 `authenticateToken`
   （不限 userType），三端账号都能调，本次没动它的鉴权。
3. **CompanySettings 的字段读取收窄**：原来把接口返回的所有字段 spread 进表单，
   保存时会把 `language` 按页面加载时的旧值写回去，正好会**覆盖掉用户刚切的语言**。
   改成只挑 `CompanyInfo` 声明过的 8 个字段。
4. **Billing 求和 bug 顺带修了**：`sum + p.amount` 在后端返回字符串时会变成字符串拼接
   （踩坑 002）。因为本次把金额显示改成 `formatMoney`，不修的话金额会更明显地错，属于同一改动范围。
5. **确认不受影响**：admin 运营端、customer-portal 本次**一行未动**；
   数据库**零改动**（`users.language` 字段本来就有）；OSS / 邮件 / 权限体系均未触及。
