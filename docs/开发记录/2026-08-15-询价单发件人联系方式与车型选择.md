## 需求与实现

### 第 8 条 · 询价单增加发件人的电话和邮箱（优先级：高）

原来整张询价单只有一组联系人，取件方（发货人）没有任何联系方式，
服务商拿到询价后没法直接联系发货人约提货时间。

- 发货联系人（姓名 / 电话 / 邮箱）**并进 `inquiries.route_from` 的 JSONB**，不新增数据库列
  （做法与订单模块一致，见踩坑 047）
- 原有的 `contact_name / contact_phone / contact_email` 三列**语义收窄为收货联系人**，
  界面与 Excel 表头都明确标成「收货联系人」
- 三个入口一起改：客户门户建单、运营端建单/编辑、Excel 批量导入

### 第 9 条 · 取件地和派送地的页面布局（优先级：中）

客户反馈两侧地址挤在一起、边界感不强，容易把派送地址填进取件栏。

- 客户门户：一侧一张**带边框的卡片**（`AddressCard`），地址在上、该侧联系人在下，两张完全对称
- 运营端本来就是左右两个 Section，只在「起运地」里补了发货联系人一组
- 顺手修了一个既有问题：地址四格在移动端是 `grid-cols-2`，德语的
  「Straße und Hausnummer」放不下会被截断，改成 `grid-cols-1 sm:grid-cols-2`
  （提示词必须完整显示，Frank 2026-06-01 定的规范）

### 第 10 条 · 建询价单时增加车型选择（优先级：高）

卡派 LTL 要先选专车 / 拼车，选专车后再选车长。

- **「专车 / 拼车」不新增字段**，复用已有的 `inquiries.transport_type`（值域 FTL / LTL）：
  FTL = 专车（整车），LTL = 拼车（零担），语义完全对得上
- **车型（车长）新增一列** `inquiries.vehicle_length_code`（迁移 128，可空）。
  七档：4m / 6.2m / 7.2–7.45m / 7.8–8.2m / 9.0–9.6m / 12m / 13.6m
- 为什么不复用 `carriers.vehicle_types`：那一列存的是**车厢类型**
  （帘式 / 集装箱底盘 / 平板 / 冷藏，见迁移 126），和车长是两个维度，
  混用会重演踩坑 013 的「两套词表一个名字」
- 界面规则：本地派送不显示这一块；卡派 LTL 可选专车/拼车；卡车运输 FTL 本身就是整车，
  固定专车、只让选车长。**车型只在专车下存**，切回拼车会把车型一起清掉（前端、后端、导入三处都做了）

## 关联影响

**一并改了的：**

- **服务商询价摘要**（`buildSummaryText`）：原来是「起运地 / 目的地 / 联系人」三段，
  联系人是孤零零一组。现在改成两段各带自己那侧的联系人，并在抬头加了运输方式和车型。
  不改的话客户填的发件人电话根本传不到服务商手里，第 8 条等于白做一半。
- **询价 Excel 导出**：加了运输类型、车型、发货联系人三项（共 5 列），
  收货侧的三列表头由「联系人 / 电话 / 邮箱」改为「收货联系人 / 收货联系电话 / 收货联系邮箱」。
- **批量导入模板**：加了 5 列，专车/拼车与车型两列带下拉。
  **客户手上的旧模板仍然可用** —— 旧表头「联系人 / 电话 / 邮箱」「Contact / Phone / Email」
  「Ansprechpartner / Telefon / E-Mail」都在别名表里继续认，一律按收货侧落（已用旧表头实测）。
- **运营端详情与编辑页**：客户填的发货联系人和车型运营看得到、也改得了。

**确认不受影响的：**

- 订单模块（`orders`）完全没动。订单表单里的 `transportType.*` 文案因为共用语言包，
  中文 FTL 从「整车 (FTL)」变成「专车 (FTL)」，是文案统一，不影响取值。
- `carriers.vehicle_types`（车厢类型）没动，和本次的车长是两个独立字段。
- 承运商门户没动。
- 存量询价单：新列可空，老单全是 NULL；界面上没有值就不显示那一行。

## 上线注意

**生产必须先跑迁移 128 再发后端**，否则建单会因为 INSERT 里多一列而失败：

```bash
psql "$DATABASE_URL" -f server/database/migrations/128_inquiries_vehicle_length.sql
```

前端可以后发；先发前端的话，车型选了也不会存（后端还没这列），不会报错但会静默丢。
