# 2026-08-07 · 车型统一为代号 · 补后端 options 返回值

> 模块：基础数据接口
> 承接：`2026-08-07-车型词表统一为代号.md`（提交 `2776e6c`）
> **上一个提交只改了前端，等于什么都没变——本篇补上真正生效的那一处。**

---

## 一、上一个提交为什么是个"假修复"

`2776e6c` 做了三件事：前端改读基础数据、迁移 126 转存量、加空态提示。
四包 lint 全绿、`build:check` 通过、迁移在事务里验得漂漂亮亮，**看上去可以上线了**。

上线后在生产页面上拉了一次基础数据接口，返回是：

```json
{"value":"Curtain Side", "label":"Curtain Side (篷布车)", "code":"CURTAIN_SIDE"}
```

**`value` 是英文名**，代号在单独的 `code` 字段里。而前端 `checked` / `onChange`
绑的是 `opt.value` —— **存进库的还是英文名**。

也就是说上一个提交只是把「写死的英文名」换成了「从接口取的英文名」，
**筛选依然匹配不上，问题一点没解决**。

### 为什么所有门禁都没拦住

因为**代码本身没有任何错误**：类型对、lint 干净、构建通过、迁移逻辑正确。
错的是"我以为 `opt.value` 是代号"这个**假设**，而假设不会被编译器检查。

## 二、根因：options 接口的 value 是按类型分别指定的

`server/modules/system/routes.js` 的 `/master-data/:type/options` 里，
每种基础数据的 `value` 取值都**刻意对齐"业务表里已经存的格式"**：

| 类型 | value | 为什么 |
|---|---|---|
| countries | `name_en` | `orders.country` 存的就是英文名 |
| currencies / container-types | `code` | 本来就存代号 |
| **special-requirements** | **`code`** | **迁移 120 从 name_zh 改过来的** |
| **vehicle-types** | ~~`name_en`~~ → **`code`** | **本次，迁移 126** |

所以「统一成代号」这件事，**天然是前端 + 后端 + 迁移三处一起改**，
少任何一处都不生效。上一个提交漏了后端这一处。

## 三、改动

`server/modules/system/routes.js` 一处：车型分支 `value = row.name_en` → `value = row.code`。

**没有其他改动。** 前端和迁移在上一个提交里已经是对的。

## 四、验证（在生产上真拉接口，不只看代码）

把改动临时部署到生产、`pm2 reload`，然后用管理端登录态拉接口：

| 阶段 | 接口返回的 value |
|---|---|
| 改之前 | `"Curtain Side"` ← 英文名，前端存进去的就是它 |
| 改之后 | `"CURTAIN_SIDE"` ✔ 代号 |

`label` 两次都是 `"Curtain Side (篷布车)"`（显示不受影响，仍是本地化名称）。

**验完立刻把生产恢复成原代码**（正式版本走 CI，不留手工改动），
并确认 `/api/health` 正常。

其余：`server` lint 退出 0。

## 五、波及面排查

全仓库只有两处消费车型选项，**都会自动跟着变对**：

| 位置 | 影响 |
|---|---|
| `CarrierList.tsx` 新增承运商 | 勾选后存的从英文名变成代号 ✔ 正是本次目的 |
| `OrderAssign.tsx` 派单页车型筛选 | 传给 `/carriers/match` 的从英文名变成代号 ✔ 与库里对齐 |

**确认不受影响**：其余基础数据类型（国家/币种/箱型/船司/港口/特殊要求）
的分支一个字没动。

## 六、教训

**"改完了、门禁全绿"不等于"功能生效了"。**
凡是跨前后端的字段格式变更，必须在真实链路上取一次真实返回值来对。

今天这是第二次靠"在真东西上看一眼"抓到自己的 bug
（上一次是城市名变音符号，踩坑 053）——两次都是数据层/构建层全绿、
真实环境一验就露馅。
