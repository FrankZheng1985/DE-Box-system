# 2026-08-17 财务记录详情接口（GET /finance/records/:id）

> 模块：财务（finance）＋ 运营管理端财务详情页
> 性质：预防性修复，无数据库迁移

---

## 一、要解决的问题

`admin/src/pages/FinanceDetail.tsx` 没有专用详情接口，靠拉两个列表再在前端 `find`：

```tsx
const arRes = await api.get<any>('/finance/receivables?pageSize=100')
const apRes = await api.get<any>('/finance/payables?pageSize=100')
const found = [...arRes.data, ...apRes.data].find(r => r.id === id)
```

`pageSize=100` 是分页第一页而不是全部，所以 `financial_records` 一旦超过 100 条，
靠后的记录用 `/finance/:id` 直接访问就会落到「记录不存在」分支 —— 而记录其实存在。
翻页越多坏得越多，且全程 200、无任何报错。

**为什么现在修**：2026-08-16 的提交 bd2b013 修好了订单详情页单据流卡片，
新增了「单据流条目 → `/finance/<entity_id>`」的跳转路径。
在那之前前端字段名是错的、跳转恒等于 `#`，这条路走不到，隐患一直没暴露；现在它可达了。

生产目前只有 1 张订单及其应收应付（本地开发库 3 条），短期不会触发，属于预防性修复。

## 二、改了什么

### 后端 `server/modules/finance/routes.js`

新增 **`GET /api/v1/finance/records/:id`**，按 id 查单条 `financial_records`。

- **返回结构与列表逐字对齐**：`fr.*` + `counterparty_name` + `order_number`。
  详情页原本吃的就是列表行，字段名一致才不用改渲染部分（同踩坑 066 的教训）。
  应收对手方在 `clients`、应付在 `carriers`，一条 SQL 里 join 两张表再 `COALESCE`。
- **权限**：`requirePermission('finance:view', 'portal:billing_view', 'carrier_portal:billing_view')`
  —— 与 `/receivables`、`/payables` 两个列表完全相同的三个码（任意一个满足即放行）。
  **刻意不新增权限码**：本接口的数据可见范围和列表一模一样，没有新的权限面；
  新增一个码反而要配迁移 + 角色勾选，而生产 push 即部署、CI 不跑迁移，
  等于给一个纯前端修复挂上一个必须手工跑迁移的前置条件。
- **租户隔离**（新增 `canReadRecord()` 辅助函数）：列表是「先收窄查询条件再查」，
  详情没有条件可收窄，只能查出来再判，口径与列表一致：
  - 客户（CLIENT）只能看自己的**应收**
  - 承运商（CARRIER）只能看自己的**应付**
  - 运营（OPERATOR）两边都能看

  不属于当前登录方的一律按 **404**「财务记录不存在」返回，不回 403 ——
  回 403 等于告诉对方这个 UUID 是一条有效记录（CLAUDE.md 第 8 条）。
  **应付记录里是承运商成本价，客户门户绝不能看到。**
- **非 UUID 直接 404**（新增模块级 `UUID_RE`，写法沿用 order / cmr / inquiry 三个模块）：
  扔给 pg 会抛 `invalid input syntax for type uuid`，白白变成 500。
- **路由顺序**：`/records/:id` 第一段是固定的 `records`，与现有 `PUT /:id/payment`、
  `PUT /:id/void` 不冲突。已在代码里留注释：将来若加 `GET /:id`，必须排在它后面。

### 前端 `admin/src/pages/FinanceDetail.tsx`

- 改调 `GET /finance/records/${id}`，删掉拉两个列表 + `find` 的逻辑。
- `id` 缺失时直接结束 loading，不发请求。
- 捕获到 404 时不再 `console.error`（那是「记录真的不存在」的正常路径，页面照常显示提示），
  其余异常仍然打日志。
- 导入方式改为 `import api, { type ApiResponse } from '../utils/api'`，与其他页面一致。

## 四、关联影响分析

**一并处理的**

- 财务详情页是 `/finance/:id` 的唯一消费方，改完即闭环。
- 两个跳转入口都验证过指向同一个 id（`financial_records.id`）：
  - 财务列表页 `FinanceManagement.tsx:702` 的 `onView` → `/finance/${row.id}`
  - 订单详情页 `OrderDetail.tsx` 单据流卡片 `docFlowRoute()` → `/finance/${doc.entity_id}`
    （FI_AR / FI_AP 的 `entity_id` 就是 `financial_records.id`）

**确认不受影响的**

- `GET /finance/receivables`、`/payables` 两个列表接口一行没动，
  客户门户 `Billing.tsx`、承运商门户 `Billing.tsx`、运营端财务列表页行为不变。
- `PUT /finance/:id/payment`、`PUT /finance/:id/void`、导出、账龄、利润分析、摘要
  全部未改，路由顺序也没被新接口影响（`/records` 是固定段）。
- 未新增权限码，`MENU_PERMISSIONS`、角色权限表、权限同步门禁都不需要跟着改。
- 客户门户 / 承运商门户目前**没有**财务详情页，本次不给它们加页面；
  新接口对它们开放只是把隔离口径提前做对，避免以后加页面时漏掉。

**留下的边界**

- 详情接口按单条查，没有做「上一条 / 下一条」之类的翻页，本次不需要。
