## 一、开工前拍板的三个决策（2026-08-02 Frank 定）

| 决策点 | 结论 | 理由 |
|--------|------|------|
| 客户等级口径（计划"待确认"第 5 条） | **新增独立字段 `client_level`（VIP / NORMAL）**，与现有 `credit_level`(A-D) 并存 | A-D 是财务风险评级（看账龄和回款），VIP/普通是商务待遇分级（看销售关系和货量）。塞进一个字段会出现"想给回款一般的老客户挂 VIP"做不到的死角 |
| 信用超额预警发给谁 | **只发内部**（财务 `finance` / 运营经理 `op_manager` / 管理员 `sys_admin`） | "你的信用被冻结了"直接推给客户，商务上容易出事，让业务员自己去谈 |
| 信用日志和释放按钮放哪 | **客户详情页新增「信用风控」Tab**，不新增侧边栏菜单 | 权限沿用已有的 `client:credit`，不用再配一套权限码和菜单映射 |

## 二、做了什么

### 1. 数据库（迁移 111）

| 表 | 字段 | 说明 |
|----|------|------|
| `clients` | `client_level VARCHAR(10) NOT NULL DEFAULT 'NORMAL'` | 商务等级，CHECK 限 `VIP` / `NORMAL`，存量全部落 NORMAL，加索引 |
| `carriers` | `carrier_category VARCHAR(20) NOT NULL DEFAULT 'EXTERNAL'` | CHECK 限 `EXTERNAL` 外部服务商 / `OWN_FLEET` 自营车辆，加索引 |
| `carriers` | `carrier_type VARCHAR(20)` | CHECK 限 `PLATFORM` / `FLEET` / `INDIVIDUAL`，**允许 NULL**——存量不知道是哪一类，留空让运营慢慢补，不硬塞默认值制造假数据 |
| `carriers` | `remarks TEXT` | 特点 / 优势 / 短板，调度选车时参考 |

### 2. 信用管理内核

- `credit-manager.js` 的 `_logAndReturn` 按检查结果分流连接：PASSED 跟事务走，
  **WARNING / BLOCKED 用独立池连接写日志**，避免被 `createOrder` 的回滚一起撤销（详见踩坑 027）
- 返回值新增 `logId`，供"人工释放"定位到具体那条拦截记录
- `overrideBlock()` 从死代码变成有 API 调用的活代码

### 3. 信用预警接通知引擎

- `NOTIFICATION_TYPES` / `NOTIFICATION_TYPE_LABELS` 新增 `CREDIT_ALERT`（客户信用超额预警）
- `order/service.js` 新增 `notifyCreditAlert()`：信用检查结果不是 PASSED 时，
  给 finance / op_manager / sys_admin 三个角色发站内信+邮件（渠道走用户偏好 AUTO）
- 同样用 `getPool()` 独立连接发，BLOCKED 回滚也照发
- 通知发送失败只记 `console.error`，不影响下单主流程的报错信息
- `admin/src/pages/Settings.tsx` 的通知事件清单补上 `CREDIT_ALERT`（key 必须和后端一致，踩坑 004）

### 4. 后端 API

| 方法 | 路径 | 权限 | 说明 |
|------|------|------|------|
| GET | `/api/v1/clients/:id/credit-logs` | `client:credit` | 信用检查日志，支持 `result` 筛选和分页，带释放人姓名和订单号 |
| POST | `/api/v1/clients/:id/credit-release` | `client:credit` | 人工释放：日志标 PASSED + 解除客户冻结，原因必填，走变更追踪 |
| PUT | `/api/v1/clients/:id/credit-block` | `client:credit` | 手动冻结 / 解冻，冻结原因必填，同时补一条 `check_point='MANUAL'` 的日志 |

其它后端改动：
- 客户列表新增 `clientLevel` / `creditLevel` 筛选参数；创建和编辑支持 `clientLevel`
- 承运商列表新增 `carrierCategory` / `carrierType` 筛选；创建和编辑支持三个新字段，
  非法值在进 SQL 前挡掉（不让数据库 CHECK 约束的原始报错透给前端）
- 变更追踪白名单：`CLIENT_FIELDS` 加 `client_level` / `credit_blocked`，
  `CARRIER_FIELDS` 加 `carrier_category` / `carrier_type` / `remarks`
- 两个模块的 Excel 导出各自补上新列

### 5. 前端（运营管理端）

| 页面 | 改动 |
|------|------|
| `ClientList.tsx` | 新增「客户等级」列（VIP 琥珀色徽章 + 冻结红标）、等级筛选下拉、新建弹窗加等级选择；列宽 7 列改 8 列重排 |
| `ClientEdit.tsx` | 新增「商务等级」区块（客户等级）；信用区块补「风险类别」下拉（LOW/MEDIUM/HIGH，带敞口口径说明） |
| `ClientDetail.tsx` | 头部加 VIP 徽章和冻结标；基本信息加「客户等级」行；**新增「信用风控」Tab**（按 `client:credit` 权限过滤显示）；`fetchClient` 抽成 `useCallback` 供子组件刷新 |
| `components/ClientCreditPanel.tsx`（新建） | 信用风控面板：额度/敞口/可用额度/风险类别四张卡 + 冻结横幅 + 检查日志表格 + 人工释放 + 冻结/解冻 |
| `CarrierList.tsx` | 新增「分类 / 类型」列（徽章+小字两行）、分类和类型两个筛选下拉、新建弹窗加分类/类型/备注；列宽 7 列改 8 列重排 |

### 牵连到的地方

1. **订单创建流程**：`createOrder` 的信用检查分支多了一次通知发送。
   WARNING 仍然放行（行为不变），BLOCKED 仍然抛错阻止下单（行为不变），
   只是两种情况现在都会给内部发预警、并且日志确定留得下来。
2. **通知偏好**：`notification_preferences` 现在多了一个可配置事件 `CREDIT_ALERT`。
   没配过偏好的用户默认只收站内信（`_resolveChannel` 的系统默认），
   要收邮件得到「系统设置 → 通知设置」里勾上。
3. **变更追踪**：客户和承运商的变更历史里会开始出现新字段的变更行，
   以及 `CREDIT_RELEASE` / `CREDIT_BLOCK` / `CREDIT_UNBLOCK` 三种新的 transactionType。
4. **Excel 导出**：客户导出多「客户等级」列，承运商导出多「分类」「类型」「备注」三列，
   下游如果有人按固定列序解析导出文件需要留意。

### 确认不受影响的边界

- **客户门户 / 承运商门户**：两个门户都没有直接读 `clients` / `carriers` 全字段的接口
  （`client` 和 `carrier` 模块在 P5 已挂 `requireUserType('OPERATOR')`），
  订单相关的 JOIN 全部是显式列，`remarks`（我们对服务商的评价，含"短板"）
  **不会漏给承运商本人**，`client_level` 也不会漏给客户。
- **服务商询价（P6）**：`carrier-inquiry` 模块 JOIN carriers 时取的是显式列，不受影响。
- **权限体系（P5）**：本次没有新增权限码，信用相关全部复用 `client:credit`，
  承运商字段复用 `carrier:edit`，不需要跑权限迁移，Sidebar 菜单映射无变化。
- **报价/询价/财务模块**：没有读写这几个新字段，不受影响。
