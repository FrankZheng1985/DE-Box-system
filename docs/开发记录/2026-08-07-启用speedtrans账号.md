## 三、⚠️ 密码状态：证据是二手的，我无法独立证实

交接文档记载 Frank 已于 **08-03 09:22** 在用户管理页轮换过
`admin` / `siemens` / `speedtrans`（另一对话查 nginx 日志得出）。
按此证据启用是安全的。

但要说清楚一个**我自己造成的取证损失**：`users.updated_at` 本可作为旁证，
而 **2026-08-04 我改绑 `linked_entity_id` 时把它覆盖成了改绑时间**，
所以现在从库里看不出密码何时变过。

> 教训：改存量行时顺手更新 `updated_at`，会**抹掉该行原有的时间线索**。
> 涉及安全相关字段（密码、绑定、启停）的表，排查时别把 `updated_at`
> 当成某一个字段的变更时间——它只记录"最后一次任意改动"。

**如果 08-03 那次设的密码没有存进密码管理器**（`admin` 就发生过这种情况，
后来只能重设），那启用了也登不进去，仍需 Frank 跑：

```bash
cd server && node scripts/reset-user-password.js
```

脚本强制 ≥12 位且三类字符，比页面重置（只要 ≥6 位）更稳。
