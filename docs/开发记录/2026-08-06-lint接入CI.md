# 2026-08-06 · 把四个包的 lint 接进 CI

> 模块：CI/CD
> 背景：三前端 08-04 补了 ESLint、后端 08-06 补了，但 **CI 一个都不跑**。
> 一个只有人想起来才手动执行的检查等于不存在（踩坑 038）。Frank 同意接入。

---

## 一、改了什么

`.github/workflows/deploy.yml` 新增 `Lint All Packages` 步骤，并调整了顺序：

| 步 | 原来 | 现在 |
|---|---|---|
| 3 | 根 `npm install` | 同左 |
| 4 | 构建 admin | **carrier-portal `npm ci`**（从第 6 步提前） |
| 5 | 构建 customer-portal | **Lint 四个包** ← 新增 |
| 6 | carrier-portal `npm ci` + 构建 | 构建三端 |
| 7+ | SSH / 部署 | 同左（编号顺延） |

**为什么把 carrier-portal 的 `npm ci` 提前**：它不在根 workspaces 里，
不先装依赖 lint 就跑不了（踩坑 034 同一个根因）。

**为什么 Lint 放在构建之前**：有问题就在这里停，省掉后面的构建时间，
更重要的是**绝不让不合规的代码碰到生产**——第 9-12 步才是 rsync 和 PM2 重启。

```yaml
- name: Lint All Packages
  run: |
    set -e
    for pkg in server admin customer-portal carrier-portal; do
      echo "──────── lint: $pkg ────────"
      (cd "$pkg" && npm run lint)
    done
```

## 二、验证（重点：**证明这道闸真的会拦人**）

只验"通过"是不够的——踩坑 038 讲的就是"声称存在的校验其实从没生效"。
所以做了**反向测试**：

1. **从干净环境按 CI 确切顺序复现**（worktree 无 node_modules，与 CI 起点一致）：
   根 `npm install` → carrier-portal `npm ci` → lint 循环 → 三端构建，全过。
2. **故意注入违规**：往 `server/core/number-range.js` 末尾加一行 `console.log`，
   原样跑 CI 的 run 块 → **退出码 1，且停在 `server` 就没继续跑后面三个包**，
   证明 `set -e` 确实中断循环、CI 会在此失败。
3. 还原注入，复跑确认干净。

> ⚠️ 中间踩了个自己的坑：第一次做反向测试时把 `npm run lint` 管道给了 `grep`，
> **管道会吃掉退出码**，测出来是 0，差点误判"闸门失效"。
> 验证退出码的测试**绝不能带管道**。

| 项 | 结果 |
|---|---|
| YAML 语法 | 合法，15 个 step，Lint 排第 5（早于全部构建与部署） |
| 四包 lint（干净环境） | 全部退出 0 |
| **注入违规后** | **退出码 1，在 server 处中断** ✔ |
| 三端构建 | 全部成功 |

## 三、影响

- **lint 失败会挡住生产部署**——这正是它的意义。
  真遇到紧急发布被卡住时，正确做法是修掉它，或对那一行加
  `// eslint-disable-next-line <规则名> -- 理由`，
  **不要**删掉这一步或改成 `continue-on-error`（已写进 yml 注释）。
- 当前四个包都是 0 error，接入不会立刻卡住任何人。
- 前端的 35 个 `react-hooks/exhaustive-deps` 是 **warning**，
  lint 脚本已去掉 `--max-warnings 0`，不会挡部署。

## 四、⚠️ 顺带发现：健康检查其实从来不会让 CI 失败

`Health Check`（第十二步）现在是这样：

```bash
if [ "$HTTP_STATUS" = "200" ]; then
  echo "健康检查通过 (HTTP $HTTP_STATUS)"
else
  echo "警告: 健康检查返回 HTTP $HTTP_STATUS（可能服务还在启动中）"
fi
```

**两个分支都不 exit 非 0**，所以哪怕服务起不来，这一步照样绿。
换句话说「CI 全绿」目前**不能证明生产服务是活的**——
这和踩坑 042 说的「CI 状态 ≠ 生产状态」是同一件事的另一面。

改成失败即红是合理的，但要先解决误报：现在只 `sleep 5` 就探活，
PM2 reload 可能还没起来，直接改成阻断会造成大量假失败。
**属独立任务（需要重试+退避），本次未改，先记在这里。**
