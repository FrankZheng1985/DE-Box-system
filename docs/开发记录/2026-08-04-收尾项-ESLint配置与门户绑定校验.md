## 一、本次做了什么

### 1. 三端补 ESLint 配置（原以为只有 carrier-portal 坏）

**实际情况比交接文档记的严重**：`admin` / `customer-portal` / `carrier-portal`
三端**都**缺 `.eslintrc.cjs`，`npm run lint` 从建项目起就直接失败，
一次都没执行过。三端的 lint 脚本和 eslint 依赖倒是一直都在。

补了三份配置，按全局 CLAUDE.md「前端编码规范 · ESLint 规则」：

| 规则 | 取值 | 理由 |
|---|---|---|
| `no-console` | error，放行 `error` / `warn` | 全局规范明文要求 |
| `@typescript-eslint/no-unused-vars` | error，`^_` 前缀豁免 | 全局规范明文要求 |
| `@typescript-eslint/no-explicit-any` | **off** | 规范未要求，存量 120 余处，开了全是噪音 |
| `react-hooks/exhaustive-deps` | warn（来自 recommended） | 见下方"没做的事" |

### 2. 清掉 lint 报出的 25 个错误（纯死代码，不改行为）

- 22 处未使用的 import / 类型 / 局部变量
- `OrderCreate.tsx` 父组件里 5 行重复的 `useMasterDataOptions` 调用
  —— 子组件各自已经拉过一遍，父组件这 5 个结果从未被引用，
  其中 `countryOptions` 还被子组件同名变量遮蔽。
  **实际影响：每次进新建订单页多打 5 个基础数据接口，结果全扔掉。**
- `FinanceDetail.tsx` 的 `const profit = isAR ? null : null` 残留占位

### 3. lint 脚本去掉 `--max-warnings 0`

剩余 35 个警告全是 `react-hooks/exhaustive-deps`。补依赖数组可能引发
无限重渲染，需要逐个页面验证，不适合放在收尾轮里做，保留为提示。

### 4. 登录时校验门户账号绑定的公司是否存在

补上踩坑 035 说过、但**从没实现也无处实现**的防护（详见踩坑 038）。

门户账号（CLIENT / CARRIER）的 `linked_entity_id` 有值但对应公司查不到时，
登录直接拒绝并返回 `BOUND_COMPANY_MISSING`。

**为什么必须在登录拦**：`requireTenantBinding` 只挡"绑定为空"，
挡不住"绑定指向已删除的 ID"。后者让 `WHERE client_id = <悬空UUID>`
永远匹配不到行，接口全部返回 200 + 空数组、控制台零报错——
客户以为"系统里没有我的单子"，运营也查不出毛病。

## 三、关联影响分析

**受影响并已一并处理：**

- 登录接口新增一条拒绝分支 → 客户门户 / 承运商门户的登录页会显示新提示语，
  两端三语语言包已同步补齐（`admin` 是运营端碰不到这条，**故意不加**，
  避免制造无用 key 让 `check:i18n` 产生噪音）。
- `OrderCreate.tsx` 删掉父组件 5 行 hook 调用后，`useMasterDataOptions` 的
  import **仍然需要**（子组件 631-633、898-900 行在用），已确认未误删。
- `InquiryEdit.tsx` 的 `effectiveLdm` 只删了 554 行那次未使用的解构；
  它在 317 / 322 行的另一处**是真在用的**，未动。

**确认不受影响：**

- **开放 API 的第三方合作方不受影响**：新增的是登录接口的拒绝分支，
  开放 API 走的是 API Key 通道，不经过 `/auth/login`。
- **运营端账号不受影响**：新校验只作用于 `user_type IN ('CLIENT','CARRIER')`，
  `OPERATOR` 完全不进这个分支。
- **绑定为空的账号行为不变**：仍然照旧登录成功、由 `requireTenantBinding`
  在调接口时挡下。本次只新增"绑定指向不存在公司"这一种情况的处理。
- **数据库无改动**：本轮没有迁移，编号仍停在 120，下次从 **121** 起。

## 五、本次没做的事（需要 Frank 决定）

### 1. 那两个悬空绑定的账号本身还没处理

`siemens`(CLIENT) / `speedtrans`(CARRIER) 的 `linked_entity_id` 仍指向已删除的公司。
两个账号目前都是**停用**状态，代码层面现在也拦得住了，不影响使用。

要彻底清干净有三条路，**属于数据决策，需要 Frank 拍板**：
- 删掉这两个演示账号
- 改绑到现有公司（`clients` 只有 安百 / 翼能，`carriers` 只有 Eurosped / SGF）
- 保持现状（已停用 + 登录已拦，风险已消除）

### 2. 准时率口径：**建议暂不改**

交接文档提到"业务上是否该用 `expected_delivery_date` 而不是 `delivery_date`"。
查了生产数据：

| 字段 | 29 单里填了的 |
|---|---|
| `delivery_date`（现用） | **1 单** |
| `expected_delivery_date` | **0 单** |

改成 `expected_delivery_date` 会让准时率对所有承运商都显示 "-"。
**真正的问题不是口径选哪个，是这两个日期字段运营基本没在填**——
属于数据录入流程问题，不是代码问题。建议等字段真的有人维护了再谈口径。

### 3. 35 个 `react-hooks/exhaustive-deps` 警告

补依赖数组可能引发无限重渲染，每个都要逐页验证，建议单开任务处理。
