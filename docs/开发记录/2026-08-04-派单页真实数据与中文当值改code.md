## 一、派单页的准时率和覆盖路线：接口根本没查

前端 `MatchedCarrier` 里写着 `on_time_rate` / `covered_routes`，
但 `/carriers/match` 的 SQL 里**根本没有这两个字段**。
于是「历史准时率」永远显示 `-`、「覆盖路线」区块永远不渲染 ——
这两处从写出来那天起就是空的，中文界面下也一样。

### 现在的算法

| 字段 | 口径 |
|---|---|
| 准时率 | 该承运商已送达/已完成、且填了计划送达日的单里，**实际送达日**（`order_status_logs` 里第一条 `DELIVERED`/`COMPLETED` 的日期）不晚于 `orders.delivery_date` 的占比 |
| 覆盖路线 | 跑过的**真实线路**（装货城市 → 卸货城市）按次数取前 5 条 |

覆盖路线**没有新建表**，也没让运营手工维护——直接从历史订单跑出来，
比一张要人维护的路线表更准也更省事。

### 两个诚实处理

1. **样本为 0 时准时率返回 `null`**，界面显示 `-`。
   不给 0%，否则新承运商看起来像「准时率 0%，很差」。
2. **界面把样本量一起显示**成「100%（1 单）」。
   一两单算出来的 100% 不该显得跟几百单一样权威。

NUMERIC 回来是字符串（踩坑 002），颜色阈值判断加了 `Number()`。

### 生产实测

```
Eurosped | 样本 0  | 准时率 null | 路线 (无)
SGF      | 样本 1  | 准时率 100.0 | 路线 lunen → madrid
```

## 二、「中文当值」改成存 code

`103_master_data_seed.sql` 里专门写了注释，说特殊要求存 `name_zh` 是
**刻意**与前端硬编码对齐的。这个决定带来三个问题：

1. 运营在「基础数据维护」里改一次中文名，历史订单里的值就成了孤儿
2. 开放 API 的合作方得推中文过来，对外接口很别扭
3. 前端语言包只能拿中文当 key（`specialRequirement.<中文>`），很脆

### 2.1 特殊要求（迁移 120，动了 28 行存量）

映射**从库里现查**不写死 —— 生产的 `md_special_requirements` 运营已经改过，
加了「危险品」「UN3480电池」这些种子文件里没有的行。

干跑（事务里执行后 ROLLBACK）确认后才真跑：

| 原值 | 新值 | 行数 |
|---|---|---|
| 危险品 | `DG` | 23 |
| 无 | `NONE` | 4 |
| 超宽超重 | `OVERSIZE` | 1 |

换不掉的 0 行、迁移后非 code 残留 0 行。

配套改动：
- options 接口 `special-requirements` 的 `value` 从 `name_zh` → `code`
- `OrderEdit` 里硬编码的中文值数组删掉，改从基础数据接口取
- `OrderCreate` 默认值 `'无'` → `'NONE'`；`OrderDetail` 按 code 查语言包
- 语言包 `specialRequirement.*` 从中文 key 改成 code key

### 2.2 ⚠️ 开放 API 的合作方不用改

新增 `normalizeSpecialRequirement()`，入库前归一。生产实测：

```
"危险品"          → "DG"
"Dangerous Goods" → "DG"
"DG" / "dg"       → "DG"
"温控运输"        → "TEMP_CONTROL"
"合作方自己编的值" → "合作方自己编的值"   ← 认不出来的原样保留
""                → null
```

**认不出来就原样存是刻意的**：合作方的业务信息不能因为我们的字典没收录就丢掉。

### 2.3 清关文件类型（零风险）

`customs_documents` 生产是**空表**，不需要数据迁移。
5 个中文值直接换成 `CUSTOMS_DECLARATION` / `COMMERCIAL_INVOICE` /
`PACKING_LIST` / `CERTIFICATE_OF_ORIGIN` / `OTHER`，
语言包 `customsDocType.*` 一并改成按 code 索引。
