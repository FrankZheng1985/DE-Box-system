## 一、做了什么

### 1. 订单新增「客户单号」customer_ref

客户报单、对账说的都是**他们自己的单号**。询价表 2026-07 就有 `inquiries.customer_ref`，
订单一直没有，导致「询价阶段能按客户单号对上，转成订单后就对不上了」。

**为什么不复用已有的 `orders.external_ref`**：那是开放 API（P8）给外部系统对接用的，
和 `external_source` 一起有唯一约束 `uq_orders_external`，客户手填的单号塞进去会撞约束，
也会污染 API 侧语义。

**刻意不加唯一约束**：一票货分两个柜、分批出运时，同一个客户单号对应多张订单是正常业务。

覆盖范围（Frank 逐项确认过）：
- 三个产品的导入模板都加这一列（第一列，选填，最长 100 字符）
- 两端建单表单都加输入框（客户门户在「基本信息」区块，管理端在客户旁边）
- 订单列表显示 + **搜索框可搜**
- 订单详情页标题下显示
- 订单 Excel 导出、财务应收/应付导出都带这一列
- CMR 管理页（两端）列表显示

### 2. 集装箱单（FTL）新增「提柜地点」

FTL 单此前只有目的地侧，默认从卸货港提柜。现在可以指定堆场或客户自有仓库：
- 导入模板加 6 列（装货国家/邮编/城市/地址/联系人/电话），**整组选填**
- 客户门户与管理端的 FTL 表单各加一个「提柜地点（选填）」区块
- 留空 → `pickup_address` 落 NULL，表示按常规从卸货港提柜

### 3. 顺带修掉的三处

- **列表路线显示**：集装箱单的两头本该是「卸货港 → 最终目的地」，两端列表却一直读装卸货城市。
  以前 FTL 单装卸货地址都空，显示「- → -」不明显；加了提柜地点后变成「Hamburg → -」，
  看着像目的地丢了。改成按产品取值（列表接口相应带出 `pod` / `final_destination`）。
- **搜索框文案骗人**：三个搜索框都写着「搜索…客户…」，但后端 SQL 从来没有按客户名搜。
  后端补上 `c.company_name ILIKE`，文案同步改为实际支持的字段。
- **空串写进 JSONB**：两端建单页把没填的地址字段以 `''` 存进 `pickup_address`，
  `pickup_address->>'zipCode'` 拿到的是空串而不是 NULL。改为只写填了值的字段
  （踩坑 047 防护第 3 条自己踩了一次）。
- **提柜城市与卸货港占位符撞车**：两处都写「如：Hamburg」，实测填表时容易填错行。
  提柜地点区块改用专属占位符（「如：Hamburg（提柜城市）」「堆场 / 仓库名称、街道门牌」）。
