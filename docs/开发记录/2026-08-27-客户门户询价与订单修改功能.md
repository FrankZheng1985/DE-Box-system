## 需求原文

> **现状描述**：在尚未获得报价前，无法手动修改询价订单的基本信息。
> **期望效果**：客户端已经建立的询价单和订单，增加一个修改的按钮，这样子当询价单或订单的
> 基本信息（如尺寸重量，地址，国家等）有变化的时候可以直接在原基础上修改。不用重新建立
> 询价单或订单。当然，所有的信息可以修改的前提是还没有获得报价，如果获得报价了，就要提醒
> 客户端，此订单已经提供报价，如果需要继续操作，就要重新变成待报价状态。

## 两处业务口径（Frank 2026-08-27 拍板）

| 问题 | 决定 |
|------|------|
| 订单侧「可以改」的边界 | **只有「待审核」（PENDING_REVIEW）可改** —— 我司尚未受理。一旦确认/派车就只能联系运营 |
| 已报价的询价怎么改 | **作废原报价 + 询价退回待报价**，历史版本与金额全部保留可追溯 |

「未获得报价」这个说法在订单上几乎不成立（订单多数是报价被接受后转过来的、本来就有价），
所以订单侧换成了状态口径。

## 做了什么

### 后端

**1. 询价退回待报价（新端点）**

`POST /api/v1/inquiries/:id/reopen`，运营与客户门户共用
（`inquiry:edit` / `portal:inquiry_manage`，无新权限码）。

逻辑抽在 `inquiryService.reopenForEdit()` 而不是写在路由体内 ——
这是一次**逆向状态流转**，是本次最该被验证的一段，抽出来才能脱开 HTTP 和登录态直接测。

- 状态守卫：只有 `QUOTED` 能退回。`ACCEPTED`（已转订单）、`REJECTED`、`CANCELLED` 一律拒绝
- 报价侧：`SELECT ... FOR UPDATE` 行锁 → 有 `ACCEPTED`/`CONVERTED` 的报价就**整单拒绝并回滚**
  （它们背后挂着订单）；其余在途报价置 `CANCELLED` + `void_reason`，口径与
  `POST /quotations/:id/void` 完全一致
- 询价状态回 `PENDING_QUOTE`，询价与每张报价都写 `changeTracker` 留痕

**2. 客户改订单（新端点 + 新权限码）**

`PUT /api/v1/orders/:id/basic-info`，`requireUserType('CLIENT')` +
`requirePermission('portal:order_edit')`（**迁移 134 新增**）。

**为什么另开端点而不是放开 `PUT /orders/:id`**：后者的语义是「运营编辑订单」，
它的 fieldMap 里有 `clientPrice`。放开给客户等于以后任何人往那个 fieldMap 里加字段，
都默默地把这个字段也交给了客户 —— 正是踩坑 069 的成因（加字段的人不会想到还有另一类调用方）。

三道守卫：① 不是自己家的单回 404（不回 403）；② 状态必须 `PENDING_REVIEW`；
③ 字段白名单 `CLIENT_EDITABLE_FIELDS`（**金额、状态、承运商、服务类型都不在里面**）。

**3. `editOrder` 支持地址字段**

原本的 fieldMap 没有 `pickupAddress` / `deliveryAddress`，而苏凌明确要求能改地址和国家。
补上两个键，并按 `model.create` 的口径 `JSON.stringify` 后再进 SQL；
`ORDER_TRACKED_FIELDS` 一并补两条，改地址才会进变更明细。运营端编辑页也一并受益。

### 前端

| 页面 | 路由 | 说明 |
|------|------|------|
| 修改询价单 | `/customer/inquiry/:id/edit` | 两层结构（卡派/整柜）与三层结构（本地派送一柜 N 票）各一套 |
| 修改订单 | `/customer/orders/:id/edit` | 地址、货物、日期、集装箱信息；**没有金额输入框** |

入口都在详情页右上角：询价单 `PENDING_QUOTE`/`QUOTED` 时显示「修改」；
订单 `PENDING_REVIEW` 且账号有 `portal:order_edit` 时显示。

已报价的询价点进编辑页会看到一条琥珀色提示条，说明「继续修改会作废在途报价并退回待报价」，
**点了确认按钮、退回成功之后表单才解锁** —— 能填却存不进去比直接不给填更让人恼火。

**服务类型故意不给改**（询价、订单都是）：换类型等于换业务线和计价基础，
两层与三层结构的表单也整个不一样，要换请新建。

## 关联影响分析

**一并改了的：**
- `editOrder` 是运营端 `PUT /orders/:id` 和门户新端点共用的，补地址字段后**运营端也能改地址了**。
  运营端的 OrderEdit 页面目前不发这两个字段，所以行为不变；将来要开放只需前端加输入框。
- 地址卡片从 InquiryList 抽成组件，**InquiryList 的渲染结果一字未变**（原样搬过去，
  只多了一个默认 true 的 `showEmail` 开关），tsc/lint/build 全过。

**确认不受影响的：**
- 运营端改订单仍走 `PUT /orders/:id` + `order:edit`，**守卫和字段范围一个都没动**。
- 承运商门户完全不涉及：两个新端点一个限 `CLIENT`、一个限运营+客户。
- 报价模块的 `POST /quotations/:id/void` 没动；新代码只是复用了它的作废口径
  （`status='CANCELLED'` + `void_reason`），两边将来要改得一起改。
- 迁移 134 是 additive 的，**不跑也不会 500** —— 没人有 `portal:order_edit`，
  按钮不显示、端点回 403，功能不可用而已。这和踩坑 063 那次「代码要新列而列不存在」不同。

**没做的：**
- **不发系统通知给运营。** `NOTIFICATION_TYPES` 里没有合适的类型，新增一个要连带改
  通知设置页、三语标签、邮件模板，范围太大。目前靠询价列表的状态徽章变色 +
  报价时效列变回「已等待 X 天」作为信号。上线后看运营反馈再决定要不要补。
- 询价编辑页**不能改服务类型**，订单编辑页同理（见上）。

## 🚨 上线顺序（不能反）

```bash
# 1. 结构变更前先备份（134 虽然只加数据不改结构，但按规矩照做）
ssh eu-tms "cd /var/www/germany-box-system/server && export \$(grep '^DATABASE_URL' .env | xargs) \
  && pg_dump \"\$DATABASE_URL\" | gzip > /var/backups/germany-box-db/germany_box_transport_\$(date +%Y%m%d_%H%M%S).sql.gz"

# 2. 跑迁移 134
ssh eu-tms "cd /var/www/germany-box-system/server && export \$(grep '^DATABASE_URL' .env | xargs) \
  && psql \"\$DATABASE_URL\" -f database/migrations/134_portal_order_edit_permission.sql"

# 3. 确认权限码到位
ssh eu-tms "cd /var/www/germany-box-system/server && export \$(grep '^DATABASE_URL' .env | xargs) \
  && psql \"\$DATABASE_URL\" -c \"select perm_code from permissions where perm_code='portal:order_edit'\""

# 4. 再 push（push main = 立刻上生产）
```

⚠️ 迁移文件是靠 CI 的 rsync 传上服务器的，所以第 2 步要跑的那份文件，
**得先有一次 push 把它传上去** —— 或者用 scp 单独传这一个 sql 文件上去再跑。
本次采用：**先 scp 迁移文件 → 跑迁移 → 再 push 代码**，避免「代码先到、权限码没有」的空窗。
