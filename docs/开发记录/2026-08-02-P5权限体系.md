## 🎯 目标

1. **员工分权**：细粒度权限码方案（permissions + role_permissions + `requirePermission` 中间件），8 个已 seed 的角色真正产生差别。
2. **前端守卫**：Sidebar 按权限过滤菜单、路由守卫、页面内敏感按钮按权限隐藏。
3. **堵安全漏洞**：client/carrier 模块当前只挂 `authenticateToken`，CLIENT/CARRIER 账号能读写全部主数据。
4. **客户多账号**：client_admin 可管理本公司子账号（新建/停用/角色分配），client_user 受限。

## 🧠 关键决策（Frank 2026-08-02 拍板）

| 决策 | 结论 | 理由 |
|------|------|------|
| 权限粒度 | **细粒度权限码**（不用角色白名单简化版） | P6 服务商询价的信息隔离、以后加岗位都能直接受益，不用改代码重新部署 |
| 客户门户子账号 | **本阶段一起做** | 计划内范围 |
| 弃用 `auth_objects`/`auth_values` | 保留表不动，但不再扩展；新建 permissions/role_permissions | V2 那套 15 个 auth_objects 已 seed 但 auth_values 空表、无任何中间件消费，救活成本高于新建 |
| 权限数据从哪来 | JWT 只带 `roleId`/`roleCode`，权限码由后端按 role_id 查表 + 内存缓存 | 权限码约 50 个，塞进 JWT 会让 token 很大；且改权限后必须重新登录才生效，体验差。缓存做成改权限时主动失效 |
| 迁移号 | **109** | 开工时误以为 P2/P3/P4 未做，实际它们已由别的对话上线（106/107/108 已占用），本次顺延到 109 |
| 敏感字段用组合权限 | 编辑客户放行 `client:edit` **或** `client:credit`，改哪些字段在处理函数里按字段判 | 财务岗需要维护信用额度但不该改公司资料；只挂 `client:edit` 会让财务的 `client:credit` 形同虚设（冒烟测试实测撞到） |
| 租户过滤失效方向 | 新增 `requireTenantBinding` 中间件，门户账号未绑定公司直接 403 | 各模块的过滤条件写成 `if (linkedEntityId) 才加`，绑定为空时不过滤 = 返回全部数据。生产验证时发现的，见踩坑 023 防护规则第 2 条 |
| 订单/清关/GPS/财务的租户隔离 | 本次一并修 | 探查中发现这些接口的 `clientId`/`carrierId` 取自 query 参数，客户门户账号换个参数就能看别家数据。属于同一类漏洞，不修的话权限体系是纸糊的 |

## ⚠️ 坑 / 注意

1. **`UserManagement.tsx:178,210` 有存量 bug**：提交时写 `Number(form.role_id)`，但 `roles.id` 是 UUID → `Number()` 得 NaN → JSON 序列化成 `null` → **给员工分配角色一直没真正存进去**。权限体系依赖 role_id，必须先修这个。
2. `requireUserType` 里有 `userType === 'OPERATOR'` 无条件放行的分支——细粒度权限上线后要重新审视，否则任何运营账号仍然全放行。
3. 角色码是 `sys_admin` 不是 `admin`，前端 `AuthContext.isAdmin()` 判错了。
4. 迁移 100 开头 `DROP TABLE ... permissions, role_permissions CASCADE`——重跑 100 会毁掉本次新表。生产不会重跑，但本地重建库时要注意先跑 100 再跑 106。

## 🔗 关联影响清单

1. **所有登录账号的可见范围都会变**。上线后 op_staff 看不到财务菜单、看不到信用额度；
   client_user 看不到账单和账号管理；carrier_driver 看不到费用结算。**这是需求 9 要的效果，但要提前知会使用的人。**
2. **存量账号的角色**：迁移末尾把 `role_id IS NULL` 的账号按端别兜底成 op_staff / client_user / carrier_driver。
   如果生产上有本该是财务或经理的账号（因为 UUID bug 一直没存上角色），
   **上线后必须去用户管理页重新指定角色**，否则他们会按运营专员的权限运行。
3. **`GET /api/v1/orders/stats` 收成运营专用**：两个门户如果以后要用，得走 `/dashboard/client` 或 `/dashboard/carrier`。
   已确认当前两个门户都没调它。
4. **`GET /api/v1/system/settings` 收成运营专用**：确认两个门户只调 `/system/settings/account`（自己的资料），不受影响。
5. **`auth_objects` / `auth_values` 两张表保持原样**，登录接口仍返回 `authObjects` 字段，
   前端 `hasAuth` 系列也保留——避免动到别处。但**新代码一律用 `hasPermission`**，
   `hasAuth` 系列后续可以清理（本次未动）。
6. **PM2 多进程下缓存各一份**：改完角色权限，当前进程立即生效，另一个进程最迟 60 秒。
   部署时按规范 `pm2 delete all` 再 `pm2 start`，不会有旧缓存残留。
7. **确认不受影响**：报价确认链接（`/quotation-response/:token`，免登录）没挂任何权限中间件，
   邮件里的三个确认链接照常可用；官网留言接口 `POST /contact` 也没挂（本来就是匿名提交）。
