## 四、关联影响分析

### 通知引擎行为变化（影响所有调用 `notify()` 的模块）

`notify()` 的**签名和调用方式没有变**，现有调用点（order/service.js、cmr、customs、
shipping-release 等）无需改动。但内部行为有三点变化：

1. **`channel='BOTH'` 时从写两行变成写一行。**
   原来会额外写一条 `type='EMAIL_xxx'`、`title='[邮件] xxx'` 的记录，
   用户在通知列表里看到重复条目。现在合并为一行。
   → 影响 `GET /notifications` 列表和未读数，数量会变少（这是修复，不是回归）。
   → 生产库里的历史 `EMAIL_*` 记录保持原样不动，不做清理。
2. **用户没有邮箱时自动退回 SYSTEM 渠道**并打 warning 日志，不再静默丢弃。
3. **`userIds` 会去重并过滤空值**，重复传同一个用户不会写多行。

### 定时任务

- 资质到期提醒 → 通知 `sys_admin` + `op_manager` 角色（原来 `targetRole: 'ADMIN'` 无实际效果）
- 逾期催款 → 通知 `finance` + `sys_admin` 角色（原来 `targetRole: 'FINANCE'` 无实际效果）
- 事件类型收敛到既有 11 个常量：`QUALIFICATION_EXPIRY` → `QUALIFICATION_EXPIRING`，
  `OVERDUE_PAYMENT` → `INVOICE_DUE`，**没有新增第 12 个类型**，保证设置页的清单完整覆盖。
- 新增每 2 分钟的邮件队列轮询任务。

### 自动开票账期

`clients.payment_terms` 从此真正生效：订单完成时应收到期日 = 完成日 + 客户账期。
**承运商应付仍固定 30 天**——`carriers` 表没有账期字段，本次不加（属 P7 承运商改造范围）。

→ 联动：逾期催款 cron 依赖 `due_date`，账期改对之后逾期判定才准确。
→ 客户 `payment_terms` 现在可以在客户编辑页正确保存（原来保存就报错），两处配套才闭环。

### 前端

- **ClientList**：信用等级和应收余额从"永远显示 `-` 和 €0.00"变成显示真实值。
  应收余额取后端 `SUM(amount - paid_amount)`，只统计 `RECEIVABLE` 且未付清的记录。
- **ClientEdit**：老数据里如果有 `payment_terms` 存成非数字的脏值，下拉会显示"请选择"，
  需要重新选一次再保存。（已确认 `clients.payment_terms` 是 INTEGER 列，
  存不进字符串，所以生产库里不会有脏值——这条只针对可能被手工改过的本地库。）
- **customer-portal CreateOrder**：表单字段从 2 个增加到 8 个，
  客户下单需要填的信息变多，但这是后端建单本来就要求的（admin 端一直是这样）。
  原来填的地址**根本没存进库**，运营看到的是空地址。

### 确认不受影响的边界

- **carrier-portal**：本次完全没有改动。
- **财务模块**：只有 `due_date` 的计算方式变了，`financial_records` 表结构和其他字段未动；
  已存在的财务记录不会被回溯修改。
- **ERP 内核其他引擎**（document-engine / credit-manager / posting-period 等）：未改动。
  `core/` 仍然不依赖 `utils/`，发信逻辑放在 `utils/email-queue.js`，架构分层没有破坏。
- **订单状态机**：未改动，`updateStatus` 的流转规则原样保留。
- **CMR / 清关 / 放单模块**：调用 `notify()` 的方式不变，只是通知行数从 2 行变 1 行。
