## 二、#23 部分报价的设计（Frank 2026-09-28 定：客户能看，但要全部报完才能接受）

**不改表结构**：「这一票没有报价行」= 未报价；填 0 = 免费送。两者严格分开。

| 环节 | 行为 |
|---|---|
| 管理端填价 | 空着 = 暂不报价（占位符「暂不报价」）；至少填一票才能保存 |
| 后端写入 | `replaceDeliveryLines` 跳过空价，不再按 0 兜底；一票都没填直接报错 |
| 发送 | 部分报价**不发**带「同意报价」按钮的确认邮件（发了客户点同意也只会报错），运营提示里说明原因 |
| 补价 | 管理端「已发送」的部分报价出现「补充报价」按钮 → 编辑页只有「保存修改」；**补全的那一刻自动补发一次确认邮件**，之后再改价不重复发 |
| 接受 / 转单 | `createOrderFromQuotation` 里拦截：还有未报价的票就抛错。门户接受、邮件链接接受、运营手工转单都走这个函数，一处拦三条路 |
| 列表 | 两端都加「报价进度」列：全部报价（绿）/ 部分报价 x/y（黄）；卡派 / 卡车显示「-」 |
| 客户门户 | 部分报价不显示「接受」，显示「等全部报价」；详情弹窗里未报的票显示「待报价」，合计写「已报合计」 |

### 顺带修掉的 bug
- **管理端编辑本地派送报价时，派送票和已报价格根本不加载**（编辑模式只拉了报价详情，没拉询价的派送票），
  逐票报价整块不显示、提交也不带逐票行。放开部分报价后「回头补价」必须走编辑，所以一并修了。
- 发送报价后，前端把后端「邮件没发出去」的原因（部分报价 / 客户无邮箱）丢掉了，只显示「发送成功」。现在原样显示。
- 客户门户「我的报价」操作列在英语 / 德语下按钮会挤出格子（原有问题），放宽列宽并允许换行。

## 四、关联影响

- **数据库**：无结构变更、无迁移。
- **邮件**：部分报价发送时不再发确认邮件；补全后自动发一次。全部报价的报价行为与以前一致。
- **老数据**：以前前端要求每票必填、后端空价按 0 写，所以老的本地派送报价每票都有报价行，不会被当成部分报价。
  唯一例外是「报价之后询价又加了派送票」的老报价——现在会被判为部分报价、不能接受（以前会按 0 元建单）。
  生产上有没有这种单**未核实**，上线后可用下面这句查：
  ```sql
  SELECT q.quotation_number, q.status,
         (SELECT count(*) FROM inquiry_delivery_orders d WHERE d.inquiry_id = q.inquiry_id) AS drops,
         (SELECT count(*) FROM quotation_delivery_lines l WHERE l.quotation_id = q.id)     AS priced
  FROM quotations q
  WHERE q.business_type = 'LOCAL_DELIVERY' AND q.status IN ('SENT','PENDING_DECISION');
  ```
- **开放 API**：未改动（询价推送本来就要求预计到仓）。
- **确认不受影响**：卡派 LTL / 卡车 FTL 的报价、转单流程（没有派送票，不进部分报价逻辑）；新版本报价复制逐票行（复制的都是有值的价格）。

## 六、注意事项

- **主工作区 `server/node_modules` 是空的**，根 `node_modules` 里也没有 express；worktree 里要单独装后端依赖。
  `server/package-lock.json` 与 `package.json` 不同步（缺 `ali-oss`），`npm ci` 会失败，需用 `npm install`。
  另外在 `server/` 里直接跑 `npm ci` 会被 npm 当成整个 workspace 的安装，把根目录依赖冲掉——要在隔离目录装好再移进来。
- 模板「示例」页里卡派示例行的「柜号」「预计到仓日期」是空的，但这两列是必填，照示例填会报错（未改，另提）。
