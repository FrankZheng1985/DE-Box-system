## 功能说明

合作方配一个接收地址，我方在状态变化时主动 POST 通知，省去轮询。

| 事件 | 触发 |
|------|------|
| `ORDER_STATUS_CHANGED` | API 来源订单的状态变更 |
| `INQUIRY_QUOTED` | API 来源询价的报价已发送 |
| `QUOTATION_DECISION` | 该报价被接受（转订单）或拒绝 |

**Outbox 模式，完全不侵入业务模块**：不在 order/quotation 的写路径上插钩子，而是每分钟
增量扫 `order_status_logs` / `quotations.updated_at` 入队，再由分发器投递。好处是业务代码
零改动、漏推可靠（游标回看 120 秒 + 唯一约束去重）、失败重试不影响主流程。

- **签名**：`X-EUTMS-Signature: t=<unix秒>,v1=<HMAC-SHA256(secret, "t.rawBody")>`（Stripe 风格）
- **重试**：2xx 即成功；失败按 1m/5m/30m/2h/6h 退避共 5 次，耗尽判 FAILED
- **双实例安全**（PM2 -i 2）：入队靠 `UNIQUE(api_key_id, event_type, dedupe_key)` + ON CONFLICT DO NOTHING；投递靠 `FOR UPDATE SKIP LOCKED` 领取（与 email-queue.js 同一套路）
- **成本不外泄**：报价扫描点名列查询，carrier_cost 进不了载荷（踩坑 026，冒烟有回归断言）

## 关键设计决定

1. **webhook_secret 明文存储**，与 API Key 只存哈希不同：HMAC 签名要求服务端持有原文。
   风险可接受——该密钥只能伪造通知，不能调用接口；admin 页面刻意允许查看（运营要交给合作方）。
2. **去重用普通唯一约束而非部分索引**，这样 `ON CONFLICT (…) DO NOTHING` 能直接推断（踩坑 020）。
3. **游标回看 120 秒**：两实例并发写游标有竞态，宁可重复扫描（唯一约束挡住）也不漏事件。
4. **报价去重键 = 报价UUID:状态**：同一版报价改金额重发不会重复推事件（保守），
   合作方可用回查接口拿最新金额。
5. **迁移播种游标为 NOW()**：上线不回灌历史事件，避免给合作方灌一堆陈年状态。

## 关联影响分析

1. **业务模块零改动**：order/quotation/inquiry 的代码一行没动，这是选 outbox 的主要理由。
2. **新增每分钟 cron**：无合作方配 Webhook 时首查即返回（`LIMIT 1` 探测），不空转扫描。
3. **api_keys 加两列**（可空）：现有点名列 INSERT 不受影响；KEY_COLUMNS 显式加入两列，key_hash 仍永不外泄。
4. **前端**：OpenApiManagement.tsx 增至 **892 行，超过 800 行红灯线**——见下方遗留。
5. **确认不受影响**：对外推送/回查端点、/api/v1 全部路由、其他 4 个 cron 任务均未改动。
