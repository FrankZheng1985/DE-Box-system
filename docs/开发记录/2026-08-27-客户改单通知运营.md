# 2026-08-27 客户改单通知运营（开发意见 #12 收尾）

## 背景

意见 #12（客户门户自助修改询价/订单）在 d809cf2 上线时留了一个尾巴：
客户在门户里改了单子，运营端毫无感知——尤其是「已报价询价退回待报价」这条路径，
运营辛苦做的报价被作废了都不知道，等客户催的时候才发现要重新报。

本次给三条客户改单路径补上运营侧站内通知，全部复用现有通知引擎，
不加新表、不加迁移、不加通知类型。

## 通知规则

| 触发路径 | 谁触发才发 | 通知内容 |
|---------|-----------|---------|
| `PUT /inquiries/:id`（编辑待报价询价） | 仅 CLIENT（运营自己编辑不通知） | 客户 X 修改了询价单 N，请以最新内容为准 |
| `POST /inquiries/:id/reopen`（已报价退回） | 仅 CLIENT | 客户 X 正在修改询价单 N，已退回待报价，M 张在途报价已作废 |
| `PUT /orders/:id/basic-info`（改订单基本信息） | 端点本身仅 CLIENT 可用 | 客户 X 修改了订单 N 的基本信息，请在审核时以最新内容为准 |

- **收件人**：全体在职运营（`user_type='OPERATOR' AND is_active`），与「新订单」「批量导入」通知同口径
- **类型**：复用 `NOTIFICATION_TYPES.STATUS_UPDATE`，不新增类型（新增类型要动偏好设置页，本次不需要）
- **时机**：事务提交之后、用独立连接发；发送失败只 `console.warn`，
  绝不抛回前端——单子已经改成功了，报错会让客户以为失败再提交一遍（与批量导入汇总通知同套路）
- **措辞**：reopen 的通知不说「请重新报价」——此刻客户还没改完内容，改完保存会再发一条编辑通知
- **三语**：titleKey/messageKey 走 P9 语言包机制，zh/en/de 各补 6 个 key

## 关联影响

- **不受影响**：通知引擎、邮件队列、通知偏好——只是新增调用点，未动引擎代码；
  三处通知都在事务外发送，主流程行为（改单/退回/作废）与 d809cf2 完全一致
- **邮件渠道**：operators 无 notification_preferences 行时渠道解析为 SYSTEM（仅站内信）；
  若将来有运营把 STATUS_UPDATE 设为邮件渠道，这些通知会自动跟着走邮件队列，无需改代码
- **运营端 UI**：站内信铃铛是现成组件，无前端改动；询价类通知无 related_order_id（表列是订单外键），点击不跳转，属预期
- **无迁移**：上线只需部署代码

## 遗留边界（本次刻意不做）

- 客户**删除**询价（DELETE /inquiries/:id）不通知——守卫保证只有「运营完全没动过」的单能删，通知价值低
- 客户**新建**询价也没有运营通知（历史如此，不属于 #12 范围），要做另立需求
