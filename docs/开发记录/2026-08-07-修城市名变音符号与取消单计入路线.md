# 2026-08-07 · 修派单页路线匹配的两个缺陷

> 模块：承运商 `/match`
> 来源：在生产上真点了一遍派单页发现的（数据层测试全绿，UI 一眼看穿）

---

## 一、怎么发现的

为验证「承运商接单提示条」，在生产建了一张测试单 `EU-20260807-0003`
（Lünen → Madrid），走完全流程时看见：

**Eurosped 卡片显示着「覆盖路线 LUNEN → MADRID」，可我做的绿色
「跑过这条线」标记就是不亮**——而本单正是 Lünen → Madrid。

## 二、缺陷 1：归一化漏了变音符号

```
lower('Lünen') = 'lünen'
lower('LUNEN') = 'lunen'   ← ü ≠ u，永远不相等
```

昨天写这个匹配时只做了大小写和空格归一。**在德国业务里
München / Köln / Düsseldorf 全是这个毛病，这个匹配基本等于废的。**

### 为什么昨天的测试没发现

**我测的时候用的是 `lunen`——和库里存的一模一样。**
拿"和数据库长得一样"的值去测字符串匹配，测的是"相等的东西相等"，
什么也没验证。详见踩坑 053。

### 改法

不用 `unaccent` 扩展（生产 RDS 没装，装扩展要库级权限），
用内置的 `translate()`：

```js
function normCity(expr) {
  return `TRANSLATE(LOWER(TRIM(REPLACE(${expr}, 'ß', 'ss'))), ` +
    `'áàâãäåéèêëíìîïóòôõöøúùûüñçý', ` +
    `'aaaaaaeeeeiiiioooooouuuuncy')`
}
```

- `ß` 先单独 `replace`：`translate()` 是 1:1 映射，做不了 `ß→ss`
- **两个串各 27 字符，长度必须相等**——不等时 `translate()` 不报错，
  会静默吞掉多余字符（写完数了一遍确认）

## 三、缺陷 2：取消的单被算作"跑过这条线"

测试单取消之后，SGF 仍然显示"跑过 Lünen → Madrid"。

查出 `route_hits` 和 `covered_routes` **都只过滤了 `carrier_id IS NOT NULL`**，
没排除已取消/已拒绝的订单——**虚报承运商的线路经验，会误导运营派单**。

两处都加上：

```sql
AND o.status NOT IN ('CANCELLED', 'REJECTED')
```

## 四、验证（生产库实跑）

归一化本身：

| 输入 | 输出 |
|---|---|
| `Lünen` / `LUNEN` | 同为 `lunen` ✔ |
| `München` | `munchen` |
| `Köln` | `koln` |
| `Straße` | `strasse` |

完整查询三种参数组合：

| 用例 | 结果 |
|---|---|
| 带变音 `Lünen→Madrid` | Eurosped 命中并排第一 ✔ |
| 不带变音 `LUNEN→MADRID` | **与上一行结果完全一致** ✔ |
| 不传参数 | 无人命中，只显示历史覆盖路线（行为不变）✔ |
| SGF 的覆盖路线 | 回到 `[]`，取消的测试单不再计入 ✔ |

其他：四包 lint 全部退出 0；`carrier/routes.js` 实际 `import()` 加载成功。

## 六、关联影响

- **只动了 `/match` 一个接口**，派单页前端未改。
- 不传筛选参数时行为不变。
- **确认不受影响**：`/carriers` 列表、导出、承运商门户均未触碰。
- 准时率计算（`delivered` / `ontime` 两个 CTE）**本次没动**——
  它已经限定了 `DELIVERED/COMPLETED` 状态，本来就不含取消单。
