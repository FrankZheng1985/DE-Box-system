# 2026-08-07 · 三端 SPA 缓存策略修复（nginx）

**模块**：运维 / nginx

## 问题

前端部署后，用户浏览器仍在跑**缓存的旧 index.html**，去请求上一版的 chunk；
而部署规范里的 `rm -rf dist/assets/*` 已把旧 chunk 删了，SPA 兜底又返回 index.html
冒充 JS，于是报「MIME type text/html」白屏。

根因：`location /` 没有 `Cache-Control`，index.html 走 nginx 默认的启发式缓存。
**每次部署都会咬一批人**，不是本次特有。详见
`docs/踩坑经验库/060_SPA的index.html没设no-cache导致每次部署都白屏一批人.md`。

## 修改文件

| 文件 | 操作 | 说明 |
|---|---|---|
| `deploy/nginx-eutms-app.conf` | 修改 | 三端各加一个 `assets` location（`immutable` 长缓存、**不配 try_files**），三端 SPA 主 location 加 `no-cache` |
| `docs/踩坑经验库/060_*.md` | 新增 | 踩坑记录 |

线上同步：scp 到 `/etc/nginx/snippets/eutms-app.conf` → `nginx -t` → `systemctl reload nginx`。
线上备份 `eutms-app.conf.bak-20260807-222834`。

## 改前 / 改后对照（实测 curl）

| 路径 | 改前 | 改后 |
|---|---|---|
| `/dashboard`、`/carriers` | 无 Cache-Control | `no-cache` |
| `/impressum.html` 等不带 hash 的文件 | 无 Cache-Control | `no-cache` |
| `/assets/index-*.js` | 无 Cache-Control | `public, max-age=31536000, immutable` |
| `/customer/`、`/carrier/` | 无 Cache-Control | `no-cache` |
| `/customer/assets/*`、`/carrier/assets/*` | 无 Cache-Control | `immutable` |
| 已删除的旧 chunk | **200 + text/html**（冒充 JS） | **404**（老实报错） |
| `/`（官网） | 已有 `no-cache` | 不变 |

## 回归验证（全部实测通过）

- `/admin/` → 301 `/dashboard` ✅
- `/carrier`、`/customer` 裸路径 → 301 带斜杠版本 ✅
- 官网首页仍是 homepage（title `KALUNA SPED - Europäische Transportlösungen`）✅
- `/api/v1/auth/login` 正常响应 ✅
- `/dashboard` 带 `If-None-Match` → **304** ✅（证明 no-cache 只是协商，不是每次重传）

## 关联影响

- **对用户**：本次改动上线后，**老用户还需要硬刷新一次**才能拿到带 no-cache 头的
  新 index.html；从那以后不用再刷。
- **对部署流程**：`rm -rf dist/assets/*` 可以继续用了（旧 chunk 缺失现在是干净的 404，
  且不会再有人拿着旧 index.html 去要它）。
- **确认不受影响**：后端 API、三端路由 301、官网、安全响应头（每个 location 都保留了
  `include snippets/eutms-security-headers.conf`——nginx 里子 location 一旦有自己的
  `add_header` 就不继承父级，所以这个 include 一个都不能漏）。

## 本次踩的坑（已记入全局 CLAUDE.md）

第一次 scp 传上去的是**主工作区那份没改过的文件**——`EnterWorktree` 之后
Bash 的 `pwd` 仍是主工作区，而我用了相对路径 `deploy/nginx-eutms-app.conf`。
全程零报错：scp 成功、`nginx -t` 通过、reload 成功，只是改动没上线。
靠"探测发现改了等于没改 → 比对本地/线上文件大小"才发现。
**worktree 会话里的 scp/cp/rsync 一律用绝对路径，送完必须在服务器侧核对内容。**
