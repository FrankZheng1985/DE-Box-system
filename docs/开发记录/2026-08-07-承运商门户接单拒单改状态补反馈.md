## 一、问题比测试报告写的更严重

原代码三个操作是一个模子：

```js
const handleAccept = async (id) => {
  try {
    await api.post(`/orders/${id}/accept`)
    fetchOrders()                      // 成功：订单直接消失，无任何提示
  } catch (error) {
    console.error('接单失败:', error)   // 失败：用户什么都看不到
  }
}
```

`handleReject`、`handleUpdateStatus` 同样如此。

- **成功**：当前 tab 筛的是 `ASSIGNED`，接完单订单状态变了就从列表消失，
  承运商成没成全靠猜
- **失败**：错误只进浏览器控制台，**界面毫无反应**——
  承运商会以为没点上而反复点

第二条比第一条严重：一个真实在用的门户，操作失败却装作什么都没发生。

## 二、一个我先猜错、查证后更正的地方

我一开始怀疑更深一层：这个项目很多接口是「HTTP 200 + body 里 `code:400`」
（登录就是这样），而 `carrier-portal/src/utils/api.ts` **只在 `!response.ok`
时抛异常**，那样业务失败就会被当成成功。

**查证后不成立**：`order/controller.js` 的 `accept` / `reject` 用的是
`res.status(400).json(...)`，是真 HTTP 400，api 客户端会抛 `ApiError`。
所以问题就是 catch 把错误吞进了 console，没有"静默成功"这一层。

记在这里是因为「HTTP 200 装错误」这个模式在本项目确实存在，
下次遇到类似排查值得先确认接口到底怎么返回，别照搬结论。

## 三、改法

沿用**本端已有**的 `{ text, ok }` 提示模式（`CompanySettings.tsx`、
`GPSReport.tsx` 都在用），不另起一套 Toast 组件
——共享组件是另一个对话「前端组件化二梯队」的活，这里不越界。

- 三个 handler 都在成功/失败时 `setMessage(...)`
- 页面标题下方加一条 `role="status"` 的提示条，绿=成功、红=失败
- **文案直接用 `res.message` / `error.message`**：后端 `接单成功` / `拒单已记录`
  在 `message-codes.js` 里已有 `ORDER_ACCEPTED` / `ORDER_DECLINED`，
  api 客户端会按当前语言翻译好，**不用新增翻译也自动三语**。
  只在后端没给 message 时才退回本地兜底 key。
- **拒单失败时不关弹窗、不清空理由**，让人看到错误能直接重试
  （原来成功路径才清，失败路径本来也没清，这次显式写明意图）

### ⚠️ 没做到的：没有在浏览器里真正走一遍

两个原因，都不是"忘了"：

1. **worktree 里 `preview_start` 跑的是主工作区的代码**（全局 CLAUDE.md 明确
   警告过的坑），起出来验的不是这份改动。
2. **唯一的承运商账号 `speedtrans` 是停用状态**，且密码不该经我手。

所以 UI 层（提示条真实渲染出来、颜色对不对）**仍需人工看一眼**。
数据层与构建层已验到位。

## 六、关联影响

- **只动了承运商门户这一个页面**，其余两端与后端一个字没碰。
- `fetchOrders` / 拒单弹窗 / tab 切换等原有逻辑未改，只在结果处加了提示。
- 提示条**不自动消失**，与本端 `CompanySettings`、`GPSReport` 的既有行为一致；
  每次操作前 `setMessage(null)`，不会看到上一次的残留。
