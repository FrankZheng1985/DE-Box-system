## 关键设计决定

### 为什么是软删除

Frank 2026-08-07 拍板。询价单是凭证链上游，客户删掉之后运营侧必须还能追溯
「这张单去哪了、谁什么时候删的」。原实现是 `DELETE FROM inquiries`，
明细行跟着 CASCADE，删完什么都不剩。

### 删除守卫：两道，而不是一道

1. **状态必须是 `PENDING_QUOTE`** —— 已报价/已接受属于业务凭证链，只能走取消
2. **运营还没在这张单上动过手** —— 这条是本次新加的，关键在于
   「PENDING_QUOTE 不等于没人管」：
   - 自 536bd5c 起建草稿报价不再推进询价状态，运营可能正编着草稿
   - 发给服务商的询价（`carrier_inquiries`）也不改询价状态，邮件可能已经发出去了

有了第 2 条，`quotations` / `carrier_inquiries` 的外键**永远指不到一张被删的单**，
这两个模块的查询一行都不用改。用前置条件消灭问题，比在 N 个下游查询里加过滤可靠。

### 软删除过滤放在 `applyScopeFilter()` 里

列表 / 统计 / 报价时效 / 导出四个查询都走这个函数，过滤放进去以后新加的查询
自动带上，不会漏。单条详情不走它，`loadInquiryWithAccessCheck` 里另有一份。

### 摘要为什么删那两行

苏凌的原话是「删除客户信息和渠道信息」。这份摘要是直接粘给欧洲服务商询价的：
客户名等于把货主直接告诉承运商，服务类型是内部渠道口径，对方既看不懂也用不上。

## 关联影响分析

**一并改了的**

- 客户单号查重（导入）、external_ref 查重（开放 API）—— 不改的话客户删掉错单后
  同一个单号再也导不进来，详见踩坑 057
- 幂等唯一索引 `uq_inquiries_external` —— 同上，不改会 500
- 三端 `apiMessage` 语言包 —— P9 约定，后端加中文文案必须配码 + 三语

**确认不受影响的**

- `quotations` / `carrier_inquiries` 模块：删除守卫保证外键指不到已删单，无需过滤
- 运营管理端询价页：删除接口的权限从 `inquiry:delete` 扩成
  `inquiry:delete` 或 `portal:inquiry_manage`（任一满足即放行），运营侧行为不变
- 权限字典：`portal:inquiry_manage` 迁移 109 已定义并分配给 `client_admin`，
  本次**不需要**新增权限迁移；`check-permission-menu-sync.js` 通过
- 报价时效统计口径：未动，只是分母不再包含已删单
