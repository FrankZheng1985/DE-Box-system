# 2026-08-06 员工以自己的身份进入客户门户

**模块**：客户管理（admin）+ 认证（server）+ 客户门户（customer-portal）

---

## 需求

运营人员在「客户管理」列表点一个按钮，直接进入某家客户视角的客户门户，
用来排查「客户说他那边看不到某张单」这类问题，不用再靠截图来回问。

Frank 拍板的边界（2026-08-06）：

| 决策点 | 选择 |
|--------|------|
| 以什么身份进去 | **员工自己的身份**，不借用客户的任何账号 |
| 门户内的权限 | 与客户本人等效（可下单、可改资料） |
| 谁能用 | 新增权限码 `client:impersonate`，默认给 `sys_admin` + `op_manager` |

唯一的例外限制：**代入期间禁止改密码**（原因见下）。

---

## 核心设计：外壳是客户，内核是员工

JWT payload 长这样：

```js
{
  id:             员工自己的 users.id,     // ← 内核：审计、通知、profile 查到的都是员工本人
  username:       员工用户名,
  userType:      'CLIENT',                // ← 外壳
  roleCode:      'client_admin',          // ← 外壳：借这套 portal:* 权限码
  linkedEntityId: 目标客户ID,              // ← 外壳：限定只看这一家
  impersonation: { sessionId, operatorId, operatorUsername, operatorDisplayName, companyName }
}
```

**为什么 `userType` 必须是 `'CLIENT'`，不能是 `'OPERATOR'`**：

order / inquiry / cmr / customs / gps / finance / notification 七个模块的租户过滤
统统写成 `if (userType === 'CLIENT' && linkedEntityId) { 加过滤 }`。
身份写成 OPERATOR 的话这些分支**根本不走** —— 等于在客户门户里不加任何过滤，
把**所有客户**的订单、账单、清关数据全都显示出来。

所以「外壳是客户」不是取巧，是同时满足「以员工身份」和「只看得到这一家」的唯一做法。
实测反证：把 `linkedEntityId` 换成一个不存在的 UUID，订单接口返回 0 条 —— 过滤确实按它生效。

**为什么 `roleCode` 借 `client_admin`**：客户门户的菜单和接口都按 `portal:*` 权限码放行，
而员工自己的运营角色一个 `portal:*` 都没有，不借的话进去是一片空白。

**这样设计的好处**：
- 客户的账号不被占用，`last_login_at` 不被污染（实测仍是 08-05）
- 审计台账里直接就是员工本人
- **客户哪怕一个门户账号都还没建，员工也能进去看**（实测通过）

## 两步握手，不把 token 塞进 URL

```
员工点按钮
  → POST /api/v1/clients/:id/impersonate   （要 client:impersonate 权限）
  ← 返回一次性票据（60 秒过期）
  → 浏览器新标签打开 /customer/login?ticket=xxx
  → POST /api/v1/auth/impersonate/exchange （免登录，只认票据）
  ← 返回上面那个 token（有效期 2 小时）
```

**为什么不让第一步直接返回 token**：token 要传给客户门户，只能走 URL，
而 URL 会进浏览器历史、进 nginx access log、作为 Referer 发给页面上的外链。
票据是一次性的、60 秒过期、库里只存 sha256，即便泄漏也基本无法利用。

**为什么票据必须落库而不是放内存**：生产 pm2 是 `-i 2` 双实例，
内存 Map 里的票据只有签发它的那个实例认得，换票请求被负载均衡打到另一个实例
就查无此票——约一半概率随机失败，最难排查。这张表同时就是审计台账。

---

## 为什么必须禁掉改密码

`PUT /api/v1/auth/password` 按 `req.user.id` 改密码，而代入态的 `id` 是**员工自己的账号**。
员工在客户门户的「账户设置」里改一次密码，改掉的其实是自己的**运营端密码**，
下次登管理端就进不去了，而他以为自己改的是客户的。所以这个接口在代入态直接 403。

## 安全设计

1. **票据一次性**靠一条 `UPDATE ... WHERE used_at IS NULL AND expires_at > NOW() RETURNING`
   原子完成，不拆成 SELECT + UPDATE（并发下两个请求都能过 SELECT）。
2. **签票到换票之间会隔一次页面跳转**，这期间员工账号可能被停用、客户可能被作废，
   所以换票时按库里当前状态重新校验双方，不信票据里的快照。
3. **代入 token 反向访问运营端接口会被拒**：它的 `userType` 是 CLIENT、`roleCode` 是
   `client_admin`，`requireUserType('OPERATOR')` 直接 403 —— 不能拿它绕回去看全量客户数据（实测通过）。
4. **全程留痕**：`impersonation_sessions` 表 + `console.warn` 日志各记一份。
5. **前端也守一道**：门户拿到 token 仍校验 `userType === 'CLIENT'`（踩坑 028 的教训）。

## 关联影响

- **`PUT /api/v1/auth/password` 行为变化**：代入态调用返回 403。
  客户本人和员工在管理端改密码完全不受影响（实测客户本人走到了正常的"旧密码错误"校验）。
- **客户门户通知**按 `req.user.id` 取，代入态下员工看到的是**自己的**通知，不是客户的。
  不越权，但排查"客户没收到通知"时要知道这一点——得去看客户账号本人的通知。
- **客户门户「账号管理」页**：代入态下员工能管理该客户的成员账号（符合"与客户本人等效"口径）。
  其中"不能改自己角色/不能停用自己"两条自保护判断对员工恒为 false（员工不在该公司成员列表里），
  也就是说员工可以停用该客户的任何成员，包括客户管理员。
- **客户门户 Layout 根节点** 由 `flex` 改为 `flex flex-col` 外包一层，
  未开启代入时不渲染横幅，DOM 结构和视觉与改动前一致。
- **确认不受影响**：承运商门户（未接入本功能）、正常登录链路（`POST /auth/login` 一行未改）、
  客户本人的登录与使用（两条链路各签各的 token，互不挤下线）。

## 部署注意

1. **先跑迁移 122**，再部署后端，最后部署前端。
   顺序反了会出现「按钮已经有了，但后端 404 / 权限码不存在」。
2. 迁移是 additive 的：`CREATE TABLE IF NOT EXISTS` + `ON CONFLICT DO NOTHING`，
   不改任何现有表结构，可重复执行。
3. 部署后如果运营经理看不到按钮，去「角色权限」页确认 `op_manager`
   勾上了「进入客户门户」——迁移只在权限码首次插入时自动授权。
