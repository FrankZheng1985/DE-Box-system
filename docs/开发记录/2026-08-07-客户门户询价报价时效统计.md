# 客户门户 · 询价报价时效统计

- **日期**：2026-08-07
- **模块**：客户门户 询价页（customer-portal / server inquiry）
- **需求**：客户端询价界面增加「询价单建立后到提供报价」的时效统计，按天

---

## 一、做了什么

客户门户「询价」页新增两处时效展示：

1. **列表新增「报价时效」列**
   - 已收到报价的单：显示 `1.5 天`（建单 → 第一次收到报价）
   - 还在等报价的单：显示琥珀色 `已等待 2.4 天`
   - 其余情况显示 `-`

2. **列表上方新增一排统计卡片**（口径覆盖该客户的全部询价，不只当前页）
   - 平均报价时效（副标：已报价 X / 共 Y 单）
   - 最快报价
   - 最慢报价
   - 待报价最长等待（副标：待报价 N 单）

## 二、时效口径（重要）

**时效 = 询价单 created_at → 第一张【非草稿】报价的 created_at，单位天，保留 1 位小数。**

- **为什么排除草稿**：草稿是运营还在编的报价，客户门户「我的报价」页本来就会把 `DRAFT`
  过滤掉、客户根本看不到。把草稿算进来等于客户没拿到价却显示「已报价 0 天」。
- **为什么用 created_at 近似"发出时间"**：`quotations` 表没有单独的发送时间列，
  `updated_at` 会被后续任何一次编辑覆盖，不能当发出时间用。实际操作里运营是建完就发，
  误差在当天以内。要精确到"真正点发送的那一刻"，需要给 `quotations` 加 `sent_at` 列
  并在 `POST /quotations/:id/send` 里写入 —— 属于表结构变更，本次没做。
- **为什么保留 1 位小数**：物流询价多数当天就报价，取整会全变成 `0 天`，统计失去意义。
- **等待天数只对 `PENDING_QUOTE` 的单计算**：已取消 / 已拒绝的单不该继续往上涨。

## 四、关联影响

- **数据库**：无表结构变更、无迁移脚本、无数据订正。全部靠已有的
  `inquiries.created_at` + `quotations.created_at/status` 现算。
- **权限**：没有新菜单、没有新页面，沿用列表接口已有的
  `requirePermission('inquiry:view', 'portal:inquiry_manage')`，**不需要权限四件套**。
- **租户隔离**：新接口和列表接口一样先过 `requireTenantBinding`，再用 `applyScopeFilter`
  按 JWT 的 `linkedEntityId` 强制收窄，客户只能看到自己公司的时效（踩坑 016）。
- **路由顺序**：`/quote-sla` 注册在 `/:id` 之前（踩坑 001）。
- **运营管理端**：admin 的询价列表调的是同一个 `GET /inquiries`，本次只是多返回三个字段，
  admin 页面没读这几个字段，行为不变。承运商门户不碰询价，不受影响。
- **前后端类型**：新字段用 `::float8` 输出，pg 直接回数字而不是字符串（踩坑 002）；
  前端 interface 用 snake_case 与 API 对齐（踩坑 003）。
- **部署顺序有硬依赖**：统计接口是新加的，前端先上线会 404。前端已把这个请求的失败单独
  吞掉（只少一排卡片，列表照常显示），但正常顺序仍应 **先发后端、再发前端**。

## 五、已知的展示边界（不是 bug，但要知道）

运营建了报价但**还没点发送**时，询价单状态已经翻成「已报价」（这是
`POST /quotations` 里建单即置 `QUOTED` 的既有行为），而时效列会显示 `-`
（因为客户还没拿到价）。也就是「状态说已报价、时效列是横杠」这种短暂状态。
如果觉得别扭，两条路可选：

1. 给 `quotations` 加 `sent_at`，询价状态改成发送时才翻 `QUOTED`（口径最干净，动的地方多）
2. 时效列对这种单显示「报价准备中」而不是 `-`（纯展示层，改一处）
