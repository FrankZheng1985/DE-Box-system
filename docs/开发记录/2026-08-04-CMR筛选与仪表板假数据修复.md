## 一、CMR 的两个筛选 Tab 一直查不到数据（踩坑 036 收尾）

### 问题

上一轮修了清关和放单的筛选 Tab（小写 key 对不上大写枚举），
CMR 还剩两个 Tab 是坏的，点下去永远是空列表：

| Tab | 原来发给后端的值 | 为什么查不到 |
|---|---|---|
| 待签署 | `pending` | 真实状态有三个：`UNSIGNED` / `SENDER_SIGNED` / `RECEIVER_SIGNED`，后端只支持单值等值比较 |
| 有异常 | `exception` | 它筛的**根本不是签署状态**，是货损标记 `has_damage_note` |

### 改法

后端 `GET /cmr`：
- `signStatus` 支持逗号分隔多值，多值时用 `= ANY($n)`，单值照旧走 `=`
  （所以承运商门户、客户门户的单值调用不受影响）
- 新增 `hasDamage=true` 参数，筛 `has_damage_note = true`

前端 `CMRManagement.tsx`：
- 「待签署」的 key 改成 `UNSIGNED,SENDER_SIGNED,RECEIVER_SIGNED`
- 「有异常」用哨兵值 `DAMAGE`，请求时切到 `hasDamage=true` 而不是 `signStatus`

### 生产核对

CMR 表当前是空的（0 行），所以只能核对 SQL 正确性，
等有数据后需要 Frank 在页面上逐个 Tab 点一遍确认。

## 二、仪表板 5 处写死的假数据接上真值

P9 翻译时发现这几个数字是硬编码的，当时只翻译没改行为，本次接真实来源。

| 卡片/待办 | 原来 | 现在的口径 |
|---|---|---|
| 今日新订单副标题 | 写死 `+3 vs 昨日` | 今日新增 − 昨日新增，负数显示 `-N` |
| 运输中副标题 | 写死 `8 即将到达` | 见下方「三」 |
| 本月完成副标题 | 写死 `完成率 94.2%` | 本月完成 / 本月新建，文案里写明口径 |
| 待办·账单 | 写死 `2 个账单待确认` | **改成「N 笔应收未结清」** |
| 待办·资质到期 | 写死 `1 个运输公司资质到期` | 30 天内到期，口径同 cron 的资质到期提醒 |

### 为什么「账单待确认」要改文案而不是接数据

`financial_records.payment_status` 的值域是
`UNPAID / PARTIAL / PAID / OVERDUE / VOID`，**没有「待确认」这个状态**。
硬凑一个出来等于继续骗人，所以改成统计真实存在的「未结清应收」
（`UNPAID` + `PARTIAL` + `OVERDUE`），三语文案一并改成「N 笔应收未结清」，
让标签和数字对得上。

本月一单没建时完成率给 0，不除出 `NaN`。

## 三、⚠️ 自己写的查询也踩了坑：「即将到达」把逾期单算进去了

第一版写成：

```sql
COALESCE(eta, delivery_date) <= CURRENT_DATE + INTERVAL '3 days'
```

**只有上界没有下界**，于是 ETA 已经过期的在途单也被算成「即将到达」。
生产实测：26 条在途，全部被算进「3 天内到达」——数字看着漂亮，实际毫无意义。

加下界 `>= CURRENT_DATE` 之后复测：

```
3天内到达 0 | 逾期未到 26
```

顺带单独统计了「在途但已超过预计到达日」，卡片副标题改成：
**有逾期未到的就先报这个**（比「即将到达」更需要人立刻处理），没有才显示即将到达。

> 教训：接真实数据的查询，一定要拿生产数据跑一遍看数字合不合理。
> 这条 bug 在本地空库上永远看不出来 —— 0 条数据时两种写法结果都是 0。
