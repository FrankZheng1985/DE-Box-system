## 三、验证结果

生产实测四个用例（临时账号已在同一脚本内清理，无残留）：

```
✅ 不传角色               → 400 参数错误：必须为账号指定角色
✅ 角色留空串             → 400 参数错误：必须为账号指定角色
✅ CLIENT 账号挂运营角色  → 400 角色「sys_admin」属于 OPERATOR，不能分配给 CLIENT 账号
✅ 角色类型匹配           → 201 用户创建成功（未误伤正常请求）
```

账号健康检查（踩坑 035 / 036 的排查 SQL）：

```
① 启用但无角色的账号        无 ✅
② 启用但绑定悬空的门户账号  无 ✅
③ 角色类型与用户类型不匹配  无 ✅
④ 启用的运营端账号数        1（= admin）✅
```

登录实测：`siemens` / `speedtrans` 返回「账号已停用」；`admin` + 旧公开密码
返回「用户名或密码错误」，确认密码已不是仓库里那个公开值。

> 注意：本项目 HTTP 状态码恒为 200，业务码在响应体的 `code` 字段里。
> 只看 HTTP 状态码会把 401 误判成登录成功。

## 遗留事项

1. **JWT 有效期 7 天且无失效机制**（`server/modules/auth/routes.js:97`，无黑名单/
   tokenVersion）。`suling` 8-03 01:17 登录过，其旧 token 里仍是
   `userType: OPERATOR` + `roleCode: sys_admin`，**降权在最长 7 天内不完全生效**，
   最晚 8-10 自然失效。要立即掐断只能换 `JWT_SECRET`，代价是所有人重新登录一次。
2. **需通知苏凌换登录入口**：`suling` 现在是客户账号，要从
   `https://kalunasped.com/customer/` 登录，密码不变。
3. **git 历史仍可检索到旧明文密码**（`git log --all -S admin123` 命中 6 个提交）。
   密码已轮换，危害大幅下降；彻底清除需重写历史，会改掉所有 commit hash。
4. **生产工作区有 64 个未提交改动**，线上代码与仓库对不上，建议另开一次专门梳理。
