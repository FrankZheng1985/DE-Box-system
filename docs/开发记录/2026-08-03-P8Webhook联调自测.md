> 模块：open-api（扩展）+ admin 前端
> 迁移：无

## 为什么做这个

Webhook 上线后有个联调空档：合作方给了接收地址，我方**只能干等真实业务事件发生**
才知道地址通不通、对方验签写没写对。第一次对接最需要确认的恰恰是这件事。

现在运营在密钥编辑弹窗点一下「发送测试事件」，立刻看到结果。

## 功能说明

- 后端 `POST /api/v1/open-api/keys/:id/webhook-test`：同步向对方接收端发一条
  `WEBHOOK_TEST` 事件，把对方的**状态码、耗时、响应体片段**原样带回
- 前端：Webhook 地址下方的按钮 + 结果卡片（成功绿色带状态码耗时；失败红色带错误原因和排查方向）
- 地址改动未保存时，按钮旁提示「先保存再测试」（后端测的是库里的值，不是表单里的）

**与真实投递的三点区别**（有意为之）：

| | 真实事件 | 测试事件 |
|---|---|---|
| 执行 | cron 异步 | 同步，立刻返回结果 |
| 投递记录 | 写 outbox | **不写**，不污染投递记录 |
| 失败处理 | 退避重试 5 次 | 不重试，直接把失败原因给运营看 |

签名方式与真实事件完全一致——这正是测试的意义所在（能验证对方验签实现）。

## 关联影响分析

1. **真实投递链路零改动**：sendTestEvent 是独立函数，runWebhookCycle 未动。
2. **不写 outbox** 是刻意设计：测试记录混进投递列表会让运营分不清哪些是真业务。
   代价是测试结果不留痕（只在当次弹窗显示），可接受——真出问题会有真实投递记录。
3. **权限**：走 admin-routes 整组的 `open_api:manage`，op_staff 403（冒烟已验）。
4. **对外契约是纯新增**：合作方只需保证接收端对未知事件类型返 2xx（文档已写明）。
5. **确认不受影响**：对外推送/回查端点、cron、其他 admin 端点均未改动。
