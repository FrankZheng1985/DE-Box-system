## 为什么原先 LTL/FTL 填不了柜号

`inquiries.container_no` 是迁移 129 加的，当时只给本地派送用。
建单函数 `service.js#createInquiryRecord` 里硬写着：

```js
// 柜号只有本地派送用得上
payload.businessType === LOCAL_DELIVERY ? (payload.containerNo || null) : null
```

**LTL/FTL 就算前端传了柜号也会被静默丢掉** —— 所以客户只能把柜号挤进「贵司单号」
（这也是 Frank 截图指出的现状）。本次把这个限制去掉。

### 三个关键设计取舍

**1. 数据库列必须可空，必填放应用层**
库里 27 张历史询价没有这两个值，列若设 `NOT NULL` 迁移直接失败。
必填由前端表单 + 后端 POST 校验 + 导入解析三处共同保证。

**2. 必填只在「新建」时校验，编辑不卡**
后端 `validateContainerAndArrival` 只挂在 `POST /`，`PUT /:id` 不校验；
管理端表单同样是 `required={!isEdit}`。否则运营编辑一张老询价时会被要求补齐历史数据，卡死在页面上。

**3. 旧模板要明确报错，不能静默放行**
两条导入通道的新列都标了 `required: true`，客户手上的旧模板缺列会被
`importErrMissingColumns` **整表挡下**并提示"请使用最新的导入模板"。
既然产品上定了必填，就不能让旧模板悄悄导进一批空值。

### 管理端一个会被打爆的地方（本次一并修）

`InquiryEdit.tsx` 原先柜号只在 `hasDeliveryOrders`（本地派送三层单）分支里传：

```js
...(hasDeliveryOrders ? { containerNo: ..., deliveryOrders: [...] } : { cargoItems: [...] })
```

也就是**运营代客户建 LTL/FTL 询价时根本不带柜号**。加上必填校验后，当天运营就会建不了单。
已把 `containerNo` 提到 payload 公共层。

## 顺带修掉的生产问题：所有日期少一天

验证时发现存 `09-20` 读出 `09-19`。根因是 pg 把 DATE 解析成**进程本地时区**的午夜，
而生产服务器是 `Asia/Shanghai (UTC+8)`、客户在德国：

```
2026-09-20 → Date(09-20 00:00 +08:00) → "2026-09-19T16:00:00.000Z" → 德国显示 9 月 19 日
```

**不只影响新字段**：库里 12 个 DATE 列全都吃这一套，
`finance/routes.js:176,242` 的 `new Date(row.due_date).toISOString().slice(0,10)`
说明**财务到期日一直在少一天**。

已在 `core/db.js` 加 `pg.types.setTypeParser(1082, v => v)`，DATE 按 `'YYYY-MM-DD'` 返回。
**这是全局行为变更**：只影响 DATE 不动 TIMESTAMP，SQL 侧日期比较不受影响，
财务那两处跟着修对。详见踩坑 073。
