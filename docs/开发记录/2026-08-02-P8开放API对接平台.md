## 功能说明

易抵达/傲翼/翼能等外部系统直推询价单和订单，对外前缀 `/api/open/v1`，
与 `/api/v1` 的 JWT 登录体系完全隔离，认证方式为 `X-API-Key` 请求头。

| 端点 | 用途 |
|------|------|
| `GET  /api/open/v1/ping` | 连通性自检（联调第一步） |
| `POST /api/open/v1/inquiries` | 按订单号维度推询价单（复用 P3 的 inquiry_cargo_items 按件明细，LDM 自动算） |
| `POST /api/open/v1/orders` | 按柜号维度直接下单（固定价客户，完整过 ERP 内核，落 PENDING_REVIEW） |

核心机制：

- **身份即钥匙**：每把 Key 绑定一个客户档案（`api_keys.client_id`），推进来的单据自动挂该客户，请求体不允许指定客户
- **幂等**：`(partner_code, externalOrderNo)` 去重，重复推送返回首次创建的单据（`duplicated: true`，HTTP 200），实现是"事务内先查后插 + 捕获 23505"，**不用 ON CONFLICT**（部分唯一索引推断不出，踩坑 020）
- **免登录操作人**（踩坑 019）：凭证 created_by 用"建钥匙的运营 → 在职 sys_admin"兜底，不伪造身份不放开 NOT NULL
- **留痕**（踩坑 027）：api_request_logs 走独立池连接，成功/被拦/回滚都留记录
- **限速**：按钥匙内存滑窗（默认 60 次/分钟，api_keys.rate_limit_per_min 可调）；PM2 双实例下是"每实例"计数，防滥用够用
- **密钥安全**：库里只存 SHA-256，明文只在签发脚本输出一次；查 api_keys 一律点名列，key_hash 永不外流（踩坑 026 思路）

## 关联影响分析

1. **inquiries / orders 加两列**（均可空）：存量数据不受影响；全库现有 INSERT 都是点名列写法，不受新列影响。
2. **新增两个部分唯一索引**：按踩坑 020 防护规则全仓搜过 `ON CONFLICT`，现有语句全部落在其他列（order_id、user_id/event_type、doc ids），无一命中新索引，不受影响。
3. **复用而未改动**：inquiryService.replaceCargoItems、orderService.createOrder、documentEngine、creditManager、notificationEngine——open-api 只是调用方，行为与运营端建单完全一致（凭证/信用/变更追踪/通知一个不少）。
4. **前端三端零改动**；权限四件套不适用（开放 API 不走 JWT/权限码，无新菜单页面）。
5. **nginx 无需改**：`/api/` 已整体反代到 :3002，`/api/open/v1` 自然覆盖（部署后需实测确认）。
6. **确认不受影响**：/api/v1 全部现有路由（app.js 只追加了一行挂载）；CI/CD 构建（无新依赖，只用 node:crypto）。

## 注意事项 / 遗留

- **契约仍是草案**：字段清单待易抵达/傲翼/翼能书面确认，确认前不要给对方签发正式钥匙（文档第 8 节列了待确认事项）。
- **限速是每实例计数**：PM2 2 实例时实际上限约为配置值 2 倍。要精确全局限速得上 Redis，当前不值得。
- **重复推送不更新内容**：幂等语义是"返回已存在的单据"，对方推错数据要改，走运营人工处理。
- **P8 后续对话可做**（本次未做，属计划内拆分）：admin 端 API 日志查看页 / 密钥管理页（届时按权限四件套补）、状态回查接口、Webhook 状态回传（对外文档 v1.1 讨论范围）。
- 测试脚本冒烟时需要手动打开当月过账期间（生产由 P0 的过账期间 cron 自动管理，测试库没有 cron）。
