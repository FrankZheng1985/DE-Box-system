## 一、做了什么

### 1. 新增体检脚本

`server/scripts/check-dangling-entity-bindings.js`

踩坑 035 的「排查方法」原本只是文档里一段手抄 SQL，现在做成可跑的工具：

```bash
cd server && node scripts/check-dangling-entity-bindings.js
```

- 列出所有 CLIENT / CARRIER 账号及其绑定状态（有效 / 未绑定 / **悬空**）
- 退出码：`0` = 无悬空绑定，`2` = 存在悬空绑定
- 改绑：`--fix --bind 用户名=公司名`（可重复）

**该脚本刻意永不修改 `is_active`**。启用停用账号是独立的安全决策，
不该被一个"修绑定"的操作顺手做掉。

同名公司超过一条时脚本会拒绝猜测，提示改用 UUID 手工处理。

### 2. 改绑两个悬空账号

| 账号 | 原绑定 | 现绑定 | 启用状态 |
|---|---|---|---|
| `siemens` (CLIENT) | `1953e9c8-…`（公司已删） | **安百** `22b9827c-…` | **仍停用** |
| `speedtrans` (CARRIER) | `85061206-…`（公司已删） | **SGF** `b380819d-…` | **仍停用** |

选择依据：安百有 27 单且此前**没有任何门户账号**（翼能已有 suling、duguirong）；
SGF 有 7 单且准时率/覆盖路线的样本都在它名下，便于验证承运商门户。

## 二、执行过程（按数据安全纪律）

1. **备份**：`/root/db-backups/users-20260804010743..sql`（6 条记录，含两个目标账号）
2. **只读检查**：脚本报告 2 个悬空绑定，退出码 2
3. **干跑**：事务内执行两条 UPDATE → 打印结果 → **ROLLBACK**，
   确认各影响 1 行、`is_active` 不变，且数据库未被改动
4. **真跑**：`--fix --bind siemens=安百 --bind speedtrans=SGF`，退出码 0
5. **独立复查**：不信脚本自己的复查，另跑一段 SQL 确认
   - 剩余悬空绑定数 = **0**
   - 启用中的门户账号数 = **2**（suling / duguirong），两个目标账号仍停用
