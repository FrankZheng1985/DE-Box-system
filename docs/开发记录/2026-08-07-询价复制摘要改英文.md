# 询价「复制摘要」文本改为英文（可切三语）

**日期**：2026-08-07
**模块**：询价（inquiry）
**分支**：worktree-inquiry-summary-en

---

## 需求

「复制摘要」生成的文本原来全是中文标签（询价单号／起运地／货物明细／合计…），
而这份文本的用途是**直接粘给欧洲服务商询价**，对方看不懂中文。改成英文。

## 做法

摘要属于「后端自己渲染、前端拿到就是成品」的文案，正好走 P9 已有的后端语言包
（`server/utils/i18n.js` 的 `t(lang, key)` + `server/i18n/locales/*.json`），
不另造一套。三语标签一次补齐，中文和德文都留着。

**语言默认值刻意不跟界面语言走**：`resolveLang(req)` 读的是 Accept-Language，
也就是操作员的界面语言（多半是中文），拿它渲染这份文本就又变回中文了。
所以这类"转给服务商的成品"单独用 `resolveCarrierDocLang(req)`：
只认显式的 `?lang=`，默认 `en`。

**导出 Excel 一并纳入**（Frank 2026-08-07 确认）：那份 Excel 按代码注释也是
"方便服务商筛选排序"用的，同样是转给服务商的成品，原来却跟着界面语言走，
中文界面导出来就是中文表头。这次和摘要统一成默认英文。

## 改动文件

| 文件 | 操作 | 说明 |
|------|------|------|
| `server/modules/inquiry/service.js` | 修改 | `buildSummaryText(inquiry, items, lang = 'en')` 新增第三个参数；所有中文字面量换成 `t(lang, 'inquirySummary.*')`；新增 `PUNCTUATION`（中文全角冒号＋【】，英德半角冒号＋[]）和 `businessTypeLabel()`；`formatAddressLines()` 加 lang 参数；删除只服务于这里的中文常量 `BUSINESS_TYPE_LABELS` |
| `server/modules/inquiry/routes.js` | 修改 | 新增 `resolveCarrierDocLang(req)`（`?lang=` → 默认 en），摘要两个端点 ＋ 导出 Excel 共三处调用；新增 `enumLabel()` 译枚举值；`buildExportHeaderCells(inquiry, lang)` 加参数；**删除中文常量 `BUSINESS_TYPE_LABELS` 和 `STATUS_LABELS`**；import 补 `normalizeLang` |
| `server/i18n/locales/zh.json` | 修改 | 新增 `inquirySummary` 段（29 行）＋ `inquiryStatus` 段（5 行），纯新增 |
| `server/i18n/locales/en.json` | 修改 | 同上，英文 |
| `server/i18n/locales/de.json` | 修改 | 同上，德文 |

`inquiryStatus` 的三语措辞直接照搬 `admin/src/i18n/locales/*.json` 里已有的同名段，
保证导出的 Excel 和管理端界面上看到的状态名是同一套说法。

## 接口变化

三个端点都**向后兼容**，不传参数就是英文：

- `GET /api/v1/inquiries/:id/summary?lang=en|zh|de`
- `POST /api/v1/inquiries/summary?lang=en|zh|de`（body 仍是 `{ ids: [...] }`）
- `GET /api/v1/inquiries/export?lang=en|zh|de`（**行为变更**：原来跟界面语言，现在默认英文）

`lang` 认不出来时（比如 `?lang=fr`）回退英文，不报错。

## 关联影响

- **前端不用改**：`InquiryDetail.tsx` 和 `InquiryManagement.tsx` 只是把 `data.text`
  原样显示／复制，不传 lang 就拿到英文。弹窗标题等界面文案仍走前端 i18next，跟着界面语言。
- **`buildSummaryText` 只有这两个端点调用**（`server/modules/inquiry/routes.js:198`、`:456`），
  没有别的调用点会被默认值改变行为。
- **`order/service.js` 的 `BUSINESS_TYPE_LABELS` 不受影响**：本次删掉的是 inquiry
  模块内部那份重复的中文副本，order 那份是独立导出、另有 4 处引用，原样保留。
- **导入模板 / 导入报错仍跟界面语言走**：`routes.js` 里另外三处 `resolveLang(req)`
  （`/import-template` 和两个导入端点）**刻意不动**——那些是给操作员和客户自己看的，
  中文同事要中文模板。只有"转给服务商"的那三个端点改成默认英文。
- 客户名（`clients.company_name`）、货物描述这类**数据**仍按库里原样输出，
  英文摘要里客户名可能还是中文——`clients` 表只有一个名称字段，没有英文名列。
  要让服务商看到英文客户名，得给客户表加英文名字段，属于另一件事。

## 验证

**本地实跑**（worktree 里 `node app.js` 起在 3002，连本地 `germany_box_transport`，
已用 `lsof -a -p <pid> -d cwd` 核对进程 cwd 确实是 worktree 那份代码）：

- `GET /:id/summary` 带 `Accept-Language: zh-CN`（故意模拟中文界面）→ 回来是**英文**，
  证明确实没跟界面语言走。
- `GET /export` 同样带中文 Accept-Language → 下载的 xlsx 用 ExcelJS 读回来核对：
  工作表名 `Inquiries`、27 个表头全英文，且 `Service type = Truck LTL`、
  `Status = Accepted` —— 改前这两列的**值**会是「卡车派送 LTL」「已接受」。
- `?lang=zh` 三处仍回中文（工作表名「询价单」、状态「已接受」），中文用法没被弄坏。
- `?lang=de` 回德文；`?lang=fr`（不支持）回退英文，不报错。
- 纯函数层面：用 Frank 提供的那张单（INQ-20260806-0002）的字段跑 `buildSummaryText`，
  en / zh / de 三种输出逐行核对；未知业务类型（如 `SEA_FCL`）回退成原始代码，
  不会露出 `businessType.SEA_FCL` 这种给服务商看不懂的字符串。
- `node scripts/check-i18n-keys.js` 退出码 0；`server/scripts/check-permission-menu-sync.js` 校验通过。
- 单独核对 routes.js 用到的 27 个 `excel.*` 键在三语包里都齐。

## 注意事项

摘要里的键用的是模板字符串 `t(lang, \`inquirySummary.${key}\`)`，
`check-i18n-keys.js` 的静态扫描**认不出来**（脚本自己有说明）。
以后往摘要里加字段，三语包必须手工同步补齐，别指望校验脚本报错。
