# 2026-08-07 · 空日期防线补齐到全部写入日期的模块

**模块**：carrier / order / quotation / finance / shipping-release

## 背景

承运商编辑那个 bug（踩坑 059）修完后，从**数据库**反推做了一次全量排查：
生产 15 个 `date` 列 + `orders.eta`（timestamp，同样拒收空串），逐个追写入点。

结论是**没有第二处会立刻炸的**——其它前端入口都恰好兜住了
（`|| null` / `|| undefined` / `orNull()` / 必填校验）。但**后端有 5 处裸传，
防线全在前端**。carrier 之所以炸，正因为它的前端是唯一没写兜底的那个：
这不是"carrier 特别倒霉"，是"其它几个恰好没被触发"。

按踩坑 059 自己定的防护规则第 1 条（「凡是往 date 列写值的接口，
空串必须在后端转成 null」），把这几处一并兜上。

## 修改文件

| 文件 | 操作 | 说明 |
|---|---|---|
| `server/utils/normalize-date.js` | **新增** | 公共 `normalizeDateFields(body, fields)`，只把「字符串且去空格后为空」转 null；`undefined` 保持不变（调用方普遍用 `!== undefined` 判断要不要更新该列） |
| `server/modules/carrier/routes.js` | 改 | 原来的本地私有函数改为引用公共实现 |
| `server/modules/order/service.js` | 改 | `createOrder` / `editOrder` 入口各加一行，字段含 `pickupDate` `deliveryDate` `expectedDeliveryDate` `eta` |
| `server/modules/quotation/routes.js` | 改 | POST `/`、PUT `/:id`、POST `/:id/new-version` 三个入口，字段 `validUntil` |
| `server/modules/finance/routes.js` | 改 | POST `/records`，字段 `dueDate`（`paid_date` 不在其中——它是后端 `NOW()` 写的，前端传不进来） |
| `server/modules/shipping-release/routes.js` | 改 | PUT `/:orderId/status`，字段 `releaseValidUntil` |

## 行为变化：**没有**

前端本来就不会传空串（各自都兜住了），这次等于纯加一道后端保险。
唯一的实质变化是：**万一**哪天前端漏了兜底，会静默存 null 而不是整条 500 失败。

## 实测（本地 3002，跑的是 worktree 代码，已核对进程 cwd）

8 条全过：

| 链路 | 结果 |
|---|---|
| 承运商编辑（空日期 + 改车型） | ✅ 200，`license_expiry=null`，车型落库 |
| 订单创建（4 个日期全空） | ✅ 200，`pickup_date`/`eta` 均 null，货描正常 |
| 订单编辑（空日期 + 同时改备注） | ✅ 200，备注真的存进去了（验证不再整条回滚） |
| 放单状态更新（空 `releaseValidUntil`） | ✅ 200，快递公司字段正常落库 |
| 财务记录创建（空 `dueDate`） | ✅ 200，`due_date=null`，金额备注正常 |
| 报价创建（空 `validUntil`） | ✅ 200，`valid_until=null` |
| 报价编辑（空 `validUntil` + 改备注） | ✅ 200，备注正常 |
| 反向：填了日期照样正常存 | ✅ 库里 `2026-09-01`，与提交值一致 |

> 反向那条测试脚本一度显示 `2026-08-31`，查库确认是 **脚本自己**用了
> `toISOString().slice(0,10)`——正是踩坑 039 明令禁止的写法，反倒印证了那条规则。
> 库里存的是正确的 `2026-09-01`。

测试数据（2 个订单、2 张财务记录、2 条报价及其凭证）已全部清理，本地库复核为 0。

## 关联影响

- **Open API**（`open-api/service.js`）：本来就有 `checkDate` 校验 + `|| null`，不受影响，也不需要改。
- **carrier_inquiries**（服务商回价）：后端本来就是 `req.body.validUntil || null`，已安全，未改。
- **condition_records**（定价条件 `valid_from`/`valid_to`）：只有读（`pricingEngine.calculatePrice`），
  没有前端写入路径，不适用。
- **documents / journal_entries** 的日期：内核引擎生成，前端传不进来，不适用。
- **承运商门户**：全端没有任何日期输入框，不适用。
- **确认不受影响**：所有前端页面均未改动；接口出入参、字段名、状态流转、权限码全部未变。
