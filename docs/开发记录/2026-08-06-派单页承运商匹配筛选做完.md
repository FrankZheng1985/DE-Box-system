## 一、原来断在哪

这不是"后端少写了几行"，而是**整条链路都没接上**：

- **前端根本不传**：`OrderAssign.tsx` 调的是裸 `api.get('/carriers/match')`，
  而且它和订单详情是 `Promise.all` **并行**请求的——那时候还没拿到订单，
  **物理上也拿不到装卸货城市**。
- **后端收了不用**：三个参数解构出来就扔了，接口返回全部启用中的承运商。

## 二、口径（Frank 拍板：车型硬筛 + 路线排序）

定这个口径之前先查了数据，因为它直接决定可行性：

| 筛选维度 | 数据源 | 当时现状 |
|---|---|---|
| `vehicleType` | `carriers.vehicle_types` | 两家承运商都是 `[]` |
| `vehicleType`（备选） | `carrier_vehicles.vehicle_type` | **0 条车辆记录** |
| `routeFrom`/`routeTo` | 订单历史 | 清库后只剩 2 单 |

**三个维度当时都没有数据**。所以：

### 车型：硬筛，但「没填过」不算不合格

把 `carriers.vehicle_types`（声明的能力）和 `carrier_vehicles.vehicle_type`
（实际在册车辆）**并起来**当作「已知能力集」：

- 集合为空 → 这家根本没维护过车型信息，**未知 ≠ 做不了**，照常显示
- 集合非空 → 才要求包含所需车型

不这么做的话，以当时数据一硬筛派单页直接变空，运营没法派单。

### 路线：只影响排序，绝不排除

覆盖路线是从历史订单算出来的，**"没跑过这条线"不等于"跑不了"**——
尤其系统刚开始运营。命中的排前面并返回 `route_matched` 供界面标记。

排序：`route_matched` → 有准时率样本 → 准时率 → 综合评分。

## 三、改了什么

### 后端 `server/modules/carrier/routes.js`

- 新增 `caps` CTE 算「已知能力集」（大小写归一）
- 新增 `route_hits` CTE 算「跑过这条线几次」（大小写与首尾空格不敏感）
- `WHERE` 加车型硬筛（三段短路：没传 / 能力集为空 / 包含所需车型）
- `SELECT` 加 `route_matched`，`ORDER BY` 以它为第一优先
- **三个参数全部可选**：一个都不传时行为与改动前完全一致

### 前端 `admin/src/pages/OrderAssign.tsx`

- **把并行改成串行**：必须先拿到订单才知道装卸货城市
- 用本单城市拼 `routeFrom` / `routeTo` 传给匹配接口
- `MatchedCarrier` 加 `route_matched` 字段
- 卡片上加「跑过这条线」绿色标记（`orderAssign.routeMatched`，三语已补）

## 四、验证

SQL 是**从源文件里程序化抽出来、拿生产库真跑的**，不是另写一份差不多的。

### 参数组合（生产库只读）

| 用例 | 结果 |
|---|---|
| 三个都不传 | 两家都返回 ✔ 与改动前一致 |
| 只传 `lunen→madrid` | Eurosped `route_matched=true` **并排在第一** ✔ |
| 传 `REFRIGERATED`（两家能力集为空） | 两家仍返回 ✔ 未知不排除 |
| 路线 + 车型组合 | 同上 ✔ |

### 车型硬筛真的会排除（事务内验证后 ROLLBACK）

上面第 3 条走的是"能力集为空"分支，**证明不了硬筛有效**，所以另做一组：

事务内临时设 `SGF=[FLATBED]`、`Eurosped=[REFRIGERATED]`：

| 请求车型 | 返回 |
|---|---|
| `FLATBED` | `[SGF]` ✔ |
| `REFRIGERATED` | `[Eurosped]` ✔ |
| `CURTAIN_SIDE`（两家都不具备） | `[]` ✔ 确实排除 |
| 不传 | `[SGF, Eurosped]` ✔ |
| `flatbed`（小写） | `[SGF]` ✔ 大小写不敏感 |

ROLLBACK 后确认两家 `vehicle_types` 仍是 `[]`，**生产数据未变**。

## 五、⚠️ `vehicleType` 后端做好了，但前端传不了——因为订单表里没有这个字段

查过 `orders` 表：只有 `business_type`（TRUCK_LTL / TRUCK_FTL / LOCAL_DELIVERY）
和 `transport_type`（FTL/LTL），**没有任何"本单需要什么车型"的字段**。

所以前端无从推导该传什么。硬要从 `business_type` 猜（比如 FTL → 集装箱底盘车）
是编业务规则，不能擅自定。

后端的实现是完整且验证过的，接口契约已兑现。要让它真正用起来，二选一：

1. **给订单加"车型要求"字段**（迁移 + 建单/编辑页 UI + 派单页传参）
2. **派单页加一个手动筛选下拉**，让运营自己选"只看有冷藏车的"

两条都是新功能而不是"补完没做完的部分"，**需要 Frank 定，本次未做**。
