## 一、为什么是"手动选"而不是自动带

后端 `/carriers/match` 的 `vehicleType` 在 2026-08-06 已实现并验证
（车型硬筛，未维护过车型的承运商不排除）。但前端一直没法传，原因不是漏了：

**`orders` 表根本没有「本单需要什么车型」这个字段**，只有 `business_type`
（TRUCK_LTL / TRUCK_FTL / LOCAL_DELIVERY）和 `transport_type`（FTL/LTL），
从它们推不出车型——硬推就是替业务编规则。

两条路：给订单加车型要求字段（迁移 + 建单/编辑页 + 派单页传参），
或派单页加手动筛选下拉。**本次选后者**：不动表结构、可逆，
将来真要加订单字段也不冲突（那时把下拉的默认值设成订单要求即可）。

## 二、改了什么

`admin/src/pages/OrderAssign.tsx`：

1. **加车型下拉**，选项来自基础数据 `md_vehicle_types`
   （走已有的 `useMasterDataOptions('vehicle-types')`，
   后端 `MD_TABLES` 里本来就支持这个类型，无需改后端）。
   默认「不限车型」= 不传参数，**行为与改动前完全一致**。
2. **把原来的一个 effect 拆成两个**：
   - `useEffect([id])` 只拉订单
   - `useEffect([order, vehicleFilter])` 拉承运商
   这样换车型只重拉承运商，不用重拉订单。
3. **换筛选时保留运营已填的报价**：
   ```js
   setCarrierPrices((prev) => {
     const next = {}
     list.forEach((c) => { next[c.id] = prev[c.id] ?? 0 })
     return next
   })
   ```
   原来是无条件重置成 0——那样运营填完价改一下车型，输入就全没了。
4. **筛完一家不剩时给明确解释**，而不是让人以为系统坏了。
   文案特意写清楚：**未维护过车型的承运商不会被筛掉**，
   所以列表为空意味着所有承运商都明确不具备该车型。
5. 换筛选用独立的 `loadingCarriers`，不让整页骨架屏闪。

三语 key 3 个（`filterByVehicle` / `vehicleAny` / `noCarrierForVehicle`）已补。

## 五、关联影响

- **默认不筛，行为与改动前一致**；不选车型时请求参数与昨天完全相同。
- 路线参数（`routeFrom`/`routeTo`）逻辑未动，仍是只排序不排除。
- **确认不受影响**：`/carriers` 列表页、承运商门户、其余两端均未触碰。
- 前置依赖提醒：`carriers.vehicle_types` 目前两家都是空的、`carrier_vehicles`
  0 条，**所以现在无论选哪个车型都不会筛掉任何人**（空集按设计视为"未维护"）。
  这个筛选要真正生效，得先在承运商管理页把两家的车型填上——**属业务数据，
  不该由开发凭空填**。
