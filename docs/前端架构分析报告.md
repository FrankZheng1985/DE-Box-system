## 二、分层现状判定：「两层半」结构

理想的三层划分是：**基础组件**（与业务无关的 UI 积木）→ **业务组件**（可复用的业务块）→ **业务页面**（组装 + 页面级逻辑）。本项目现状：

### 基础组件层：有雏形，质量不错

复用是真实的，不是摆设：

| 组件 | 被引用页面数 |
|------|:---:|
| StatusBadge | 13 |
| Modal | 12 |
| StatCard | 9 |
| ConfirmDialog | 6 |
| Pagination（本次新增） | 11 |
| Toast（本次新增） | 8 |
| form/（Label/TextInput/SelectInput/TextArea/SectionTitle，本次新增） | 2 |

`Modal` 值得单独夸一句：ESC 关闭、锁背景滚动、遮罩点击关闭、4 档尺寸、i18n 都做了，是这层的标杆。

**仍然缺失**：统一的表格组件。21 个页面各自内联 `<table>`，规范里的 `table-fixed + colgroup` 对齐规则目前靠每个页面自觉遵守，没有组件兜底。

### 业务组件层：存在，但多数是「单页专用拆件」

OrderFilesSection、ClientCreditPanel、CarrierInquiryPanel、OrderImportModal 等确实抽出来了，
但引用数几乎都是 1 —— 它们本质是「把大页面的一块搬出去」。这没错（控制了页面行数），
只是要认识到这层**还没有真正的跨页复用**。EntityAccountsPanel（2 处）、InquiryQuotationTabs（2 处）是仅有的例外。

### 页面层：扁平堆放，页内自治

36 个页面平铺在 `pages/` 一个目录，没按业务域分子目录。
所有数据获取直接在页面里调 `api.get/post`（FinanceManagement 有 11 处），
API 端点字符串散落各页 —— **没有按业务域的 service 层**，
后端改一个端点路径需要全文搜索才能找全调用点。

## 三、做得好的地方（值得保持）

1. **路由层规范**：全部懒加载 + Suspense；`ProtectedRoute` 挡用户类型、`PermissionRoute` 挡权限；
   登录页独立于 Layout。App.tsx 里还留了「create 必须写在 :id 之前」的防坑注释。
2. **api.ts 封装到位**：统一超时、重试、`ApiError` 分类（超时 / 网络错误可区分）、
   按 `messageCode` 翻译错误提示，并且有明确注释说明为什么不能反向 import i18n（循环依赖）。
3. **i18n 覆盖率 100%**：admin 36/36、客户门户 12/12 页面全部接入 `useTranslation`。
4. **TypeScript `strict` 开启**，类型集中在 `types/`。
5. **注释是「讲为什么」的注释**，且大量引用踩坑编号，三端风格统一。
6. **大页面内部有自我组织**：OrderCreate 虽长，但内部拆了 TruckFormSection / ContainerFormSection /
   OrderSummary，且只有 9 个 `useState` —— 不是意大利面。

## 四、主要问题（按影响排序）

### 🔴 问题 1：三端之间靠复制粘贴共享代码（未解决）

| 文件 | 重复情况 |
|------|---------|
| `BrandMark.tsx` | 三份**完全相同**（diff 为 0） |
| `format.ts` | 客户门户与承运商门户完全相同，与 admin 仅 20 行差异 |
| `LanguageSwitcher.tsx` | 三份仅 7 行差异 |
| `OrderImportModal` / `InquiryImportModal` | admin 与客户门户各一份，约半数内容相同 |
| `AuthContext` | 三份结构类似的实现 |

**后果**：改一个格式化函数要记得改三处，漏一处就是三端行为不一致，且这类 bug 很隐蔽。

### 🔴 问题 2：核心页面超过行数红线（未解决）

红线 800 行。当前超线：OrderCreate 1278、OrderDetail 1197、FinanceManagement 1070、QuotationCreate 990、OrderManagement 976。

其中 **FinanceManagement 有 29 个 `useState`**，状态管理明显过载 —— 四个里最该先拆的是它
（OrderCreate 虽最长但内部结构反而最好）。另有约 13 个页面在 500–800 行黄灯区。

### 🟡 问题 3：ClientList 与 CarrierList 是复制粘贴关系（部分缓解）

两个 700 行级页面 diff 出 777 行 —— 结构骨架相同、实体不同。
本次抽掉分页后差距缩小，但「搜索 + 筛选 + 表格 + Toast + 分页」这套列表页骨架仍是各写一遍。

### 🟡 问题 4：没有数据层（未解决）

页面直接拼 URL 调 api，没有 `services/orderService.ts` 这类按域封装，也没有请求缓存。
目前规模还扛得住，但每加一个页面这个债多一分。

### 🟡 问题 5：前端测试为零（未解决）

三端共 0 个测试文件。`format.ts`、`api.ts` 的错误处理这类纯逻辑最容易也最值得先补。

## 七、维护须知

- 新增列表页时，分页**直接用 `components/Pagination`**，不要再手写翻页按钮
- 新增提示时，**直接用 `components/Toast`**，不要在页面里再定义一份
- 表单控件从 `components/form` 导入
- `OrderManagement.tsx` 里有个本地 `interface Pagination`（分页元数据类型），
  与分页组件重名，那里必须用 `import PaginationBar from '../components/Pagination'` 别名导入
